# 第 05 章 数据建模与数据库基础：关系模型、schema、索引、事务、ORM

*schema 是你对世界的断言，约束是这个断言被强制执行的部分——AI 能写出跑得通的表，但只有你知道哪些事实"绝不允许发生"。*

## 为什么这一章对你重要

代码写错了，改一版重新部署；数据写错了，它就在那里，而且已经被下游读走、算进报表、发给客户了。数据层是整个系统里**唯一没有 undo 的层**。

AI 写 schema 的时候看不见三样东西：你的业务不变量（invariant，绝不允许出现的状态）、你的数据量增长曲线、你的并发形态。所以它交付的东西有一个稳定特征：**在一次单人操作、一百行数据、无并发的条件下全对**。没有外键、没有唯一约束、没有索引、没有事务边界，全靠"应用代码会记得的"——直到第二个进程、第二个开发者、或者一次重试出现。

这一章要给你的是三层能力：能读懂一份 schema 在断言什么、能预测一条查询在数据量涨一百倍后会怎样、能推演两个请求同时来会发生什么。数据库在真实负载下怎么坏（锁等待、慢查询、连接池、迁移锁表、复制延迟、备份恢复）见第 06 章；这一章讲的是那些故障的**根**——建模、索引、事务的机制本身。

## 核心机制

### 5.1 第一性原理：数据库是"被强制执行的事实约定"

大多数人把数据库当"存东西的地方"。这个心智模型是所有错误的源头。更准确的说法是：

> 数据库是一组**关于世界的断言**，加上一台**拒绝接受违反断言的写入**的机器。

区别在"拒绝"两个字。你的应用代码也可以检查"一个用户只能有一个默认收货地址"，但应用代码有很多份、会被绕过：另一个 endpoint、一个后台脚本、一次数据修复、你昨晚让 AI 写的一次性 backfill、一次并发。而数据库的约束只有一份，任何路径进来都要过它。

由此推出本章的判断主轴：**每次看 AI 生成的 schema，你问的不是"字段够不够"，而是"哪些坏状态在这份 schema 下是可以被写进去的"**。如果一个绝不该发生的状态在物理上可写，那它迟早会被写进去——这不是概率问题，是时间问题。

三条推论，后面所有内容都是它们的展开：

1. **能用约束表达的规则，不要放在应用层。** 约束是免费的正确性（写入时几乎零成本，错误在发生的那一刻就被挡住，而不是三个月后在报表里被发现）。
2. **数据的形状决定查询的代价。** 索引不是"性能优化"，是建模的一部分：你决定了哪些查询是 O(log n)，哪些是 O(n)。
3. **写入的原子单位是事务，不是语句。** 业务上"一件事"如果被拆成三条自动提交的语句，那么系统就存在一个"只做了一半"的状态，而它没有任何人设计过。

### 5.2 关系模型：一张表是一个命题

关系模型不是"Excel 加强版"。它的原始定义是逻辑学的：**一张表是一个谓词（predicate），一行是一个为真的事实**。

`orders(id, customer_id, status, placed_at)` 这张表的谓词是："编号为 id 的订单，由 customer_id 下单，处于 status 状态，下单时间为 placed_at。"表里存在这一行 = 断言这句话是真的。表里没有 = 这句话不成立（封闭世界假设）。

这个视角一旦拿到手，很多设计问题会自动有答案：

- **一列存两种含义就是两个谓词挤在一张表里。** 比如 `amount` 有时是订单金额、有时是退款金额（负数），你就无法只靠这张表回答任何一个干净的问题。拆表，或者加一个显式的 `kind` 列并配 CHECK 约束。
- **NULL 意味着"这个事实的这一部分未知"**，而不是 0、空字符串或者 false。如果一个列在业务上永远有值，就 NOT NULL——你等于把"未知"这个状态从宇宙里删掉了，下游所有代码少一个分支。
- **一行代表一个事实，就应该有一个唯一标识这个事实的方式**（主键）。没有主键的表意味着你无法指着一行说"就是它"，也就无法安全地更新或删除它。

**多对多要中间表**：`students`、`courses`、`enrollments(student_id, course_id, enrolled_at)`。AI 有时会在 `students` 表里塞一个 `course_ids` 字符串列（逗号分隔）或 JSON 数组。症状：想查"选了课程 X 的所有学生"就只能全表扫描 + 字符串匹配，而且 `"3"` 会匹配到 `"13"`。这是把关系模型退化成了文件格式。

### 5.3 约束：把不变量写进数据库

先明确"业务不变量"是什么：**一句关于系统状态的、必须永远为真的话**。例如：

- 一个订单必须属于一个存在的客户。
- 同一个租户下，用户邮箱唯一（跨租户可以重复）。
- 订单金额不为负。
- 一个用户在同一时刻只能有一个默认地址。
- 库存不为负。

这五句话对应五种约束工具：

| 工具 | 表达什么 | 违反时的信号 |
|---|---|---|
| PRIMARY KEY | 这一行的身份 | `duplicate key value violates unique constraint "..._pkey"` |
| FOREIGN KEY | 引用的东西必须存在 | `violates foreign key constraint`（插入时）/ `still referenced`（删除父行时） |
| UNIQUE（可复合、可带条件） | 某个组合在全表只出现一次 | `duplicate key value violates unique constraint` |
| NOT NULL | 这个事实的这一部分永远已知 | `null value in column "x" violates not-null constraint` |
| CHECK | 一行内部的取值规则 | `new row for relation "x" violates check constraint` |

几个高价值细节：

**复合唯一 vs 单列唯一。** 多租户系统里 `UNIQUE(email)` 是错的，`UNIQUE(tenant_id, email)` 才对。AI 在生成多租户 schema 时极常漏掉 `tenant_id`——这不仅是唯一性问题，也是数据泄漏问题（见第 09 章）。

**部分唯一索引表达"只能有一个"。** "一个用户只能有一个默认地址"用 `UNIQUE(user_id) WHERE is_default` 表达。这是那种应用层几乎必然写错（先查再写、并发下两个都插进去）而数据库一行搞定的规则。

**外键的删除行为是业务决策，不是技术细节。** `ON DELETE CASCADE`（连带删）、`RESTRICT`（不许删）、`SET NULL`（断开引用）三选一，AI 通常默认给 CASCADE，因为它让测试更好写。后果是删一个客户静默删掉他所有历史订单——财务数据凭空消失，而且没有任何日志说明。**你该问 AI**："每个外键的 on delete 行为是什么？删除一条父记录会连带影响哪几张表、多少行？"

**CHECK 只能约束一行内部。** `CHECK (amount >= 0)`、`CHECK (ends_at > starts_at)`、`CHECK (status IN ('pending','paid','shipped','cancelled'))` 都可以；"库存不为负"如果库存是另一张表的聚合，CHECK 就管不到——那属于事务与锁的范畴（5.13）。知道约束的边界在哪，才知道剩下的部分必须靠并发控制补上。

**"约束会不会太严，以后不好改？"** 会。这是真实成本：加约束时要清洗存量脏数据，加 NOT NULL 要给默认值。但这个成本是**一次性的、在你可控的时间发生的**；没有约束的成本是**持续的、在最糟糕的时间以最难查的形式出现的**（报表对不上、客服说"这个订单没有客户"）。

### 5.4 主键策略：三种 ID 的取舍

| 策略 | 优点 | 代价 |
|---|---|---|
| 自增整数 | 小、有序、索引局部性好 | 可枚举（`/orders/1005` 能猜到别人的）、多库合并会撞、ID 泄漏业务量 |
| 随机 UUID | 全局唯一、客户端可预生成、不泄漏信息 | 16 字节、随机分布导致索引写入分散、页面命中率下降 |
| 时间有序 ID（UUIDv7 一类） | 全局唯一 + 大致按时间递增，兼顾写入局部性 | 泄漏创建时间；实现要选对 |

两个更重要的原则，超过"选哪个"本身：

- **内部主键和对外标识可以分开。** 表内部用自增做 join，对外 URL 里暴露另一个随机的 `public_id`（带 UNIQUE 索引）。这样既有索引局部性，又不可枚举。
- **不要用业务字段做主键。** 邮箱、手机号、订单号看起来唯一，但它们会变（用户改邮箱），而主键一改，所有引用它的外键都要跟着改。业务唯一性用 UNIQUE 约束表达，身份用一个永不改变、无业务含义的代理键（surrogate key）表达。

### 5.5 规范化与"刻意的冗余"

规范化的机械化定义容易背了没用。它的实质只有一句：**同一个事实只存一份**。因为存两份就必然会有更新到一份忘了另一份的时刻（更新异常）。

反过来，什么时候该刻意冗余？两种，而且要分清：

**(a) 为读性能冗余**（缓存性质）：把 `orders` 的条数冗余到 `customers.order_count`。这是一份可以从源头重算的派生数据，风险是它会漂移。判断标准：**有没有一个"重算并对账"的路径？**没有的话，这份冗余迟早变成谎言。这类东西通常应该缓存在别处而不是主表（见第 07 章）。

**(b) 为正确性快照**（历史性质）：订单项里必须存下单那一刻的 `unit_price`，而不是 join 到 `products.price`。因为商品今天涨价了，去年的订单金额不能跟着变。这不是冗余，这是**两个不同的事实**：商品的"当前价"和订单的"成交价"。

AI 极常犯的错是把 (b) 做成 join——它看起来更"规范"，也更省一列，但它把历史事实变成了会随现在变化的东西。**症状**：财务报表里去年的总额每天都在变，没人知道为什么。**你该问 AI**："这张表里哪些值是当前状态、哪些是历史快照？金额、地址、名称在下游变更后，历史记录会不会跟着变？"

### 5.6 类型选择：那些"看起来对"的错

这一节的每一条都能独立造成一次事故，而且 AI 每一条都会犯。

**钱不要用浮点数。** `0.1 + 0.2 != 0.3`，二进制浮点无法精确表示大多数十进制小数。一万笔累加之后会差出几分钱，对账永远对不平。用定点小数（`NUMERIC(12,2)` 一类）或者**存最小单位的整数**（分、cents）。**症状**：报表尾数漂移；`WHERE amount = 19.99` 查不到明明存在的行。**问 AI**："金额用什么类型存？有没有除法或百分比计算？舍入在哪一步发生、用什么舍入规则？"

**时间必须带时区，且存 UTC。** 存本地时间（`2026-04-05 02:30:00` 无时区）的后果：夏令时切换时这个时刻可能不存在或出现两次；服务器换区域后全部数据偏移几小时；两个用户看到不同的顺序。规则：**存储用带时区的时间戳（内部即 UTC），只在展示层转成用户时区**。悉尼这种有夏令时的地方尤其致命。另外，"用户选的会议日期"这种**未来的本地时间**要单独考虑：存 UTC 会在时区规则变更后指向错误的本地时刻，这类字段应存"本地时间 + 时区标识"。**问 AI**："这个时间列是绝对时刻还是用户本地日历时间？存的是 UTC 吗？夏令时切换那天会发生什么？"

**别用字符串存日期、数字、布尔。** `'2026-04-05'` 作为文本可以排序，`'5'` 和 `'10'` 排序就错了；而且数据库无法用类型检查挡住 `'not-a-date'`。

**NULL 是三值逻辑，不是"空"。** 三个必须记住的行为：

```
NULL = NULL        →  NULL（不是 true）
NULL <> 'x'        →  NULL（所以 WHERE status <> 'done' 会漏掉 status 为 NULL 的行）
COUNT(col)         →  不计 NULL；COUNT(*) 计
SUM(全是 NULL)     →  NULL 而不是 0
UNIQUE 列          →  多数实现允许多个 NULL 并存
```

第二行是最常见的静默 bug：一个"排除已完成"的查询悄悄漏掉了一批行，数量少的时候没人发现。**症状**：两个查询的结果条数加起来不等于总数。

**枚举用 CHECK 或引用表，别用自由文本。** 否则会同时存在 `'paid'`、`'Paid'`、`'PAID'`。

**软删除（`deleted_at`）是一个有代价的决定。** 好处是可恢复、可审计；代价是：从此以后**每一个查询都必须记得加 `WHERE deleted_at IS NULL`**，忘一次就是数据泄漏或重复计数；唯一约束也失效了（删掉的行还占着 email 的唯一位置，用户重新注册会失败）。如果要软删除，唯一约束要写成部分索引 `UNIQUE(email) WHERE deleted_at IS NULL`，并且强制通过统一的视图或查询层访问。**问 AI**："软删除后，唯一约束怎么处理？有多少个查询需要加过滤条件？漏掉一个的后果是什么？"

**JSONB 是逃生舱，不是 schema。** 它适合真正不定形的东西：第三方原始回包、用户自定义字段、审计快照。它不适合承载你会频繁查询和过滤的核心字段——因为里面的键没有类型检查、没有 NOT NULL、拼错一个键名不会报错只会静默返回空。AI 很喜欢用一个 `data JSONB` 列"以后再说"，代价是三个月后你无法回答"有多少用户的 plan 是 pro"而不做全表扫描。判断标准：**你会不会 WHERE 这个字段、会不会 JOIN 它、它有没有不变量**——三个有一个是"是"，就把它提成真正的列。
