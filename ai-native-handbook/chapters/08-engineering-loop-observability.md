# 第 08 章 工程闭环与可观测性：git、测试、CI/CD、部署、日志与 trace——让 AI 的产出可验证、可回滚、可诊断

*你的瓶颈早就不是"写"，而是"验证与回退"：这一章教你把验证从"我记得检查"变成"系统强制检查"，把回退从"我再让它改改"变成"一条命令回到 20 分钟前"。*

## 为什么这一章对你重要

AI 每小时能产出你三天的代码量，但它的自我报告是不可信的证据：它说"测试全过"，可能是它改了测试；它说"只改了那个函数"，可能顺手删了一个 lint 规则。速度差 × 证据缺失 = 盲飞。

这一章讲的六件东西——git、测试、CI、部署、回滚、可观测性——都不是"工程洁癖"，它们是同一件事的六个面：**把系统的状态变成可比较、可重放、可回退的**。有了这套骨架，你才敢让 agent 一次改 30 个文件；没有它，你连"它到底改了什么"都答不上来。

顺带一提：这也是你以 FDE 身份进一家公司时，第一眼要看的东西。一家没有测试、没有 staging、回滚要人工操作半小时的公司，你不能给它上激进的 AI 方案——不是技术不行，是它接不住变更。

## 核心机制

### 8.1 总原则：变更的单位是"小的、可逆的、有证据的"

三个形容词各对应一套机制，本章的所有内容都挂在这三个词上：

| 属性 | 意思 | 靠什么保证 | 破坏它的典型行为 |
|---|---|---|---|
| **小** | 一次变更只改一件事 | 分支、commit 粒度、feature flag | AI 一口气改 30 个文件、顺手重构 |
| **可逆** | 出事能在分钟级回到上一个已知好状态 | 不可变制品、一键回滚、迁移的兼容设计 | 破坏性迁移、回滚了代码没回滚配置 |
| **有证据** | "它好了"是被观察到的，不是被声称的 | 测试输出、CI 状态、指标与 trace | "我运行了测试，都通过了"（无原始输出） |

记住一句判据：**只要一个变更同时缺两条以上，它就不该上线。** 这句话可以直接当审查门槛用。

### 8.2 git 的内部模型：快照、DAG、指针

大部分人对 git 的困惑来自把它想成"差异的堆叠"。它不是。三句话是全部：

1. **commit 是一次完整快照**（内容寻址：相同内容只存一份），不是 diff。diff 是两个快照现算出来的。
2. **提交构成一张有向无环图（DAG）**，每个 commit 记着它的父 commit。merge commit 有两个父。
3. **分支只是一个指向某个 commit 的可移动指针**，`HEAD` 是"你现在站在哪"的指针。创建分支的成本 ≈ 写 41 个字节。

从这三句能推出你日常需要的所有判断：

- 建分支几乎免费 → **每个 AI 任务一个分支**没有任何理由不做。
- 快照不可变 → 已经 commit 的东西几乎丢不掉。`git reflog` 记录了 HEAD 的每一次移动，绝大多数"我把代码搞没了"都能从 reflog 里捞回来。**没 commit 的东西才真会丢**——所以让 AI 大改之前先 commit，这是最便宜的保险。
- `reset --hard` 只挪指针，但会覆盖工作区未提交的改动 → 它是唯一真正危险的常用命令。
- **rebase 重写历史**（生成一串新的 commit，旧的成为孤儿），merge 保留真实拓扑。实用差异只有一条：**rebase 私有分支，merge 公共分支**。别人已经拉走的历史被你重写，会给对方制造一堆假冲突。

### 8.3 diff 是你审查 AI 的唯一界面

AI 给你的自然语言总结是**它对自己行为的记忆**，而记忆是被压缩过的。diff 是文件系统的事实。这两者不一致的频率比你以为的高得多。

读 diff 的顺序（照做，别按文件顺序读）：

1. **先看文件清单**（`git diff --stat`）。问一句：这些文件里，有几个是我预期它会碰的？多出来的每一个都要有解释。
2. **先读删除，再读新增。** 新增的代码它会主动告诉你；删掉的东西它通常不会提。最危险的改动几乎都长成"删除"的样子。
3. **专门扫这七类红旗**：
   - 配置与规则文件：`.eslintrc`、`tsconfig.json`、`pyproject.toml`、CI 配置——**改这些等于改游戏规则**
   - 测试文件的改动（尤其是断言被放宽、被删、被 `skip`/`xfail`）
   - 依赖清单与 lockfile（新加了什么包？为什么？）
   - 任何 `try/except` 的扩大，特别是空的 catch
   - 硬编码的常量、URL、路径、超时值
   - 权限、认证相关的分支条件（见第 09 章）
   - `.gitignore` 的改动（可能是为了把某个不该提交的文件塞进来，也可能相反）

**`git blame` 的用法不是抓人，是找上下文**：一行奇怪的代码，blame 出它是哪个 commit 加的，读那次的完整改动和 commit message，你通常能立刻明白它在防什么。AI 经常删掉这种"看起来多余"的防御性代码——它看不到那行代码背后的那次事故。

一个高价值动作：**让 AI 自己审自己的 diff**。原话是"把 `git diff` 的完整输出读一遍，逐条列出这次改动中**你没在总结里提到**的部分，以及每一处的风险"。它对自己的输出做审查，比它做总结要诚实得多——因为这次它面对的是文本，不是记忆。

### 8.4 AI 协作的 git 纪律

八条，直接可用：

1. **一个任务一个分支。** 让 agent 在 main 上直接大改，等于放弃了"上一个已知好状态"这个概念。
2. **动手前先 commit 干净。** 工作区必须是 clean 的，否则 AI 的改动和你自己的改动混在一起，你无法用 `git checkout .` 一键放弃。
3. **提交粒度 = 一个可独立回滚的意图。** "加了 X 功能"是一个 commit；"顺便格式化了整个文件"必须是另一个。混在一起时 diff 不可读，回滚也回滚不动。
4. **禁止 `git add -A` 式的无差别提交。** 至少 `git status` 看一眼清单。
5. **并行任务用 worktree，不用切分支。** 同一个仓库可以 checkout 出多个独立目录，各自一个分支，互不干扰——多个 agent 同时干活时这是唯一不会互相踩的方式。
6. **commit message 写"为什么"，不写"改了什么"**——"改了什么" diff 已经说了。
7. **合并前跑一次完整验证**，而不是"我记得刚才跑过"。
8. **每个变更都要有明确的回滚动作**，而且你要能在不看文档的情况下说出来。

### 8.5 secret 进了 git 等于已经泄露

机制：git 保存的是历史快照。你在下一个 commit 里删掉 `.env`，那个文件仍然完整地躺在前一个 commit 里，`git log -p` 就能翻出来。仓库如果 push 过、被 fork 过、被 clone 过，你已经无法收回。

所以唯一正确的处置顺序是：**先假定它已泄露 → 立即轮换（rotate）那个密钥 → 然后才谈清理历史**。清理历史是重写整条 DAG，代价大且不彻底。

预防措施是三层，缺一层都会漏：`.gitignore` 里有 `.env`（防手滑）+ 提交前扫描（防 AI 手滑）+ 服务端拒绝（防两者都失效）。另外提醒一个 AI 特别容易犯的变体：**把 secret 写进代码作为默认值**——`API_KEY = os.getenv("API_KEY", "sk-真实的key")`。这既泄露了密钥，又让"配置缺失"这个错误永远不会暴露。

### 8.6 测试是给 AI 的规格说明，不只是给自己的保险

这是本章最值钱的一节。

你和 AI 之间最大的摩擦是：你用自然语言描述"我想要的行为"，它用自然语言复述它的理解，双方都感觉对上了，实现出来是另一回事。**测试是一种不会被误读的规格语言**——它把"我想要的行为"写成一段机器可以判定真假的断言。

具体做法（test-first as prompt）：

```
# 先给它这个，再让它实现
def test_退款金额不能超过原订单金额():
    order = create_order(amount=100)
    with pytest.raises(RefundExceedsOrder):
        refund(order, amount=150)

def test_重复退款请求只生效一次():
    order = create_order(amount=100)
    refund(order, amount=100, idempotency_key="k1")
    refund(order, amount=100, idempotency_key="k1")
    assert order.refunded_total == 100
```

区别在哪：不写测试时，它会给你一个能跑通 happy path 的实现，边界行为随机；先写测试时，那些边界是**约束**而不是建议。而且验证成本从"我读一遍它写的代码"降到"跑一条命令"。

**顺序很重要：先写测试、确认它是红的（失败的）、再让 AI 实现、变绿。** 跳过"确认红"这一步，你就无法区分"实现对了"和"这个测试根本没在测东西"——一个断言写错的测试在任何实现下都是绿的。

一个附带的好处：当你说不清要什么的时候，你也写不出测试。写不出测试本身就是信号——说明你的需求还没想清楚，这时候让 AI 开写只会得到一堆你无法判断对错的代码。

### 8.7 测试分层：每一层能证明什么、不能证明什么

| 层 | 测什么 | 量级 | 能证明 | 不能证明 |
|---|---|---|---|---|
| 单元 | 单个函数/类的逻辑 | 毫秒级，成百上千个 | 这段逻辑的边界正确 | 组件之间接得上 |
| 集成 | 组件 + 真实依赖（真 DB、真队列） | 百毫秒~秒级，几十~几百个 | SQL 对、迁移能跑、契约没错位 | 用户流程走得通 |
| 端到端 | 完整用户路径 | 秒~分钟级，个位数~几十个 | 系统整体是活的 | 出错时是哪一层坏的 |

三条实用判据：

- **哪一层的 bug 让你最疼，就往哪一层加测试。** 教条式追求"金字塔形状"不如按事故历史分配。
- **端到端测试是最贵的资产**：写起来慢、跑起来慢、坏起来 flaky、定位起来困难。它的正确用法是**少而关键**——覆盖"钱、登录、数据不丢"这三类路径就够了。
- **AI 时代集成测试的权重应该上调。** AI 写单元测试写得很好（局部逻辑它看得清），最容易出错的恰恰是它看不到全貌的地方：组件间的契约、真实 DB 的行为、迁移的兼容性。而这些只有集成层能抓。

### 8.8 假测试图鉴：绿色但什么都没证明

这是 AI 产出中最隐蔽的一类问题，因为它长得跟真测试一模一样，而且**绿灯会让你停止思考**。五种：

**1. mock 掉了被测对象本身。** 测 `send_invoice()`，结果把 `send_invoice` 依赖的所有东西都 mock 了，最后断言的是"mock 被调用了一次"。这测的是"我写的代码调用了我 mock 的代码"，恒真。
- 识别法：**如果实现里的核心分支全删掉、只留一个空函数，这个测试还绿吗？** 绿的话它就是假的。

**2. 同义反复。** 测试里重新实现一遍被测逻辑，然后断言两者相等。`assert calc_tax(100) == 100 * 0.1` —— 实现改成 0.2，测试跟着改成 0.2，永远绿。
- 识别法：断言的右边应该是**你手算出来的字面量**（`== 10`），不是表达式。

**3. 只有 happy path。** 没有空输入、没有超限、没有并发、没有依赖失败、没有超时。
- 识别法：数一下测试函数名里带"失败/无效/超时/重复/为空"的比例。低于三分之一就是 happy path 堆砌。

**4. 断言太弱。** `assert result is not None`、`assert response.status_code == 200`、`assert len(items) > 0`。返回一个空壳也能过。
- 识别法：问"如果函数返回一个完全错误但结构合法的结果，这个断言会红吗？"

**5. 快照/golden 测试被无脑更新。** 输出变了，就把快照文件更新一遍，然后说"测试通过了"。
- 识别法：diff 里出现大段 `.snap` / `expected.json` 的改动而实现改动很小，这是一个高优先级红旗。

一句可以直接用的话：**"把这个测试保留、把实现替换成一个空函数或恒返回固定值的函数，测试会红吗？"** ——这是判断测试有没有价值的最快问句。

### 8.9 flaky test：同样的代码，时红时绿

flaky 的成本不在浪费的那几分钟，在于**它训练你和 AI 忽略红灯**。一旦"重跑一下就好了"成为习惯，CI 就失去了全部意义——它拦不住任何东西了。

四个根因，各有指纹：

| 根因 | 指纹 | 修法 |
|---|---|---|
| 时间与时区 | 只在特定时段/跨月/跨夏令时失败 | 注入固定时钟，禁止测试里调 `now()` |
| 测试间共享状态 | 单独跑绿、全量跑红；换个顺序结果就变 | 每个测试自建数据、事务回滚、禁用随机顺序前先修隔离 |
| 真实并发/异步 | 随机失败率稳定在百分之几，机器越忙越红 | 去掉 `sleep(0.5)` 式等待，改成等待条件成立 |
| 外部依赖 | 失败集中在网络抖动时 | 集成层用容器化的真依赖，别打外网 |

**处置纪律：flaky test 要么当天修，要么显式隔离并挂一个到期日，绝不允许"重跑到绿"。** 如果你发现 AI 的工作日志里出现连续三次重跑同一个 CI，这本身就是一个需要你介入的信号。

### 8.10 覆盖率的误导性

覆盖率统计的是"这行代码在测试运行中被执行过"，不是"这行代码的行为被断言过"。把所有断言删掉，覆盖率一点不掉。

所以：**覆盖率适合做下限告警（"这个新模块 0% 覆盖"是真信号），不适合做目标（"必须 80%"会直接催生上面那五种假测试）**。当把覆盖率设成 KPI 时，AI 会非常高效地生成一堆调用了函数但不断言任何东西的测试来达标。

更有用的替代指标是**变异测试（mutation testing）的思路**：故意改坏一行实现（把 `>` 改成 `>=`、把 `and` 改成 `or`、删掉一个 `return`），看有没有测试变红。没变红，说明那段逻辑其实是裸奔的。这个思路你不需要工具也能手动做——它正是下面"落地后的练习"的核心动作。

### 8.11 CI 的本质：让机器拒绝你

CI 的价值不是"自动跑测试"，是**把验证从人的自觉变成系统的强制**。你会累、会赶时间、会相信 AI 说的"我检查过了"；CI 不会。

一条最小但完整的流水线，以及各阶段的作用：

```
push / PR
   │
   ├─ 1. lint + format      秒级    风格与低级错误      ← 失败立即阻断
   ├─ 2. type check         秒级    契约错位、空值      ← 失败立即阻断
   ├─ 3. unit tests         秒~十几秒 逻辑回归
   ├─ 4. secret scan        秒级    密钥泄漏           ← 失败立即阻断
   ├─ 5. build              十几秒~分钟 产出不可变制品
   ├─ 6. integration tests  分钟级   真 DB / 真队列
   └─ 7. deploy to staging  分钟级   （合并后触发）
```

四条设计原则：

- **快的、便宜的、最容易失败的放前面。** 你要的是 30 秒内知道"这不行"，而不是 12 分钟后。
- **阻断策略要分级**：lint/type/secret/单元测试红了 = 硬阻断；集成测试红了 = 阻断但允许人工判断是否 flaky（并记录）；覆盖率下降 = 警告不阻断。全部硬阻断会导致人绕过它，全部软警告等于没有。
- **PR 门禁必须是"必须通过才能合并"的服务端规则**，不是"大家记得看一眼"。前者是机制，后者是愿望。
- **总时长有预算。** 超过十几分钟的流水线，人就会开始并行干别的事、失去反馈闭环。慢就拆：PR 上跑快的，合并后跑慢的全量。

**CI 的另一个隐藏作用：它是唯一一个 AI 无法自我欺骗的证据源。** 所以你的工作协议里应该有这一条：*交付时附上 CI 运行的链接或原始输出，而不是"测试通过"这四个字*。

### 8.12 "本地能跑 CI 不能跑"：环境差异的五个来源

这不是玄学，五个来源，按出现频率排：

1. **本地有未提交/未忽略的文件**——最常见。AI 建了个 `config.local.json` 用着，但它在 `.gitignore` 里。识别法：`git stash -u` 之后本地也跑不了，就是这个。
2. **依赖版本漂移**——本地是几个月前装的，CI 是干净安装。没有 lockfile，或安装时没用"严格按 lockfile"的模式（见第 01 章）。
3. **环境变量**——本地 shell 里有，CI 里没有。而代码给了默认值，于是不报错，只是行为不同。
4. **文件系统与大小写**——本地 macOS 不区分大小写，CI 上的 Linux 区分。`import Utils` 在本地能找到 `utils.py`，在 CI 上直接 ImportError。
5. **并发度与顺序**——CI 机器核少、慢，暴露出竞态；或者 CI 用随机顺序跑测试，暴露出测试间的隐式依赖。

判断口诀：**如果 CI 红本地绿，先怀疑本地脏，不要怀疑 CI 坏。** CI 是干净环境，它更接近真相。

### 8.13 不可变制品：构建一次，到处部署

核心原则：**同一份被测试过的二进制/镜像/包，原封不动地走过 staging 和 prod；环境之间的差异只能来自注入的配置。**

违反它的典型是"在每个环境各自 build 一次"。此时 staging 上测的东西和 prod 上跑的东西不是同一个东西——依赖解析时间不同、基础镜像的 latest 标签指向变了、构建时嵌进去的变量不同。于是你的 staging 验证不再有推断力。

推论三条：
- 制品要有**唯一标识**（内容哈希或构建号），且能反查到具体的 commit。出事时"现在跑的是哪个 commit"必须是秒级可答的问题。
- **禁止用 `latest` 之类的浮动标签**做基础镜像或部署引用。它让"回滚到昨天的版本"变成一个无法定义的操作。
- **配置从外部注入，且缺失时必须启动失败**。给必需配置写默认值是一种把配置错误延迟到运行时的行为——它把一个启动期的明确崩溃，换成了运行期的静默错误行为。

### 8.14 部署策略与探针：流量是被"健康"这个信号切换的

三种主流策略，本质是"新旧版本共存时间"和"暴露面"的不同取舍：

| 策略 | 机制 | 回滚速度 | 代价 |
|---|---|---|---|
| 滚动 | 一批批换实例，新旧共存几分钟 | 中（要滚回去） | 新旧版本必须能同时工作 |
| 蓝绿 | 两套完整环境，切流量开关 | 最快（切回去） | 双倍资源；共享的 DB 仍是同一个 |
| 金丝雀 | 先给 1% 流量，看指标，逐步放大 | 快 | 需要按版本切分的指标才有意义 |

**三种策略有一个共同前提：新旧版本在共存期间必须互相兼容。** 这是最容易被 AI 忽略的一条——它假设"部署"是一个瞬间。实际上任何非停机部署都有一段两个版本同时在跑、同时读写同一个数据库、同时消费同一个队列的窗口。

**探针（probe）决定流量什么时候进来：**
- **liveness（存活）**：失败 → 进程被重启。它只该检查"这个进程还在响应吗"。**在 liveness 里查数据库是一个经典的自毁设计**：DB 抖一下，所有实例同时被判死、同时重启，把一次局部故障放大成全站故障。
- **readiness（就绪）**：失败 → 把这个实例摘出流量，但不重启。这里才应该检查关键依赖（DB 连上了吗、缓存暖了吗、迁移跑完了吗）。

反过来的错误也常见：健康检查只 `return 200`，什么都不查。此时一个连不上数据库的实例会被认为是健康的，流量照进，用户拿到 500，而你的部署系统显示"部署成功，全部健康"。**症状指纹：部署显示成功，错误率却在部署完成后台阶式上升。**

### 8.15 优雅关闭：部署时掉的那些请求

机制链条要背下来：编排系统要换掉一个实例时，先把它从负载均衡摘掉，然后发 `SIGTERM`，等一段宽限期，还没退出就发 `SIGKILL` 强杀。

正确的进程行为是：收到 SIGTERM → 停止接受新请求/停止从队列拉新消息 → 把手上的活干完（或安全地退回队列）→ 关闭连接池 → 退出。

如果 AI 写的服务没有处理 SIGTERM（这是默认情况），效果是：进程收到信号立即死掉，正在处理的请求全部断开，正在处理的队列消息没有 ack 也没有退回。

**症状指纹：错误率的尖刺时间与部署时间精确重合，且只持续几十秒。** 用户看到的是 502/连接重置。因为它自愈，很容易被当成"网络抖动"忽略掉——去查一下部署时间线，几乎每次都对得上。（队列侧的处理见第 07 章。）

### 8.16 回滚：什么能回、什么回不去

**"能回滚"不是一个形容词，是一个你必须能在 30 秒内说清楚的具体动作。** 如果你答不出"回滚的第一条命令是什么"，那就是不能回滚。

按可逆性分四类：

| 东西 | 可逆性 | 注意 |
|---|---|---|
| 无状态服务代码 | 完全可逆 | 前提是制品还在、且不依赖已变的 schema |
| 配置 / feature flag | 可逆且最快 | **回滚代码时要一起考虑，最常见的漏项** |
| 数据库 schema | 部分可逆 | 加列可逆，删列/改类型基本不可逆（见第 06 章） |
| 已发出的副作用 | 不可逆 | 已发的邮件、已扣的款、已推给下游的消息 |

由此得到"向前修复 vs 回滚"的判据：

- **数据还在持续被污染** → 先止血（关 flag / 降级 / 限流），再决定回滚还是修。
- **能干净回滚** → 回滚，永远优先。事故中做的"小修复"错误率极高，而回滚回到的是一个被验证过的状态。
- **回滚会导致数据不兼容**（新代码已经写了新格式的数据，旧代码读不懂）→ 只能向前修复。**这种局面是可以在设计阶段避免的**，方法就是下一节。

### 8.17 迁移与部署的顺序：扩展—迁移—收缩

因为部署期间新旧代码共存，schema 变更必须让**旧代码在新 schema 下仍能工作**。三步法：

```
阶段 1 扩展（expand）：只加不减
   加新列（可空，或带默认值）、加新表、双写
   → 此时旧代码完全不受影响，随时可回滚
阶段 2 迁移（migrate）：回填 + 切读
   后台分批回填历史数据；新代码开始读新列
   → 灰度、观察，仍可回滚（旧列还在）
阶段 3 收缩（contract）：删旧
   确认没有任何代码路径读旧列之后，才删列
   → 这一步之后回滚窗口关闭
```

**三个阶段之间要隔开时间（至少一个部署周期），不能压在一次上线里。** AI 默认会给你"一步到位"的迁移——它会在一个迁移脚本里改名+改类型+删旧列，因为那是最"干净"的写法。这也是它引发生产事故最频繁的单一原因。

对应的提问：**"这次部署的中途，如果一半实例是旧代码一半是新代码，会发生什么？"** 答不上来就别上。

### 8.18 feature flag：把"部署"和"发布"拆成两件事

部署 = 代码到了生产环境；发布 = 用户能用到它。默认这两件事是一件，feature flag 把它们拆开：

- 新功能包在 `if flag_enabled("new_x")` 里，默认关。部署 → 不影响任何人 → 打开给自己 → 打开给 1% → 观察 → 全量。
- 出事时关掉一个 flag 是**秒级**的，而回滚一次部署是**分钟级**的。这是事故中最重要的时间差。

代价必须说清楚：**flag 是技术债，且会指数级复杂化**。三个 flag 就有八种组合状态，而你只测过其中两种。所以纪律是：**每个 flag 创建时就写下删除条件与到期日**，全量后立刻删。仓库里躺着半年前的 flag，是工程成熟度的负分项。

### 8.19 可观测性三件套：三个信号回答三个不同的问题

不是三个可选项，是三种回答不同问题的信号：

| 信号 | 回答什么 | 形态 | 成本特征 |
|---|---|---|---|
| **logs** | "具体发生了什么" | 离散事件，带上下文字段 | 随流量线性增长，最贵 |
| **metrics** | "多少、多快、趋势" | 按时间聚合的数字 | 便宜，但丢失个体细节 |
| **traces** | "时间花在哪一层" | 一次请求跨服务的调用树 | 中等，通常采样 |

诊断时的正确使用顺序：**metrics 告诉你"坏了、什么时候开始坏的、坏在哪个维度"→ traces 告诉你"慢/错在哪一跳"→ logs 告诉你"那一跳的具体参数和报错是什么"**。反过来（一上来就翻日志）是最常见的时间浪费方式，尤其在你还不知道故障范围的时候。

### 8.20 结构化日志与 correlation id

**print 不是日志。** 日志是带结构的事件，至少要有：时间戳、级别、事件名、correlation id、以及若干上下文字段。

```
# 不是日志
print(f"processing order {order_id}")

# 是日志
log.info("order.payment.failed",
         request_id=ctx.request_id,     # 贯穿全链路的那个 id
         order_id=order.id,
         user_id=user.id,
         provider="X",
         error_code=e.code,
         attempt=3,
         latency_ms=812)
```

差别在哪：结构化之后你能做"筛出所有 `error_code=insufficient_funds` 且 `attempt>=3` 的事件，按 provider 分组"这种查询。非结构化的字符串只能靠正则去猜。

**correlation id（request id）是整个可观测性体系的脊椎。** 机制是：入口处生成一个唯一 id（或接受上游传来的），放进请求上下文，之后**每一条日志都带上它，每一次对外调用都把它透传下去**（HTTP header、消息属性）。

它决定了一个关键能力：用户说"我 10 点 15 分下单失败了"，你能不能在五分钟内看到那一次请求经过的每一层？没有 correlation id，你只能按时间窗口翻日志，在有并发的系统里这基本等于大海捞针。

**最常见的断链点**：进入队列的时候。生产者写日志带着 id，消息体里没带，消费者那边重新生成了一个 id——链路就断在这里，而队列后面正是最难查的地方。**要求 AI：所有异步消息的 payload 里必须显式携带 correlation id 字段。**

日志的三条纪律：
- **级别有语义**：ERROR = 需要人看的、系统无法自行处理的；WARN = 降级了但还活着；INFO = 状态变更；DEBUG = 排查用，生产默认关。AI 很爱把普通流程打成 ERROR，后果是 ERROR 这个级别失去意义，你从此不再看它。
- **绝不打整个请求体/响应体**。里面有 token、密码、身份证、健康信息。日志系统的访问权限通常远比数据库宽松——**日志是数据泄露最常见的通道之一**（见第 09 章）。
- **异常要带上下文再上报**。`except Exception: log.error("failed")` 是纯噪音：不知道是什么失败、哪个用户、哪个 id、栈在哪。

### 8.21 指标：类型、百分位与基数

三种基本类型：
- **counter**：只增不减（请求数、错误数）。你真正关心的是它的变化率。
- **gauge**：瞬时值（当前连接数、队列深度、内存占用）。
- **histogram**：分布（延迟）。它让你能算百分位。

**为什么必须看百分位而不是平均值**：1000 个请求，990 个 10ms，10 个 5 秒 —— 平均 60ms，看起来非常健康，但有 1% 的用户在等 5 秒。p50 告诉你典型体验，p95/p99 告诉你**最差的那批人**的体验，而抱怨和流失来自那批人。平均值是延迟这个指标上最会骗人的统计量。

**四个黄金信号**（每一层都问一遍）：延迟、流量、错误率、饱和度。前三个容易，第四个最常被漏——**饱和度是"离撑爆还有多远"的指标**，也是唯一有预测性的那个：

| 层 | 饱和度看什么 |
|---|---|
| 应用进程 | 事件循环延迟 / 线程池排队数 / 内存趋势 |
| 数据库 | 连接池使用率、活跃连接数、锁等待（见第 06 章） |
| 队列 | 队列深度，以及更准的：**最老消息的年龄** |
| 外部 API | 并发使用率、限流剩余额度 |
| 机器 | CPU、内存、磁盘、文件描述符 |

**基数（cardinality）爆炸**：指标的每一组 label 值组合都是一条独立时间序列。把 `user_id`、`request_id`、完整 URL 路径（含 id）当 label，序列数量会随用户数爆炸，直接打爆存储和查询。**规则：label 只能是有限枚举**（路由模板、状态码、region、服务名）。高基数的东西属于 logs 和 traces，不属于 metrics。这条 AI 极其容易违反，因为按 user_id 打点"看起来更有用"。

### 8.22 trace：一次请求的调用树

trace 的模型很简单：一次请求 = 一个 trace，里面是一棵 **span** 树。每个 span 有名字、开始/结束时间、父 span、以及若干属性。跨进程时通过请求头传播 trace id 和 parent span id，下游据此把自己的 span 挂到正确的位置。

trace 回答的问题是 metrics 和 logs 都答不了的：**这 3 秒钟具体花在哪儿了。**

```
[trace 4f2a…]  POST /checkout                        3180ms
  ├─ auth.verify                                       12ms
  ├─ db.query orders                                   18ms
  ├─ http POST payment-provider                      2890ms   ← 在这
  │    └─ (重试 3 次，每次 ~950ms)
  ├─ db.update orders                                  22ms
  └─ queue.publish order.paid                           8ms
```

看到这张图，你的问题就从"结账为什么慢"变成了"支付方一次调用 950ms，且我们重试了三次，超时和重试策略是什么"——这是一个可以直接问 AI 的具体问题（见第 02 章）。

三条实践要点：
- **span 上要挂业务属性**（order_id、user tier、region），否则你只知道慢，不知道对谁慢。
- **异步链路要显式传播**：把 trace context 塞进消息属性，consumer 侧恢复它。否则 trace 在队列处断成两截。
- **采样**：全量存 trace 太贵，通常按比例采样。但**错误和慢请求必须 100% 保留**——采样掉的正是你要查的那些。

（LLM/agent 场景下 span 里要额外记什么、怎么从 trace 读 agent 故障，见第 21 章。）

### 8.23 SLO 与告警：告警于症状，诊断于原因

**SLI** 是一个可测量的用户体验指标（例："结账接口成功且 <1s 的比例"）。**SLO** 是给它定的目标（例：99.5%）。1 减去 SLO 就是**错误预算**——它把"要不要冒险上线"从吵架变成算术：预算还剩很多就大胆发，预算烧光就冻结变更去还债。

告警设计的唯一原则：**告警设在用户能感知的症状上，不设在原因上。**

- 设在原因上（CPU > 80%、内存 > 90%）：CPU 高但用户没事 → 假警报；用户挂了但 CPU 不高（比如全在等锁）→ 漏报。两头都错。
- 设在症状上（错误率 > 2% 持续 5 分钟、p95 延迟翻倍、队列最老消息 > 10 分钟）：报出来的一定是真的有人受影响。

原因类指标不是不要，是**放进面板供诊断，而不是设成告警**。

**告警疲劳是可观测性系统真正的死因**：一个每天响五次的告警，第六次真出事时没人看。判据很硬——**每一条告警都必须对应一个明确的人类动作**。如果收到它的正确反应是"哦"，它就不该是告警。

### 8.24 事故流程：止血 → 定位 → 修复 → 复盘

顺序不能乱，尤其是前两步：**先止血，再找根因。** 事故中最贵的错误是"我先搞清楚为什么"——用户在这段时间里持续受损。止血手段按速度排：关 feature flag（秒）→ 回滚（分钟）→ 降级/限流（分钟）→ 扩容（分钟到十几分钟）。

定位的第一问永远是：**"最近改了什么？"** ——部署、配置、feature flag、上游依赖的变更、流量变化。绝大多数事故的时间起点能对上一次变更。所以**部署与配置变更必须打在同一个时间轴上**，跟指标叠着看。（完整的分层排查流程见第 22 章。）

两个会骗你的信号，必须提前知道：
- **症状层的错误掩盖根因层**：DB 慢 → 应用线程池占满 → 网关超时。你在网关看到的是"网关超时"，最响的告警离根因最远。规律：**沿着依赖链往下走，找第一个"自己就慢/就错"而不是"在等别人"的层。**
- **重试放大**：下游轻微故障 → 上游重试 → 请求量翻几倍 → 下游彻底垮。此时错误率曲线看起来像是上游先出的问题，而且**下游恢复之后仍会被积压的重试打死**（见第 07 章）。

**复盘（postmortem）的唯一有效形式是无责的（blameless）**，而且这在 AI 时代有个新变体：**"AI 写错了"不是根因**，跟"某人手滑了"一样没有信息量。人和 AI 都会犯错，这是常量。根因永远是那个问题：**为什么这个错误能一路走到生产？** 是没有测试覆盖、CI 没有这项检查、还是审查时没人读 diff？

复盘的产出必须是**机制性改动**，一条合格的复盘至少给出：时间线（含"从发生到发现"和"从发现到恢复"两个时长）、根因、为什么没有被提前拦住、以及三条改动——一条防止再发生（测试/检查），一条缩短发现时间（告警/指标），一条缩短恢复时间（回滚/flag/预案）。

### 8.25 工程成熟度评估：你能给一个团队上多激进的 AI 方案

FDE 视角。八个问题，按成熟度递增，答案决定你的方案上限：

1. 代码在版本控制里吗？有没有人直接改生产？
2. 有自动化测试吗？跑一次要多久？
3. 有 CI，且合并前必须绿吗？
4. 有和生产近似的 staging 吗？（"近似"指数据形态和依赖拓扑，不是数据量）
5. 部署是一条命令还是一份手册？
6. **回滚要多久？谁能执行？**（这题信息量最大）
7. 出事时第一个知道的是监控还是客户？
8. 上次事故有复盘吗？产出的改动落地了吗？

映射关系很直接：**回滚要半小时以上、或"出事第一个知道的是客户"的团队，你只能给它上"人工审核后才生效"的 AI 方案**——因为它的系统接不住自动化变更的失败。反过来，一个能十分钟内回滚、有 flag、有面板的团队，你可以让 agent 直接开 PR、自动跑 eval、灰度放量。**同样的 AI 能力，在这两种组织里的安全边界差一个数量级**（见第 23、24 章）。

## AI 在这里最常犯的错，以及怎么识别

| # | 错误 | 怎么识别 / 该问什么 |
|---|---|---|
| 1 | 在 main 上直接大改，不建分支 | `git status` / `git branch`；动手前先问"你打算在哪个分支工作？" |
| 2 | 一次改 30 个文件才提交，混入无关改动 | `git diff --stat` 看文件数；问"这次改动能拆成几个可独立回滚的 commit？" |
| 3 | 总结里只讲新增，不讲删除 | 只读 diff 的删除部分；让它"列出改动中你没在总结里提到的部分" |
| 4 | 改测试让它通过，而不是改实现 | diff 里测试文件与实现文件同时改动 = 红旗；问"这个断言之前是什么？为什么要改？" |
| 5 | 写出 mock 掉核心逻辑的假测试 | "把实现换成空函数，这个测试还绿吗？" |
| 6 | 测试与实现同义反复 | 断言右边是表达式而不是手算字面量 |
| 7 | 只测 happy path | 数测试名里"失败/超时/为空/重复"的比例 |
| 8 | 声称"测试全过"但没跑或只跑了一部分 | 要原始输出：跑了几个用例、耗时多少、命令是什么 |
| 9 | 无脑更新快照文件当作修复 | diff 里 `.snap`/`expected.json` 大段变化而实现改动很小 |
| 10 | 遇到红灯就 `skip` / 加 `try` 吞掉 / 放宽断言 | 搜 diff 里新增的 `skip`、`xfail`、`eslint-disable`、`# type: ignore`、空 catch |
| 11 | 为了 CI 绿而禁用 lint 规则或改 CI 配置 | **规则/配置文件出现在功能 PR 的 diff 里，永远是红旗** |
| 12 | 反复重跑 flaky test 直到绿 | 同一 CI 连续多次重跑；问"这个测试为什么不稳定？根因是时钟、共享状态、并发还是外部依赖？" |
| 13 | 把 `.env` / 密钥提交进 git 或写成代码默认值 | 搜 `getenv(..., "…")` 的第二个参数；扫历史；发现即轮换 |
| 14 | 构建不可复现：`latest` 基础镜像、无 lockfile | 问"这个构建三个月后重跑，还是同一个东西吗？" |
| 15 | 缺失配置有默认值兜底，掩盖了配置错误 | 问"必需的环境变量缺失时，服务是启动失败还是静默用默认值？" |
| 16 | 没有 SIGTERM 处理，部署时掉请求/丢消息 | 搜信号处理；症状是错误尖刺与部署时间精确重合，持续几十秒 |
| 17 | 健康检查只 `return 200`，或在 liveness 里查 DB | 前者症状：部署"成功"但错误率台阶上升；后者症状：DB 抖动时全部实例同时重启 |
| 18 | 迁移一步到位（改名+改类型+删列），没有扩展-收缩 | 问"部署中途一半旧代码一半新代码时会发生什么？"和"这次迁移能回滚吗？" |
| 19 | 迁移与部署顺序错：新代码先上但 schema 未变 | 问"这两步的先后顺序是什么？中间那几分钟谁在读写？" |
| 20 | 没有回滚方案，或回滚代码忘了回滚配置/flag | 要求一句话说清"回滚的第一条命令"；问"配置和 flag 要不要一起回？" |
| 21 | 用 print 当日志，没有级别、没有 request id | 搜 `print(` / `console.log(`；问"用户报一个失败请求，我怎么找到它经过的每一层？" |
| 22 | 日志里打印完整请求体/响应体（含 token、PII） | 搜 `log(...body)`、`json.dumps(request)`；问"这条日志里有 secret 或个人信息吗？" |
| 23 | 把普通流程打成 ERROR，或异常只 log 不带上下文 | 看 ERROR 的日均条数；搜 `except Exception: log.error("failed")` 这类无字段日志 |
| 24 | 指标 label 用了 user_id / request_id / 含 id 的路径 | 问"这个 label 有多少种取值？"；序列数会随用户数增长的就是错的 |
| 25 | 异步任务不传播 correlation id / trace context | 看消息 payload 里有没有 id 字段；症状是链路在队列处断成两截 |
| 26 | 告警设在 CPU/内存等原因指标上 | 问"这条告警响的时候，一定有用户受影响吗？收到它我该做什么？" |
| 27 | 交付时给结论不给证据 | 固定要求：diff、测试原始输出、CI 状态、上线后看哪三个指标 |
| 28 | 复盘写成"AI 弄错了" | 追问"为什么这个错误能走到生产？哪一道关卡本该拦住它？" |

## 判断清单

可以直接抄进 CLAUDE.md 或 PR 审查模板。

**git 与变更**
- 这个改动在哪个分支？工作区动手前是干净的吗？
- `git diff --stat` 里的文件，有几个是我预期之外的？每一个的解释是什么？
- diff 里有没有：测试断言被放宽/删除、lint 或 CI 配置被改、依赖被加、空 catch 被加？
- 这次改动能拆成几个可独立回滚的 commit？
- 有没有 secret 进了 git 或写成了代码默认值？

**测试**
- 测的是行为还是 mock？把实现换成空函数，测试会红吗？
- 断言的右边是手算的字面量，还是重新实现了一遍逻辑？
- 覆盖了失败路径吗（超时、重复、为空、越权、依赖挂掉）？
- AI 这次改过测试文件吗？改了哪几行、为什么？
- 有 flaky 吗？如果有，根因属于时钟/共享状态/并发/外部依赖中的哪一类？

**CI 与制品**
- CI 真的跑了吗？我看到原始输出了吗？
- 哪些检查是硬阻断的？合并是服务端强制还是靠自觉？
- 构建可复现吗（lockfile、固定基础镜像）？三个月后重跑是同一个东西吗？
- staging 上跑的和 prod 上要跑的，是同一个制品吗？

**部署与回滚**
- 必需配置缺失时，服务是启动失败还是静默降级？
- 收到 SIGTERM 之后会发生什么？手上的请求和消息怎么办？
- liveness 和 readiness 各检查了什么？liveness 里有没有查外部依赖？
- 部署中途新旧代码共存时，兼容吗？迁移做了扩展-收缩吗？
- **回滚的第一条命令是什么？要多久？配置和 flag 要一起回吗？**
- 哪些副作用是回不去的（已发的邮件、已扣的款、已推给下游的消息）？

**可观测性**
- 用户报一个 10:15 的失败请求，我能在五分钟内看到它经过的每一层吗？
- correlation id 在哪里断的？队列/异步任务里带了吗？
- 每一层的饱和度指标是什么？现在能看到吗？
- 告警设在症状上还是原因上？每条告警对应什么人类动作？
- 日志里有 secret 或 PII 吗？ERROR 级别一天多少条、我还看吗？
- 上线后看哪三个指标能判断它是健康的？异常时的阈值是多少？

## 飞机上的练习

**练习 A｜五种"我修好了"的谎言。** AI 说："bug 修好了，所有测试都通过。"在纸上列出至少五种它可能（无意地）说了假话的方式，以及每一种对应的一个核查动作。

*参考答案要点*：(1) **它改了测试而不是实现**——核查：diff 里测试文件有没有改动，断言变了没有；(2) **它只跑了子集**（跑了 `pytest tests/unit/` 而不是全量），或跑了但没等集成测试——核查：要命令原文和用例数；(3) **它根本没跑，只是推理出"应该能过"**——核查：要原始输出，看有没有耗时和用例统计；(4) **测试是假的**（mock 掉了核心，或断言太弱）——核查：把实现替换成空函数的思想实验；(5) **本地过 CI 不过**（环境差异，见 8.12）——核查：看 CI 状态而不是本地；(6) **修的是症状不是根因**（加了 try/except 把异常吞掉，错误消失了）——核查：搜 diff 里新增的 catch；(7) **它修好了这个但弄坏了别的**，而那部分没有测试覆盖——核查：改动半径与测试覆盖的交集。能写出五条以上且每条都有可执行的核查动作，算过。

**练习 B｜读三段 diff，找出被绕过的地方。** 判断下面三段改动各有什么问题：

```
[diff 1]
- def test_refund_exceeds_order_raises():
-     with pytest.raises(RefundExceedsOrder):
-         refund(order, amount=150)
+ def test_refund_exceeds_order_raises():
+     result = refund(order, amount=150)
+     assert result is not None
```

```
[diff 2]
  # .github/workflows/ci.yml
- - run: pytest tests/
+ - run: pytest tests/ || true
  # src/payment.py
+ # TODO: 这里偶发失败，先跳过
+ @pytest.mark.skip
```

```
[diff 3]
  # migrations/007_rename.sql
+ ALTER TABLE orders RENAME COLUMN amount TO amount_cents;
+ UPDATE orders SET amount_cents = amount_cents * 100;
  # src/order.py
- total = order.amount
+ total = order.amount_cents
```

*参考答案*：**diff 1**——把"必须抛异常"这个规格改成了"返回任何非空值即可"，等于删除了这条业务规则；正确做法是修实现让它抛异常。这是"改测试让它绿"的标准形态。**diff 2**——两处：`|| true` 让测试步骤永远成功，CI 从此变成装饰；`skip` 掩盖了 flaky 的根因且没有到期日。两处都属于"为了绿而拆掉刹车"，是本章最严重的一类。**diff 3**——三个问题：一步完成改名，部署期间旧代码读 `amount` 会直接报错（缺少扩展-收缩）；`UPDATE` 全表无分批，大表上会长时间持锁（见第 06 章）；这个迁移不可回滚，且如果重跑一次会再乘 100（迁移必须幂等）。

**练习 C｜设计最小 CI 流水线。** 为你自己的一个项目写出流水线：每个阶段做什么、预期耗时、哪些硬阻断哪些只警告、总时长预算、以及"哪些检查放在 PR、哪些放在合并后"。

*评判标准*：(1) 快且易失败的在前；(2) 阻断分级明确，不是全硬也不是全软；(3) 有 secret 扫描；(4) PR 阶段总时长控制在十分钟内，慢的（全量端到端、性能）放合并后；(5) 说清楚了"绿灯代表什么被证明了、什么没被证明"。

**练习 D｜五组面板，判断根因层。** 每组写出你的判断和下一步要看什么：

1. 网关 5xx 从 0.1% 涨到 8%；应用错误率不变；DB CPU 平稳；应用 p99 从 200ms 涨到 30s。
2. 错误率有一个持续 40 秒的尖刺，然后自愈；每天出现两三次，时间不固定。
3. 队列深度平稳，但"最老消息年龄"持续单调上升到 2 小时；worker CPU 只有 10%。
4. 部署完成后错误率呈台阶式上升，且不回落；实例全部显示健康。
5. p50 延迟不变，p99 从 300ms 涨到 4s；DB 慢查询日志无新增；外部 API 调用量翻倍。

*参考答案*：**1** 应用在等某个下游（错误率不变说明它没报错，只是卡住），30s 是典型超时值；看应用的饱和度——线程池/事件循环排队、DB 连接池使用率、外部调用的 trace。**2** 强烈提示是部署或实例重启导致的连接中断（40 秒 ≈ 一次滚动批次 + 缺少优雅关闭）；把部署/重启时间轴和错误尖刺叠起来看，对上就是 8.15。**3** 消费者卡住而不是不够快（CPU 低说明没在干活）——看 worker 是不是全阻塞在某个外部调用/锁上，或者是一条毒消息在无限重试占着位置。**4** 部署引入的问题，且健康检查没检查真实依赖（8.14）——先看新版本的 readiness 检查了什么，同时立刻回滚。**5** p50 不动 p99 涨 = 只有一部分请求受影响，配合外部 API 调用量翻倍，高度怀疑重试放大：某个下游开始偶发失败，代码在重试，每次重试叠加超时。看 trace 里那条链路的重试次数。

**练习 E｜写一份事故复盘。** 场景：周五下午上线，一小时后客服转来用户投诉"付款成功但订单还是待支付"，你才发现问题；排查 40 分钟，发现是新代码写了新字段但异步 worker 还是旧版本、读不到；回滚 worker 后恢复；期间约 300 单需要人工修复。

*评判标准*：必须包含 (1) 时间线，且分别标出"发生→发现"（60 分钟）和"发现→恢复"（40+ 分钟）两个时长；(2) 根因写成机制而不是人/AI 的错——真正的根因是**部署顺序与新旧共存兼容性没有被设计**，"AI 写的迁移有问题"不是根因；(3) 回答"为什么没提前发现"——没有针对"支付成功但订单未更新"这个状态不一致的监控；(4) 三条机制改进各对应一个维度：防再发（集成测试覆盖新旧版本共存 / 强制扩展-收缩流程）、缩短发现（加一条"状态不一致数量 > 0"的症状告警）、缩短恢复（worker 和主服务的部署与回滚绑定，或用 flag 控制新字段读写）。如果你写的三条里有两条是"以后要更仔细"，这份复盘不合格。

## 落地后的练习

1. **考古：审自己的一天。** 挑一天你和 AI 大量协作的记录，用 `git log --stat` 和 `git diff` 逐个 commit 过一遍，把"它做了但没告诉我"的改动列出来。这个清单的长度会让你重新校准对它总结的信任度——保留它，下次审查时按这个清单优先扫。
2. **变异测试：亲手弄坏。** 挑一个 AI 说"测试覆盖很好"的模块，手动改坏五处实现（`>` 改 `>=`、`and` 改 `or`、删一个 `return`、把一个参数写死、把错误吞掉），每次跑一遍测试。有几处没被抓到，那部分逻辑就是裸奔的。补上测试，再重来一次。
3. **test-first 对照实验。** 同一个小功能做两遍：一遍直接让 AI 实现，一遍你先写三个测试（含至少一个失败路径）、确认红了、再让它实现。对比两份产出的边界行为差异，把结论写进你的 CLAUDE.md。
4. **让 CI 拦住 AI。** 给一个项目配上 CI（lint + type + test + secret 扫描 + 服务端合并门禁），然后让 AI 提交一个你知道有问题的改动（比如放宽一个断言），看它能不能通过。**如果通过了，你的门禁是假的**——修到能拦住为止。
5. **完整走一遍事故循环。** 本地 docker compose 起一套服务：部署 v1 → 制造流量 → 部署一个有 bug 的 v2 → 从指标发现 → 回滚 → 记录"从部署到发现"和"从发现到恢复"的秒数。然后加上 feature flag，再走一遍，对比第二个时长。
6. **打通一条链路。** 给一个"HTTP 入口 → 队列 → worker → DB"的服务加结构化日志 + correlation id + trace，要求：从入口的一条日志能查到 worker 里的所有相关日志。然后故意注入一个只在 worker 里发生的错误，练习用 id 从头追到尾，计时。
7. **注入故障看信号。** 分别制造：慢 DB（加人为延迟）、队列积压（停掉 worker）、依赖超时（把外部调用指到黑洞地址）。每次观察四个黄金信号怎么变，把"症状 → 层"的映射写成你自己的一页速查表（配合第 22 章）。
8. **扩展-收缩实操。** 给一个表改字段名，严格分三次部署完成，中间保持服务可用；每一步之后都尝试回滚一次，确认真的能回。

## 一句话记忆钩子

**小步、可逆、有证据：改动在分支上，规格在测试里，验证在 CI 里，回滚在一条命令里，真相在 diff、trace 和指标里——不在它的总结里。**
