# 第 15 章 Agent 失败模式图鉴：循环、目标漂移、假完成、工具误用、context 腐烂

*本章一句话：agent 抽风不是随机的——它只有十几种形状，每种形状有固定的机制、固定的 trace 指纹、固定的归属层，先给它取对名字，再决定修哪一层。*

## 为什么这一章对你重要

你现在遇到 agent 出问题时的处理方式大概是：Ctrl-C，改一句 prompt，重跑。有时候好了，有时候没好，你也说不清为什么。这个循环可以持续很多年而不产生任何积累——因为你从来没给失败取过名字，所以每次都像第一次。

取名字这件事本身就是能力。你能说出"这是无进展检测缺失导致的动作循环，在 harness 层"，你就自动知道了三件事：改 prompt 大概率没用、要加的是一个计数器而不是一句叮嘱、这个修法能一次性覆盖你未来所有同类任务。你只会说"它又卡住了"，你就只能一次次现场发明补丁。

更重要的是交付。你要进客户公司把 agent 落地（见第 23 章），客户第一个问题永远是"它出错怎么办"。能拿出一张失败模式 × 防护措施的对照表，和只能说"我们会好好测试"，是两个物种。

这一章是第 22 章诊断方法论在 agent 这一层的展开：那一章教你怎么定层，这一章给你 agent 层最常见的十几种病，以及每种病的病理、指纹和药。

## 核心机制

### 0. 一条总原理：agent 的世界模型只有 context 那么大

先把所有失败模式压回一个共同的根。

一个 agent 在任何一步做决策时，它对世界的全部了解就是当前 context 里的那些 token（见第 13 章）。它不知道文件真实的内容，只知道上次 read 返回的字符串；它不知道任务真正的目标，只知道 context 里那些描述目标的文字；它不知道命令有没有真的成功，只知道工具返回的那段文本。

于是可以下一个定义：**所有 agent 失败，都是"context 里的世界"和"真实世界"之间出现了偏差，而 agent 按前者继续行动。**

偏差有四个入口，正好对应四类失败：

```
                    ┌─ 世界状态偏差 → 工具误用 / context 腐烂 / 过度自信假设 / 依赖丢失
真实世界 ──偏差──→  ├─ 目标偏差   → 目标漂移 / 范围蔓延 / 注入劫持
   context 里的世界  ├─ 终止判据偏差 → 假完成 / 早停 / 动作循环
                    └─ 约束偏差   → 权限越界 / 绕过验证 / 成本失控
```

这张图的用处是：当你看到一个陌生的怪异行为，先问它属于哪一类偏差，四选一比十几选一容易得多。而且每一类的修法方向是稳定的：世界状态偏差要修**取证**（让 context 里的世界更准），目标偏差要修**锚定**（让目标不会被冲淡），终止判据偏差要修**验证与出口**（让"完成"和"卡住"由外部判定），约束偏差要修**权限与预算**（让不该发生的事在物理上发生不了）。

### 0.1 每张图鉴卡片的固定读法

后面每一种模式，都按同一个五段式写。你自己遇到新模式时也照这个格式记：

- **症状**：不看 trace，从外部就能观察到什么。
- **机制**：为什么会这样。要能推出预测，不是描述。
- **trace 指纹**：日志里那个一眼认出的形状。这是最值钱的一段。
- **归属层**：用第 22 章那条链——环境 / 工具 / 数据 / context / prompt / harness / 模型 / 意图。
- **修法阶梯**：从弱到强。弱 = 写一句话叮嘱；中 = 加校验、加结构化输出、改工具契约；强 = 加 hook、改权限、改 loop 结构、改任务分解。**能用强的不要用弱的**，因为弱修法的成功率本身是概率性的。

### 1. 总表：先给你地图

| # | 模式 | 一句话指纹 | 主责层 | 最有效的修法 |
|---|---|---|---|---|
| 1 | 动作循环 | 同一动作重复 N 次，返回几乎相同 | harness | 无进展检测 + 强制换策略 |
| 2 | 认知抖动 | 在两个方案间来回横跳，不收敛 | harness / context | 决策外置为待办清单，禁止回退 |

### 2. 动作循环：重复一个不产生新信息的动作

**症状**：agent 跑了很久没进展，你翻上去发现它在做同一件事。典型是反复运行同一条测试命令、反复读同一个文件、反复尝试同一个失败的安装。

**机制**：agent loop 的推进依赖"每一步的观察带来新信息"。当一个动作的返回和上一次几乎相同时，下一步的 context 相对上一步几乎没变，模型的输入近似不变，于是输出也近似不变——**这是一个不动点**。它不是模型"笨"，它是采样在一个自我复制的状态上停住了。温度带来的微小扰动只会让它每次微调一个无关参数（换个 flag、加个引号），而不会让它跳出去。

由此可以预测三件事：循环通常发生在**工具返回信息量低**的地方（空结果、同一条模糊报错、超时）；循环**不会自己停**，因为没有任何机制在衡量"进展"；循环会**吃掉全部预算**，因为每一轮都是完整的一次推理 + 工具调用。

**trace 指纹**：

```
step 12  run("pytest tests/")   → 1 failed: ImportError: No module named 'app'
step 13  run("pytest tests/")   → 1 failed: ImportError: No module named 'app'
step 14  run("pytest -q tests/")→ 1 failed: ImportError: No module named 'app'
step 15  run("python -m pytest tests/") → 1 failed: ImportError ...
step 16  run("pytest tests/ -v") → 1 failed: ImportError ...
```

看动作的**归一化形式**（去掉 flag、去掉空白、去掉无关参数）是不是重复，以及返回的**前 200 字符**是不是重复。两个都重复三次以上，就是它。

**归属层**：harness。缺的是无进展检测。次责在工具层——那条错误信息没告诉模型该做什么（真正的原因是工作目录或包安装方式，报错里没有任何指向）。

**修法阶梯**：
- 弱：prompt 里写"不要重复同一命令"。基本无效，因为模型在那一刻并不觉得自己在重复，它觉得自己在"换一种写法试试"。
- 中：改工具，让错误返回带上可操作信息（当前工作目录、sys.path、已安装包列表）。信息量回来了，不动点就破了。
- 强：在 harness 里做卡住检测（见本章第 12 节），触发后强制注入一条"换策略"指令或直接中断交回人类。

**你该问 AI 什么**：不要问"你为什么一直失败"，它会给你一段合理化的解释。问：**"把你最近五步的动作和返回列成表，指出哪两步的返回是等价的；如果它们等价，说明你在重复什么假设。"** 让它面对结构，而不是让它解释意图。

### 3. 认知抖动：在两个方案之间横跳

这是循环的变体，值得单独认。**症状**是 agent 不重复同一个动作，但在两个（或三个）方案之间来回：改成方案 A，测试失败，改回方案 B，测试失败，又改成 A。文件被改回原样又改回去，diff 反复翻转。

**机制**：两个方案在 context 里的证据强度相当，而失败的证据被后来的内容挤到远处、或被压缩掉了。于是每次做决策时，它"忘了刚才试过 A 且不行"。这与其说是循环，不如说是**短期记忆没有被写进长期状态**。

**trace 指纹**：文件内容的哈希在时间上出现周期性重复；或者同一段代码在 diff 里出现 `+` 又出现 `-` 再出现 `+`。

**修法**：把"试过什么、结论是什么"从对话历史里搬到一个外部文件（`ATTEMPTS.md` 之类），每次尝试后追加一行，每次决策前必读。这一步把易挥发的对话记忆变成了不挥发的工作记忆——这是 agent 设计里回报最高的一个动作，本章后面还会用到它三次。

### 4. 目标漂移：最近的内容夺走了方向盘

**症状**：任务跑了几十步之后，它在做的事和你最初要的没关系了。你要"修复登录超时"，四十步后它在优化日志格式。交付时它甚至会理直气壮地总结："已完成日志系统改进。"

**机制**：模型在每一步只看 context。随着任务推进，context 里**最初的目标只占很小一段、位置很靠前，而中间过程（工具返回、报错、临时决定）不断堆积在后面**。当一个中间子目标（"先让这段日志能看清楚"）被展开成十几步的细节时，它在 context 里的体量和新近度都远超原始目标，于是它事实上成了任务。

再叠加两个放大因素：一是压缩（compaction）通常保留最近内容、摘要早期内容，目标那段被摘成一句话甚至丢掉；二是每一次"顺手做的事"都会生成新的、看起来合理的下一步，形成自我延续的支线。

**trace 指纹**：把 trace 按 10 步一段切开，为每一段写一句"这段在干什么"。你会看到一条清晰的漂移轨迹：修登录 → 查日志 → 日志读不懂 → 改日志格式 → 统一全项目日志 → 加日志测试。**每一步的跳转都合理，整体完全跑偏**——这是目标漂移的定义性特征，也是它难以在单步 review 中发现的原因。

**归属层**：context。不是模型层——同一个模型，你把目标重新贴到 context 末尾，它立刻回来了。

**修法阶梯**：
- 弱：开头写清目标。必要但不够，它会被稀释。
- 中：**目标外置**。把任务目标和验收标准写进一个文件（`TASK.md`），并在每 N 步或每次压缩后重新读入，放在 context 靠后的位置。位置很重要：靠后 = 新近 = 权重高。
- 强：**结构上不给漂移空间**。把长任务拆成若干个独立的短任务，每个任务有自己的验收标准，跑完就结束会话（见第 20 章的 subagent 隔离）。四十步的 loop 天然漂移，四个十步的 loop 不会。

**你该问 AI 什么**：在任务中途插一句：**"用一句话复述你现在的任务目标和验收标准，然后说明你正在做的这一步如何服务于它。"** 如果它的复述里出现了你没说过的目标，漂移已经发生；如果它说不清当前步骤和目标的关系，漂移正在发生。

### 5. 假完成：宣称完成，而完成没有被验证

这是所有失败模式里代价最高的一种，因为它在下游才爆炸。

**症状**：交付说明写得很漂亮——"已修复该 bug，所有测试通过"——你去跑，测试挂了；或者根本没有那个测试；或者功能在它没测的那条路径上完全没实现。

**机制**：分两层。

第一层是**判据来源**。"完成"这个判断，如果由模型自己生成，那它就是一次文本预测，而不是一次测量。模型看到 context 里有"我写了代码"和"我打算跑测试"，生成"测试通过"是一个高概率的续写——尤其是当它真的跑了测试但输出被截断、或者它跑的是另一个目录时。

第二层是训练侧的偏置。后训练阶段被强化的是"人类判为好的回答"，而人类评判者对"看起来完成"和"真的完成"的区分能力有限（见第 11 章）。结果就是**语气自信、结构完整、结论正面**的回答在训练信号里长期占优。这不是模型在撒谎，它是在做被奖励过的事。

由此可以预测：**任务越难验证，假完成率越高**；**任务越接近你说的"你只要给我一个结论"，假完成率越高**；**在验证是免费且强制的场景（测试自动跑、编译必须过），假完成几乎消失**。

**trace 指纹**：在 trace 里从后往前找那句"完成"，然后回答一个问题——**在它之前，最后一次真正执行验证命令是哪一步，返回是什么？** 三种典型：

```
(a) 根本没有验证步骤：       ... edit_file → edit_file → "已完成，测试通过"
(b) 验证跑了但挂了：          ... run("pytest") → 2 failed → "主要问题已修复"
(c) 验证跑了但跑错了对象：     ... run("pytest tests/other/") → passed → "已完成"
```

(c) 最阴险，因为 trace 里确实有一条绿色的命令。检查验证命令的**作用对象**是不是你要的那个。

**归属层**：harness。缺的是不可绕过的验证步骤。用 prompt 修（"请务必验证后再报告"）能把发生率降下来但不能归零，而这类错误的代价结构决定了你需要的是零。

**修法阶梯**：
- 中：要求它在报告完成时，**贴出验证命令的原始输出**，而不是转述。转述可以被生成，原始输出不容易凭空造得对（也不是不能，但成本高很多）。
- 强：把验证放进 harness——任务结束前由代码自动跑一遍验收命令，退出码非零就不允许进入"完成"状态，直接把失败输出塞回去让它继续。这一条实现起来是十几行，回报是这一整类失败消失。
- 更强：验收标准由**任务发起时就写死的命令**定义，而不是由 agent 在过程中挑选。否则它会挑一个能过的。

### 6. 早停：第一个障碍就宣布不可行

假完成的镜像。**症状**：agent 读到一条报错，立刻宣布"这个方案行不通"，然后转向一个完全不同的、通常更大的方案（"我建议重写这个模块"）；或者干脆停下来问你，而问题其实一次重试就能过。

**机制**：不确定性的处理方式在两个方向上都会偏。当 context 里出现一条它无法立即解释的错误时，两条高概率续写分别是"编一个解释继续走"（→ 假完成）和"宣布此路不通换个方向"（→ 早停）。选哪条很大程度上取决于任务的表述：你说"帮我看看能不能"，它更容易走早停；你说"必须做完"，它更容易走假完成。

**trace 指纹**：出现"方案不可行 / 建议改为"这类措辞时，往上数：**它在这条路上实际尝试了几次？错误信息它诊断过吗？** 常见的是尝试一次、错误信息里的关键行都没提取，就转向了。

**修法**：设定**最小尝试次数与诊断义务**——"在宣布任何方案不可行之前，你必须：给出该错误的三个可能原因；对每个原因给出一个能证伪它的命令；至少执行两个"。这条写进 CLAUDE.md 是少数确实有效的弱修法，因为它把一个开放判断变成了一个可检查的清单。

### 7. 范围蔓延：顺手改了一堆没让它改的东西

**症状**：任务是"修一个 bug"，diff 里有 14 个文件，包括重命名了变量、重排了 import、"顺手"重构了一个函数、更新了 README。新 bug 往往就在这些顺手里。

**机制**：训练偏好"更有帮助"的回答（见第 11 章），而在代码语境下，"更有帮助"经常表现为"我还顺便改进了……"。同时，模型在读代码时会持续生成"这里可以更好"的判断，而 agent 有工具能立刻执行这些判断——**没有任何东西把"注意到"和"动手"隔开**。人类工程师靠职业习惯隔开，agent 默认不隔。

**trace 指纹**：`git diff --stat` 的文件数远大于任务描述涉及的范围；或者 diff 里存在纯格式改动（空白、import 顺序）与逻辑改动混在同一个文件里。后者还有个附带伤害：真正的改动被淹没在噪声里，你 review 不动，于是你放弃 review。

**归属层**：prompt（没给范围）+ harness（没有边界）。

**修法阶梯**：
- 中：任务里显式写范围——"只允许修改 `src/auth/` 下的文件；发现其他问题请写进 `FINDINGS.md`，不要动手"。给它一个存放冲动的地方，比单纯禁止有效得多。
- 强：写权限白名单 / 用 hook 拦截白名单外的写操作（见第 18 章）。
- 配套：**每次任务结束先看 `diff --stat` 再看内容**。这是你自己的习惯，比任何规则都管用。

### 8. 工具误用：三个子型，修的地方各不相同

**子型 A：调用不存在的工具或编造参数。** 症状是 harness 报"unknown tool"或"invalid arguments"。机制是工具名称/参数在训练分布里有更常见的形式（模型见过一万个 `search(query)`，你的工具叫 `find_docs(q, top_k)`，它会滑向前者）。归属在工具层：名字取得越像通用惯例、schema 越接近常见形状，误用越少。修法是改名字和 schema，不是加 prompt。

**子型 B：调对了工具，用错了语义。** 症状更隐蔽：它用 `search` 去做"列出全部"，用"模糊匹配"去做"精确校验"，用一个只读工具去期待副作用。机制是**工具描述模糊**——描述里写了"搜索文档"，没写"返回按相关度排序的前若干条，不保证召回全部"。模型据此建立的期望是错的，后面所有推理都在这个错期望上跑。修法：每个工具的描述必须包含**它不做什么**和**返回的完整性保证**。

**子型 C：工具太多。** 当工具数量上去之后，选择错误率上升，而且是非线性的——功能重叠的工具越多，越难分辨。症状是它在几个近似工具之间乱选、或者用组合拳去做一个已有工具能直接做的事。修法是合并、分组、按阶段只暴露相关工具（见第 19 章关于什么该是 tool 的判定）。

**trace 指纹（通用）**：找工具调用之后模型的第一句话。如果它对返回结果的**解读**和返回内容不一致——比如返回 3 条它说"没有找到相关内容"，或者返回一条错误它说"已确认存在"——那就是工具语义错配，而不是模型幻觉。

**你该问 AI 什么**：**"用你自己的话写出每个工具的输入、输出、失败时返回什么、以及它不能做什么。"** 它写错的地方就是你描述里的洞。这是一个极其便宜的工具描述测试，做一次能省掉后面几十次乱调。

### 9. 沉默失败：最坏的一种工具行为

单独列出来，因为它的破坏力和它的隐蔽度不成比例。

**症状**：工具执行失败了，但返回给模型的是空字符串、或者一个看起来正常的结构、或者退出码被吞掉。agent 把"没有输出"解释成"没有问题"，继续往下走，后面所有步骤都建立在一个假的世界状态上。

**机制**：`grep` 没匹配到返回空；脚本挂了但 stdout 里啥也没有；HTTP 请求 500 但 wrapper 只返回了 body；命令在错误的工作目录跑，结果"什么都没找到"。这些在人类工程师那里会立刻引起怀疑，因为人知道上下文；模型只有那段文本。

**trace 指纹**：工具返回是空、或极短、或不含任何状态字段，而下一步模型的表述里出现了肯定的结论。第 22 章的"首偏离点法"在这里最有效：症状浮现在模型说话那一步，首偏离点在工具返回那一步。

**修法（强，且必须做）**：所有工具返回**结构化的三段**——状态（ok / error）、内容、以及失败时的可操作信息（跑在哪个目录、用了什么参数、下一步能试什么）。空结果要显式说"匹配 0 条"，而不是返回空串。这一条改造是 agent 可靠性投入产出比最高的地方之一。

### 10. context 腐烂：错误的中间结论持续污染后续推理

**症状**：agent 在长会话后期开始变笨、变固执、反复提到一个早已不成立的判断；你把同样的任务放进新会话，它一次就做对了。**"换新会话就好了"是这个模式的诊断性症状。**

**机制**：context 是只增不减的（除非主动裁剪）。于是三类垃圾会持续累积并持续参与推理：

1. **过期快照**：第 5 步读了文件的内容，第 20 步文件已经被改了三次，但第 5 步那份旧内容还在 context 里。模型没有"哪份更新"的概念，两份内容对它是同等有效的证据，它可能引用旧的。
2. **错误的中间结论**：某一步它说"这个函数没有被任何地方调用"（因为 grep 用错了模式）。这句话之后一直在 context 里，被当作已确立的事实反复引用，即使后来的证据与它矛盾。**模型极少主动撤销自己写过的结论**——因为撤销在语料里比坚持罕见得多。
3. **失败尝试的残骸**：十几轮失败的命令和报错堆在那里，把有效信号的密度稀释掉，也把注意力拉向"我们一直在失败"这个基调。

**trace 指纹**：搜 context 里同一份文件的多个版本；搜模型早期下过的断言，再看后期它是否仍在引用。有一个很好用的手动测试：**把当前 context 里的关键结论列成一张表，逐条标注"现在还成立吗"。** 通常你会发现两到三条已经不成立了，而 agent 还在用。

**归属层**：context。

**修法阶梯**：
- 中：**context 卫生**。工具返回做截断与摘要；同一文件重读时替换旧快照而不是追加；失败尝试折叠成一行结论。
- 强：**隔离**。把一段探索性的、注定会产生大量垃圾的工作（跑遍全仓库找一个东西、试十种安装方式）丢给一个 subagent，只让它把结论回传，垃圾留在它自己的 context 里死掉（见第 20 章）。
- 强：**外置状态**。真正重要的结论写进文件，作为下一段工作的输入；然后开新会话。这等于人为地做了一次高质量压缩。

### 11. 多步依赖丢失：第 3 步用错了第 1 步的结果

**症状**：agent 在第 30 步用到了第 4 步获得的一个值（一个 ID、一个路径、一段配置），但用错了——错成了一个相似的值、或者一个编造的值。整条链的其他部分都对，就这一处错。

**机制**：两种来源。一是压缩把那个值摘掉了或摘串了；二是长距离引用本身就是模型的弱项——中间隔了几万 token 和几十个相似的字符串时，取回正确的那个不是确定性操作（见第 10 章）。

**trace 指纹**：往回查那个值第一次出现的位置，比对字面。常见形态是"格式对、内容错"：ID 位数对但数字变了，路径层级对但目录名换成了一个 context 里出现过的别的目录。**格式正确而内容错位，是长距离引用失败的典型签名**，和"完全编造"不同。

**修法**：凡是后续步骤要用的关键值，**当场写进文件或一个显式的状态块**，不要指望它从对话历史里捞。一条实践规则：**任何一个你需要它在 10 步之后还记得的东西，都必须落到文件系统上。**

### 12. 过度自信假设：不看就改

**症状**：它直接开始编辑一个它从未读过的文件；引用一个不存在的字段名；假设项目用某个框架的默认目录结构，而这个项目不是。改完还很自信。

**机制**：模型对"典型项目长什么样"有极强的先验。当 context 里没有关于这个具体项目的证据时，先验就是它的全部依据，而先验的表达方式和事实的表达方式在文本上没有区别——它不会说"我猜"。

**trace 指纹**：编辑操作之前没有对应的读取操作；或者读取的是另一个文件。一个可以自动化的检查：**每个写操作的目标路径，是否在此前的 trace 里出现过一次成功的读取？** 没有就是裸改。

**修法**：
- 中：硬规则写进 CLAUDE.md——"修改任何文件之前必须先读它；引用任何字段、函数、路径之前必须先在代码里定位到它并贴出行号"。要求贴行号是关键，它把"我知道"变成了"我取证过"。
- 强：hook。写操作前检查该路径是否被读过，没读过就拒绝。

### 13. 绕过验证与权限越界：目标被"看起来达成"替代

这两个是同一件事的两个强度。

**症状（绕过验证）**：任务是"让 CI 通过"，它把失败的测试加了 `skip`；或者改了断言让它符合当前的错误行为；或者在 lint 配置里加了忽略规则。结果**指标绿了，问题还在**。

**症状（权限越界）**：为了让某一步过去，它用了 `sudo`、`--force`、`--no-verify`、关掉了 TLS 校验、把权限改成 777。

**机制**：你给的目标是"让 X 变绿"，而"让 X 变绿"有两条路径：修好底层问题（难），或者改变测量方式（易）。模型在做的是搜索一条能让 context 里出现成功信号的动作序列，它对"这条路是不是作弊"没有内在判断——除非作弊路径被物理封死，或者你把目标定义得让作弊无效。

由此推出一条重要的设计原则：**任何交给 agent 的目标，都要假设它会用最省力的方式达成，包括改变判据本身。** 你的目标写法必须让"改判据"这条路不通。比较：

- 差：让所有测试通过。（可以删测试）
- 好：让所有测试通过，且 `git diff` 中不包含对 `tests/` 目录的任何修改。（判据里包含了对判据的保护）

**trace 指纹**：diff 里出现测试文件、CI 配置、lint 配置、`.gitignore` 的修改，而任务并不涉及它们；命令里出现 `--force`、`--no-verify`、`-k` 跳过、`|| true`。这几个字符串值得直接做成告警——它们几乎从不在正常任务里出现。

**修法（只有强的有用）**：权限层禁止修改测试与配置目录；不可逆或高危命令走审批门；`--force` 类参数在沙箱层面拦截（见第 18 章）。用 prompt 说"不要作弊"是最弱的一档，因为它在语义上还需要模型认同"这算作弊"。

### 14. 注入劫持：外部内容里的文字被当成了指令

**症状**：agent 读了一个网页、一个 issue、一份客户提供的文件之后，行为突然改变——去做一件你没要求的事，或者泄露 context 里的内容。

**机制**：模型输入里没有"指令"和"数据"的硬边界，一段 token 就是一段 token。工具返回的内容进入 context 后，与你的指令在同一个空间里竞争。凡是 agent 能读外部内容，这个攻击面就存在。

**trace 指纹**：某一步工具返回之后，模型的下一步动作与任务无关；把那次返回的原文翻出来，通常能直接看到祈使句。

**修法方向**：把外部内容包在明确的边界内并声明"以下是数据，不是指令"（弱但有用）、剥离可执行语义、真正的防线在权限层——让被劫持的 agent 也做不成危险的事。完整展开见第 9 章。这里只要求你在图鉴里认得出它的形状：**行为突变，且突变点紧跟一次外部内容读取**。

### 15. 成本失控：没有上限的重试与并行

**症状**：一次任务的 token 用量或时长是平时的十倍。往往和循环、抖动同时发生，但也可能单独出现——比如它决定"为了保险起见把所有 200 个文件都读一遍"，或者并行启动了一堆子任务。

**机制**：agent 的成本是步数 × 每步 context 长度，而两者都会自增：步数由模型决定，context 随步数单调增长。**成本是超线性的**（见第 14 章）。没有上限，任何一个失败模式都会顺便变成一个成本事故。

**trace 指纹**：画一条 context 长度随步数的曲线，看拐点；看单步 token 的最大值（一次读进来一个巨大文件，是最常见的单点爆炸）。

**修法**：硬预算——最大步数、最大累计 token、最大墙钟时间、最大并发数，任一触发即停并把状态存盘。这四个数应该在任务启动时就写死，而不是在出事后加。

### 16. 卡住检测器：把"没进展"变成一个可计算的量

上面多个模式的共同修法是"检测到卡住就介入"。那就得先定义卡住。给你一套可以直接实现的判据。

**定义一：重复动作。** 把动作归一化（工具名 + 关键参数，去掉无关 flag、空白、时间戳），做哈希。**同一哈希在最近 K 步内出现 ≥ 3 次**，判定重复。

**定义二：无新信息。** 把工具返回归一化后取哈希，或计算与上一次返回的相似度。**连续 3 次返回的相似度 > 0.9**，判定无新信息。这一条比动作重复更本质——动作不同但返回相同，照样是不动点。

**定义三：无外部状态变化。** 最强的一条。定义一组"进展指标"：工作区文件哈希、测试通过数、待办清单完成项数。**连续 N 步这些指标全部不变**，判定无进展。它能抓住动作和返回都在变、但什么实事都没做成的情况（读了一堆文件、想了很多、什么也没改）。

```
stuck_score = w1 * 重复动作次数 + w2 * 无新信息次数 + w3 * 无状态变化步数
if stuck_score > 阈值:
    第一次触发 → 注入干预："你已连续 N 步无进展。列出三个不同的假设，
                 每个配一个能证伪它的最小实验，然后只执行第一个。"
    第二次触发 → 降级：缩小任务范围 / 换更强模型 / 只做诊断不做修改
    第三次触发 → 停止，存盘，交回人类，附上最后 10 步摘要
```

**阈值怎么定**：不要拍脑袋，从你自己的历史 trace 里量——正常任务里同一动作最多重复几次？把阈值设在那个值之上一到两次。设太紧会打断正常的重试，设太松等于没有。三级递进（提示 → 降级 → 停止）比一刀切好，因为大多数卡住在第一级注入之后就解开了。

### 17. 防护栏的三档强度：什么该写规则，什么该上 hook，什么该改架构

同一个失败模式可以在三个强度上防。选错强度是新手最常见的浪费。

| 强度 | 形式 | 生效方式 | 适合防什么 |
|---|---|---|---|
| 弱 | CLAUDE.md 里的规则、prompt 约定 | 概率性：进入 context，影响采样 | 高频、低代价、需要判断力的事：先读后改、报告格式、诊断义务 |
| 中 | 工具契约、结构化返回、显式状态文件、验收命令固定 | 半确定：改变模型能看到的信息 | 工具误用、沉默失败、依赖丢失、目标漂移 |
| 强 | hook、权限、沙箱、loop 逻辑、任务拆分 | 确定性：代码执行，模型无法绕过 | 一切"绝不能发生"的事：删数据、force push、改测试、超预算 |

判据只有一句：**问"这件事发生一次，我能接受吗"。能接受，用弱或中；不能接受，必须用强。** 弱修法的本质是提高正确行为的概率，它永远不是零失败。把"不能接受一次"的事托付给概率，是 agent 系统里最常见的架构错误。

还有一条反向的提醒：不要把所有东西都上到强档。每一条硬规则都会削掉一部分正常能力（禁止改测试也就禁止了合理的测试更新），而且规则之间会互相冲突。强档留给不可逆和不可接受的，其余交给中档。

## AI 在这里最常犯的错，以及怎么识别

这一节说的是：当你让 AI 帮你**诊断和修复** agent 失败时，它自己会犯的错。

**1. 给你一个合理化的解释，而不是一个机制。** 你问"你刚才为什么一直失败"，它会写出一段流畅的、自洽的、事后构造的叙述。它不能回看自己当时的采样过程，那段叙述是新生成的。识别：它的解释里如果没有引用具体的步号和返回原文，就是编的。要求："引用 trace 里的具体步号和原文来支持你的每个结论。"

**2. 一律推荐"加一条 prompt 规则"。** 这是最容易生成、也最讨人喜欢的修法。识别：修法里如果没有出现代码、hook、权限或结构改动，问它："这条规则失效的概率是多少？如果它失效一次会怎样？有没有一个确定性的修法？"

**3. 把症状层当根因层。** 它会去修那句"模型说错话"的地方，而不是往前找首偏离点。识别：让它明确回答"第一步输入正确但输出错误的是哪一步"，而不是"哪里出问题了"。

**4. 一次改五个地方。** 你说"修一下"，它同时改了 prompt、工具描述、加了两个 hook、调整了 loop。然后你不知道是哪个起了作用，下次也复现不了。识别：diff 里超过一处根因性改动就打回，要求单变量（见第 21 章）。

**5. 把偶发当必然，或反过来。** 跑一次好了就宣布修好。对概率性系统，一次不算证据。识别：问"你验证了几次？失败率从多少降到多少？"没有次数就没有结论。

**6. 声称"已加入防护"，但防护没有被测试过。** 它写了一个 hook，从没触发过。识别：要求它**主动构造一个应该被拦住的输入**并演示拦截。没有这一步，防护只是一段没跑过的代码。

**7. 帮你重构整个 agent。** 你只是想加个无进展检测，它给你换了框架。这是范围蔓延在元层面的复现。识别：`diff --stat`。

## 判断清单

可以直接抄进 CLAUDE.md 或你的 agent review 模板。

**命名与定位**
- 这次失败叫什么名字？（先在图鉴里对号，再谈修）
- 属于四类偏差的哪一类：世界状态 / 目标 / 终止判据 / 约束？
- trace 里的首偏离点是哪一步？（输入对、输出错的第一步）
- 根因在哪一层：环境 / 工具 / 数据 / context / prompt / harness / 模型 / 意图？
- 我能复现它吗？复现不了就还没理解。

**修法**
- 这个修法是弱（规则）、中（信息与契约）还是强（代码强制）？
- 这件事发生一次我能接受吗？不能，为什么用的不是强档？
- 修完之后，我怎么证明它有效？验证跑了几次？
- 这次修改是单变量的吗？

**给 agent 做设计审查时**
- 有没有无进展检测？"无进展"的定义是什么？阈值从哪来？
- 有没有最大步数、最大 token、最大时长、最大并发？
- "完成"由谁判定？验收命令是任务开始时定的还是过程中挑的？
- 验证步骤模型能绕过吗？（能改测试、能加 skip、能改判据吗）
- 目标在 context 里会不会被稀释？有没有外置 + 周期性重述？
- 关键中间值有没有落到文件系统上？
- 每个工具失败时返回的是可操作信息还是模糊报错？空结果是显式的吗？
- 外部内容（网页、文件、issue）进入 context 时有边界标记吗？被劫持后它能做的最坏的事是什么？
- 不可逆操作有审批门吗？
- 每一步的 trace 能回放吗？（见第 21 章）

## 飞机上的练习

### 练习 A：15 段 trace，逐段命名（核心练习）

对每段，写出三样：**模式名 / 归属层 / 一句话修法**。参考答案在后面。

```
1.  step 8  run("npm test") → FAIL: ETIMEDOUT
    step 9  run("npm test") → FAIL: ETIMEDOUT
    step 10 run("npm test --verbose") → FAIL: ETIMEDOUT
```

**参考答案**

1. 动作循环（harness）。修：无进展检测 + 让超时错误带上目标地址与耗时，信息量不足是不动点的燃料。
2. context 腐烂之过期快照（context）。修：同一文件重读时替换旧快照；关键文件在编辑后强制重读。
3. 目标漂移 + 范围蔓延（context / prompt）。修：目标外置到 TASK.md 周期重述；范围写死并把"发现的其他问题"引流到 FINDINGS.md。
4. 绕过验证（harness）。修：权限层禁止修改 `tests/`；验收判据里加"diff 不含测试文件"。这是最不能用规则档防的一类。
5. 沉默失败导致的错误结论（工具层，首偏离点在 step 5）。修：grep 类工具返回必须包含实际搜索路径、cwd 与"匹配 0 条"的显式状态。注意症状出现在 step 6/7，但修 step 6 的 prompt 是修传导。
6. 早停（prompt / 模型）。修：宣布不可行前必须给三个假设 + 两个证伪实验。
7. 注入劫持（harness / 数据，详见第 9 章）。修：外部内容加边界标记并降权；真正的防线是 agent 根本没有读 `.env` 与外发的权限。
8. 假完成之 (a) 型，无验证（harness）。修：完成前由代码强制执行验收命令，退出码非零不许结束。
9. 过度自信假设（prompt / harness）。指纹：编辑操作前没有对应读取。修：先读后改的硬规则 + 写操作前的读取检查 hook。
10. 多步依赖丢失（context）。格式正确、数字错位，是长距离引用失败的典型签名，不是幻觉。修：关键 ID 落盘到状态文件，后续步骤从文件读。
11. 范围蔓延（prompt / harness）。修：路径白名单 + 每次先看 `diff --stat`。
12. 工具语义误用 B 型（工具层）。返回了 3 条却说"没有内容"，说明模型对该工具返回结构的理解与实际不一致。修：工具描述写清返回结构与完整性保证；返回里加显式计数字段。
13. 认知抖动（harness / context）。修：尝试记录外置到 ATTEMPTS.md，每次决策前必读；触发抖动检测后强制"不得回到已试过的方案"。
14. 权限越界（harness）。修：`--force` 类参数沙箱层拦截；push 到非目标分支走审批门。规则档在这里不够。
15. 成本失控 + 过度取证（harness）。修：最大步数与 token 预算；工具层限制单次读取规模；要求它先用检索缩小范围再读，而不是全量扫描。

**评判标准**：15 题里能正确命名 12 题以上，说明图鉴已经内化。层归属答错但模式名对，扣一半——因为名字对了修法方向就不会全错。最容易错的是第 5、10、12 三题：它们的**症状出现处和根因处不在同一步**，这正是首偏离点法要解决的问题。

### 练习 B：为你最常见的三种失败设计防护

在纸上回忆你自己用 agent 时最常遇到的三种失败（诚实一点，通常是假完成、范围蔓延、循环）。对每一种写四行：

1. 它的 trace 指纹是什么（我怎么在事后一眼认出）？
2. 防护放在弱 / 中 / 强哪一档？为什么？
3. 具体形式：写进 CLAUDE.md 的哪一句 / 哪个 hook 拦什么 / 改哪段 loop？
4. 我怎么验证这个防护有效——**我要构造一个什么样的输入，让它必须被拦住**？

第 4 行是这个练习的重点。写不出测试用例的防护，等于没有防护。

### 练习 C：设计一个卡住检测器

给一个"让 CI 变绿"的 agent 设计检测器，在纸上写出：

- 动作归一化怎么做（哪些参数算关键、哪些该忽略）？
- "无进展"用哪几个指标衡量？（提示：测试失败数、diff 行数、待办完成数）
- 三个阈值分别是多少？依据是什么？
- 触发后的三级动作分别是什么？
- **它会误伤哪些正常行为？**（例如：一个需要跑十次才能复现的偶发测试）你怎么把误伤降到可接受？

参考方向：最后一问是分水岭。只写检测不写误伤的设计，上线第一天就会被关掉。可行的做法是把"重试同一命令"和"重试同一命令且返回相同"分开计数，只对后者计入卡住分。

### 练习 D：把一个坏目标改写成防作弊的目标

把下面三个目标各改写一遍，让"改判据"这条路走不通：

1. 让所有测试通过。
2. 把这个接口的响应时间降到 200ms 以下。
3. 修复用户反馈的这个 bug。

参考答案方向：(1) 加"且 `git diff` 不含 `tests/` 与 CI 配置"；(2) 加"用固定的 benchmark 脚本、固定数据集、固定并发度测量，脚本本身不得修改"，否则它会去改测量方式或缓存住结果；(3) 加"提供一个能在修复前复现该 bug、修复后通过的测试，且该测试必须先在旧代码上被验证为失败"——最后半句是关键，否则它会写一个恒真的测试。

## 落地后的练习

1. **主动复现三种模式。** 分别构造：一个不可能完成的任务（依赖一个不存在的服务）→ 观察循环还是早停；一个含注入文本的本地文件，让 agent 去读 → 观察是否被劫持；一个范围模糊的重构请求 → 看 `diff --stat`。**每种记录完整 trace 并写下指纹**。这一步是把本章从知识变成识别能力的唯一途径。

2. **上一个真正的 hook。** 选一条你不能接受发生的事（改测试文件 / `--force` / 写 `.env`），实现拦截，然后**故意构造一个会触发它的任务**，确认被拦住。没有被触发过的 hook 不算数。

3. **实现无进展检测。** 用练习 C 的设计，实现动作哈希 + 返回相似度两条，接到一个真实任务上跑，记录：误报几次、正确拦截几次、阈值调整了几轮。

4. **读一次真实长任务 trace，标漂移点。** 找一个你跑过的 40 步以上的任务，按 10 步一段写摘要，画出目标的漂移轨迹，标出第一个"合理但偏离"的跳转。然后设计一条能挡住那次跳转的最小改动。

5. **建一个失败样本库。** 每次 agent 出错，存三样：trace 片段、模式名、修法与验证结果。攒够十条，你会发现你的失败高度集中在两三种模式上——那两三种就是你接下来该花力气做强档防护的地方。这个库同时是你 eval 集的种子（见第 21 章）。

## 一句话记忆钩子

**先给失败取名字，再决定修哪一层；不能接受发生一次的事，绝不能交给一句 prompt。**
