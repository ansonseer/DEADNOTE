# 第 10 章 LLM 底层 I：token、embedding、attention、KV cache、context window——从机制推出能力边界
*模型不是一个"偶尔犯错的人"，而是一个在 token 序列上做条件概率预测的函数；它的每一种强和每一种弱，都能从这几个零件推出来。*

## 为什么这一章对你重要

你已经每天在指挥它了。但当它把一段话里的 "the" 数错、把两个客户的名字张冠李戴、在会话后半段忘掉你开头定的规矩、或者你只改了 prompt 开头一个字账单就翻倍时——第一反应大概是"换个说法再试一次"。那是对人的修法。对函数，修法是先找出哪个零件的哪条性质导致的，再决定改输入、加工具、还是换层解决。

本章只讲五个零件：token、embedding、attention、KV cache、context window。它们够你推出绝大多数"prompt 技巧"，不用背。训练为什么让它幻觉和谄媚见第 11 章，推理经济学见第 12 章。读完你应该能做到：看到一个症状，先说出这是哪个零件的哪条性质，再决定修法。

## 核心机制

### 0. 先把它降级成一个函数

去掉所有包装，一个 LLM 就是：

```
next_token_distribution = f(previous_tokens)
```

输入是一串整数（token id），输出是词表上每个 token 的概率。生成一段回答就是把它循环调用几百次：每次挑一个 token 接到序列末尾再喂回去。它没有别的输入通道。它"知道"的东西只存在两个地方：**权重里**（训练时压进去的统计规律）和 **context 里**（这次调用喂进去的 token）。没有第三个地方。所谓 system prompt、user 消息、tool 结果、"记忆"，到函数入口全部被摊平成同一串 token，差别只是前后夹着不同的特殊分隔 token。

记住这一点，后面所有推论都从它长出来。

### 1. Tokenization：模型看到的不是字，是编号

文本进入模型前先被一个固定的 tokenizer 切成 subword 片段并映射成整数。主流是 BPE 一类：从字符级开始，反复把语料里最常相邻的两段合并成新符号，直到词表达到预设大小（几万到十几万级）。结果是：高频英文词往往是一个 token，带空格的词形是另一个 token（`"hello"` 和 `" hello"` 编号不同），少见的词被拆成几段，中文常常一两个字一个 token、甚至一个字被拆成多个 byte 级 token，代码里的缩进、括号、驼峰各有各的切法。

由此推出的三条性质：

**密度不同。** 同样的信息量，英文、中文、JSON、代码、Base64 消耗的 token 数不一样。估算成本、判断"这份文档塞不塞得下"、比较两个 prompt 谁更贵，都只能按 token 算。粗略的直觉：紧凑的英文散文最省，中文通常更贵一些，带大量缩进和标点的结构化数据可能比同样信息的散文贵得多，随机字符串（hash、UUID、Base64）最贵——没有任何可合并的模式，几乎退化到逐字节。

**模型看不见字母。** 一个 token 是一个不透明的编号，模型没有直接通道去看它由哪些字符组成。它对"strawberry 里有几个 r"的回答，靠的是训练语料里有没有讨论过这个词的拼写，而不是去数。于是所有**字符级任务**——数字母、反转字符串、算一句话多少字、按精确字数截断、检查两段是否逐字一致——都是结构性弱区。它偶尔答对不是因为会数，是因为训练里见过。

**数字是被拆开的。** 一个长数字会被切成若干片（切法取决于 tokenizer：有的按单个数字切，有的按几位一组切）。`123456` 和 `1234567` 的切分边界可能完全不同。所以算术不是在"数值"上进行的，而是在一堆编号片段上做模式匹配：小数字、常见运算它记得很熟，位数一多、进位一多出错率陡升，而且错得很有自信——对它来说那串 token 和正确答案"看起来"一样顺。

顺便解释一个常见现象：为什么改 prompt 里一个标点、多一个空格，输出会变？因为那可能改变了 token 切分，模型看到的输入序列和之前不是"几乎一样"，而是在某一段上完全不同。

**图像也是 token。** 多模态不是另一条通道：图像先被切成网格块（patch），每块经视觉编码器变成向量，再当作一串 token 拼进同一个序列，和文字 token 一起被同一套 attention 处理。三条推论：一张图消耗可观的 token 预算，分辨率越高越贵；看图的粒度受限于块的大小，所以它读得懂"这是一张表格"，却常读错某一格里的小字或小数点；图和文字竞争同一份注意力预算，塞十张图和塞一份长文档是同一种代价。

### 2. Embedding：编号变向量，相近的意思靠得近

token id 是离散的，模型要的是能做算术的东西。第一层是一张查表：每个 id 对应一个几百到几千维的向量（embedding）。这张表是训练出来的，训练的结果是：在语料里出现在相似上下文中的 token，向量会靠得近。"猫"和"狗"近，"猫"和"HTTP"远。

两点推论：

一，模型内部处理的从来不是"词"，而是向量的几何关系。它擅长"这个和那个像不像"——相似度在向量空间里是天然操作，这是它模式匹配强的根源；它不擅长"是否精确相等"，因为向量空间里只有距离，没有相等。

二，RAG 检索用的 embedding 模型（第 16 章）是同一个思想，只是把整段文本压成一个向量。所以它有同样的性质：擅长找"意思差不多"的，不擅长找"包含这个精确 ID"的。

### 3. Attention：每个 token 看全部前文并加权

这是 Transformer 的心脏，也是你解释绝大多数"上下文现象"的工具。直觉版：

序列里每个位置的向量被投影成三份：Query（我在找什么）、Key（我是什么，供别人找）、Value（选中我你拿走什么）。用它的 Q 和前面所有位置的 K 做点积得到一排分数，softmax 成一组加起来等于 1 的权重，再用这组权重对所有 V 加权求和，就是这个位置的新表示。这一套并行做很多份（多头），有的头专看语法结构，有的专看指代关系。然后层层堆叠，几十层。

```
        token_i 的新表示 = Σ_j  softmax(Q_i · K_j / √d)_j  ×  V_j
                           ↑
                  对 j ≤ i 的所有位置（因果掩码：只看前面）
```

由此推出的性质，每一条都对应你见过的现象：

**只有 context 里的东西才影响输出，且是通过"被看到"才影响。** 你没写进去的约束，它没有任何渠道知道。你写进去了但被 attention 分到极低权重的约束，效果上等于没写。所以"它读过了"和"它用上了"是两件事。

**softmax 是一个固定总量的预算。** 所有位置的权重加起来是 1。序列越长，平均到每个 token 的权重越小。你往 context 里多塞一万 token 的"参考资料"，不是免费的：它们参与分母，把真正重要的那几行的权重摊薄了。这就是**注意力稀释**。无关内容不是"多多益善"，是噪声，而且噪声占预算。

**因果掩码：只看前面。** 生成第 i 个 token 时它只能看到 0 到 i-1。所以模型不能"回头修改"已经吐出去的东西；也所以 prompt 里放在后面的指令能看到前面的全部内容，而前面的内容被处理时看不到后面的指令。

**计算量随长度平方增长。** 每个位置要和前面所有位置算一次分数，n 个 token 就是 n² 量级的点积（工程上有各种优化，但性质不变）。所以 context 翻倍，prefill 的计算不止翻倍；长 context 又贵又慢，不是定价策略，是物理。

**多跳依赖分散在长文里天然困难。** 一次 attention 能做的是"从若干位置加权取信息"。若结论需要 A 处的事实 + C 处的事实 + 它们之间在 B 处的隐含关系，且三者相隔很远，就得靠多层叠加接力。链条越长、跨度越大，某一环权重不够高就断掉——而模型不会报错，只会顺着流畅地写下去。

### 4. 位置信息与长度外推

attention 本身对顺序是盲的：把输入 token 打乱，加权求和的结果不变。模型要知道谁前谁后，必须额外注入位置信息，主流做法是把位置以旋转或相对偏移的形式编进 Q 和 K，让点积天然带上"我们相隔多远"。

推论：模型对"距离"的感知是训练出来的，训练时见过的序列长度有一个分布，超出这个分布的位置关系它从来没练过。所以宣称的 context window 是"塞进去不报错"的硬上限，不等于"在整个范围内表现均匀"：越靠近上限，越是训练中很少经历的区域，退化是自然的。你在超长会话末尾感到它"变笨"，一部分原因在这里，另一部分在第 8 节。

### 5. 层堆叠、一次前向一个 token、没有草稿纸

从输入到输出，序列经过固定的几十层，每层一次 attention 加一次前馈变换，最后一层的最后一个位置吐出下一个 token 的分布。关键约束是：**每生成一个 token，计算量是固定的**。无论这个 token 是"的"还是一道题的最终答案，经过的层数和运算一模一样。模型没有"这题难，我多想一会儿"的内部开关。

这就是它没有草稿纸的意思：它无法在内部悄悄跑一个循环、做一次搜索、试错三次再回答。想"多算一点"，唯一的办法是**把中间步骤写成 token 输出出来**，这些 token 进入 context 被后续 attention 看到，成为下一步的输入。模型的工作记忆，就是它自己刚吐出的文字。

由此直接推出：

- "先一步步想再回答"为什么有效：不是魔法咒语，是给了它一块外置草稿纸，把一次前向能做的固定计算量，换成了几百次前向的累积计算量。
- 所谓"扩展思考"模式，机制上就是把这块草稿纸变得更长、更自由，并在训练里专门练过怎么用它。本质仍是"用更多输出 token 换更多计算"。
- 反过来，要求它"只输出最终答案，不要解释"就是在没收草稿纸。对模式匹配型任务无所谓，对多步推导任务你亲手砍掉了它的正确率。想要干净输出又要推理，就让它先推理、再用明确分隔给出结论，或把推理放进不展示的字段。

### 6. 自回归生成：错误会自我强化

每一步只预测下一个 token，然后把它当成既定事实接到序列上。这带来一个和人很不一样的性质：**它不能反悔**。第 40 个 token 一旦写错，第 41 到 400 个 token 都在"这个错误已经发生"的条件下预测，模型会尽力让后文和前文自洽——也就是把错误圆得越来越像真的。

你见过的现象：

- 它在函数名上写错一个词，接下来会围绕这个不存在的函数编出参数、返回值、用法示例，每一处都很流畅。
- 它在推理第二步算错一个数，最后的结论"逻辑严密"地建立在错数上。
- 你要它列 10 条，它第 3 条开始跑偏，后面 7 条越跑越远，因为每一条都在模仿前一条。

策略从这里推出：让它**先输出结构再填充**（先列大纲，再逐节写），每段的"条件"更干净；重要结论**在分开的调用里独立验证**，而不是在同一段生成里让它"检查一下"——同一段里的检查，条件中已经含着刚才的错误，它更倾向自洽而非推翻。这也解释了问"你确定吗"为什么常得到改口：不是它发现了错，而是"用户质疑 → 道歉修改"是高频续写模式（训练根源见第 11 章）。

### 7. KV cache：prefill 与 decode 是两个阶段

现在看推理引擎实际怎么跑。生成一个回答分两步：

**Prefill**：把整个 prompt（system + 历史 + 本轮输入）一次性并行过一遍所有层，为每个位置、每一层算出 K 和 V 存下来。这一步算力密集，耗时大致正比于 prompt 长度（叠加上一节的平方项）。用户感受到的"首 token 延迟"主要就是它。

**Decode**：之后每生成一个 token，只需要为这一个新位置算 Q/K/V，然后拿它的 Q 去和缓存里所有旧的 K 做 attention。旧 token 的 K、V 不用重算——这就是 **KV cache**。这一步是逐个串行的、访存密集的，每个 token 的时间大致是常数，所以输出越长越慢，且线性。

```
[ system prompt ][ 项目知识 ][ 历史对话 ][ 本轮输入 ] → prefill（并行，一次）
                                                          ↓
                                     [ t1 ] → [ t2 ] → [ t3 ] → ...   decode（串行，逐个）
                                     每步只算新 token，复用左侧全部 K/V
```

KV cache 的体积随序列长度线性增长，每层每头都要存——长 context 对显存的压力主要来自这里，也因此长 context 的并发能力更低（吞吐与 batching 的经济学见第 12 章）。

**Prompt caching** 是把这件事跨请求做：如果这次请求的 prompt 前缀和上一次**完全一致**（逐 token 一致），前缀部分的 K/V 就可以直接从缓存取，不用再 prefill。这带来的降本降延迟是实打实的，因为省掉的是最贵的那一段计算。

条件是"前缀完全一致"而不是"内容差不多"。由此推出一条硬规则：

**稳定的放前面，变化的放后面。** system prompt、工具定义、项目说明这些每次都一样的放最前；本轮输入、动态检索结果、时间戳放最后。你在 system prompt 开头塞一个精确到秒的"当前时间"，等于每秒打掉一次整个缓存，后面几万 token 全部重新 prefill。同理，工具列表顺序变了、某个 few-shot 例子改了一个字、历史消息被中途编辑，缓存从改动点起全部失效：它按前缀匹配，改动越靠前损失越大。

这一条在日志里长什么样：同一个 agent loop，前几轮的账单里"缓存命中的 token 数"很高，某一轮之后突然归零、总输入 token 暴涨、首 token 延迟从亚秒级跳到几秒——去找那一轮在 prompt 前部动了什么。

### 8. Context window：硬上限，不是有效记忆

把前面几节合起来，就能说清 context window 到底是什么。

**它是本次输入的长度上限，不是记忆。** 模型没有跨调用状态；你感受到的"它记得上一轮"，是 harness 把上一轮文本又塞进了这次的 context。会话越长，每次调用的输入越长，直到撞上上限，然后 harness 要么截断、要么压缩（compaction）——压缩就是让模型写一份摘要替换原文，摘要没写进去的细节就永远丢了。长会话后期发现它"忘了"你开头定的约束，机制上是两件事叠加：约束还在 context 里但被稀释了；或者约束已在某次 compaction 中被摘要掉。前者的症状是"提醒一下就回来"，后者是"提醒它也一脸茫然，像第一次听说"。

**有效注意力远小于窗口大小。** 反复观察到的规律：把一条关键事实放在长 context 的开头或结尾，模型用上的概率明显高于放在中间——**lost in the middle**。机制上是两股力量：靠近开头的位置在训练中被大量看到（很多任务的指令就在开头），靠近结尾的位置离当前生成最近；中间既不占"先入"也不占"临近"，在 softmax 的预算竞争里最容易输。叠加第 4 节的外推退化，就得到一条曲线：短 context 基本均匀，长 context 呈 U 形，中间是洼地。

**噪声不是免费的，是负资产。** 每多一段无关内容，就多一份 softmax 分母、多一份"看起来相关但不该用"的干扰源。典型的 context 污染：你之前让它改过一个旧版本配置文件，那段对话还在 context 里，现在问新版本的问题，它把旧字段名"顺手"写了进来。它不是记错了，是 attention 真的在那段旧文本上分到了权重，而模型没有"这段过时了"的标记——所有 token 在它眼里同等真实。这就是 **context rot**：会话拉长，过时、矛盾、无关内容的比例越来越高，表现随之腐烂，而不只是随长度线性变差。

所以"窗口有多大就能记住多少"是最常见的误解。正确的模型是：窗口是塞得下多少，有效注意力是用得上多少，两者差一个量级是常态，而后者还取决于噪声比例和关键信息的位置。"塞满 context"是反模式，第 13 章讲怎么反过来做。

一个从机制推出的 context 布局（这是第 13 章的起点，这里只给骨架和理由）：

| 位置 | 放什么 | 理由 |
|---|---|---|
| 最前 | 角色、不变的硬约束、工具定义 | 缓存前缀；"先入"位置权重高 |
| 前中 | 项目级知识、稳定的参考资料 | 变化频率低，尽量留在缓存里 |
| 中 | 历史对话（经过压缩） | 反正会被稀释，别放关键约束 |
| 最后 | 本轮任务、动态数据、**关键约束的复述** | 离生成最近，"临近"权重高；因果掩码下它能看到前面全部 |

注意最后一行：真正重要的约束，值得在开头写一遍、结尾再复述一遍。这不是啰嗦，是同时占住 U 形的两个高点。

### 9. 采样：为什么 temperature 0 也不完全确定

函数输出的是一个分布，最后一步要从分布里挑一个 token。temperature 把分布拉平或削尖，top-p 截掉尾部，然后按概率抽样——所以同一输入不同输出是**设计如此**，不是 bug。用户报告"它昨天还对、今天就错了"，先问采样参数。

但 temperature 设为 0（每次取最高概率）也不保证逐字一致。机制层的原因：浮点加法不满足结合律，而推理引擎会把你的请求和别人的打成不同大小的 batch、走不同 kernel 路径，累加顺序不同，末位小数就不同；当两个候选 token 概率极接近时，这点差异足以翻转选择，一旦翻转，后面整段按自回归分叉。所以"确定性"只能靠**外部约束**拿到——schema 校验、代码断言、多次采样取一致——不能靠参数。完整机制见第 12 章。

### 10. 幻觉在这一层的根源：它必须输出一个 token

先把最粗的一条讲清楚，细节留给第 11 章。函数每一步都要给出一个分布并挑一个 token，词表里没有一个 token 叫"我不知道，停止"。当 context 里没有答案、权重里也没有可靠记忆时，softmax 依然会把概率分给"看起来最像答案"的 token——一个和真实 API 命名风格一致的函数名、一个格式标准的引用。它被优化的目标是"续写得像"而不是"续写得真"，而对它来说这两者的信号是同一个：流畅度。

所以在机制层，规避幻觉不靠"叫它诚实"，靠**把"不知道"外化**：给检索工具，让"没查到"成为可观察的事件；给验证工具，让"跑不通"成为信号；要求它引用 context 里的原文位置，让"引不出来"暴露出来。这三件事都是把模型内部不存在的状态，变成系统里存在的状态。

### 11. 训练阶段给了它什么（一句话版，细节见第 11 章）

预训练把大规模文本压进权重，给它语言和世界知识，附带一个知识截止日期——之后的事它一概不知，且不知道自己不知道；监督微调给它对话格式和任务形态；偏好优化给它"人类更喜欢哪种回答"，副作用是讨好倾向。这里只需记住：**权重是有截止日期的静态快照，context 是你这次给的**；两者冲突时它不一定选后者，尤其当权重里那个版本出现过成千上万次。

### 12. 成本与延迟：从机制读账单

把第 7 节翻译成钱和时间：输入成本线性于 prefill 长度（叠加平方项，超长输入更不划算），缓存命中的部分显著便宜；输出逐个串行生成，延迟线性于输出长度，单价通常高于输入；首 token 延迟约等于未命中缓存那段的 prefill 时间。让它"先想再答"，买的是输出 token、等的是 decode 时间——准确率与成本/延迟是直接交易。看账单先问三句：输入里多少本可以缓存？输出里多少本可以不生成？多少轮串行调用本可以并成一次 prefill？（第 12 章展开。）

### 13. 从机制推出的能力边界表

把上面的性质压缩成一张可以直接用的表：任务、机制判定、该在哪一层解决。

| 任务 | 机制判定 | 解决层 |
|---|---|---|
| 判断两段话是否在说同一件事 | 向量相似度是天然操作 | 模型 |
| 从一堆杂乱描述里归纳出结构 | 模式匹配 + 语言能力 | 模型 |
| 按给定风格改写、翻译、总结 | 条件生成的主场 | 模型 |
| 写一段常规代码 | 高频模式的续写 | 模型 + 测试验证 |
| 数字母、数字数、精确长度 | token 不透明，看不见字符 | 代码 |
| 多位数算术、日期差、税额 | 数字被拆片，无草稿纸 | 代码 / 工具 |
| 逐字复制一段超长文本 | 自回归漂移 + 注意力稀释 | 代码（直接传原文） |
| 从 50 页文档里找一个精确 ID | 向量近似 ≠ 精确匹配 | 检索工具（关键词） |
| 结论依赖散布在长文各处的多个事实 | 多跳 attention 接力易断 | 先分段抽取，再综合 |
| 需要最新版本的 API 签名 | 权重是过期快照 | 把文档放进 context |
| 需要 10 次运行结果一致 | 采样 + 浮点非确定 | schema 校验 / 代码兜底 |
| 判断自己有没有错 | 同段自洽压力 > 纠错 | 独立调用验证 / 外部工具 |
| 跨会话记住一件事 | 没有跨调用状态 | harness 的 memory（第 18 章） |

用法不是背，是派任务前过一遍：这个任务落在哪一行？右列写着"代码 / 工具 / 检索"你却让模型直接做了，那就是系统设计上欠的债，迟早以一个自信的错误还回来。

## AI 在这里最常犯的错，以及怎么识别

分两组。A 组是**模型自己在这一层的失效**，你要能一眼归因到零件；B 组是**AI 帮你写系统时在这一层写出的错**，更隐蔽——那些代码看起来完全正常。

### A 组：模型自己的失效

**1. 自信的字符级错误。** 症状：问它一段话里有几个某字母、这句话多少字、把字符串反转，它给一个干脆的整数，没有迟疑标记，反复问还稳定地错成同一个数。机制是第 1 节：token 不透明。识别的第一反应——**任何"精确计数"的整数，只要它没把每一个出现逐个枚举出来，默认不信**。你该问："把每一个出现按顺序编号列出来，最后再给总数。"列出来是 3 个而它刚才说 2 个，就确认了这是机制问题，不是它"不认真"。修法是让代码数。

**2. 多位数算术、日期差、金额计算出错。** 症状很特别：量级对、格式对，只有中间几位错；或者闰年、月末、跨时区的边界错。日志里的样子是正确率随位数或步骤数陡降，而不是均匀的随机错。你该问："把这个计算写成一段可执行代码并运行。"没有执行环境时退一步："列出竖式和每一步的中间值"——那是在把草稿纸还给它。

**3. 长 context 中间被跳过，但它表现得像读过了。** 症状：它复述文档开头和结尾很准，对中间某节要么不提，要么用一句符合整体风格但原文根本没有的话糊过去。识别要主动：**埋 canary**——在长 context 中间插一句"若你读到这一句，请在回答末尾附上 `X7Q`"。回答里没有这三个字符，就说明那一段没被有效读取。这一招把"注意力有没有覆盖到"这个看不见的量变成可观察的二值信号，值得常备。

**4. 被 context 里的旧内容带偏（context 污染）。** 症状：输出里冒出你这一轮压根没提的字段名、旧变量名、上一个任务的格式。识别：在 context 里搜那个词——如果前面出现过，问题在 context 不在模型。修法是删掉或开新会话，**不是**加一句"不要用旧字段"——负面指令既占预算，又不能让它看不见旧内容。

**4b. 被 few-shot 例子带偏内容，而不只是格式。** 症状：你给三个例子只想教格式，它却把例子里的具体实体（公司名、数值范围、字段取值）搬进了新答案；或者例子恰好都是"是"，它对新样本也倾向答"是"。机制是 attention 不区分"这是格式示范"和"这是事实"——所有 token 同等真实，与当前输入相似度高的例子还拿到更高权重。识别：把例子整体换到一个明显不同的领域再跑，如果跟着变的是**内容**而不只是格式，就确认了；或把例子的标签配比故意做偏，看输出分布跟不跟着偏。修法是例子用中性占位符、正负配比均衡，而不是加一句"只参考格式"。

**5. 长会话后期变笨——要分成两种。** 症状 A：提醒一句它就恢复，这是稀释，约束还在 context 里只是权重不够。症状 B：提醒它像第一次听说，甚至反驳"你没说过"，这是 compaction 把约束摘要掉了，原文已经不存在。区分方法：让它"逐字复述本次会话里我给过的所有硬性约束"，复述不全就是 B 类。B 类不能靠提醒修，要把约束搬到每轮重新注入的位置（第 13、18 章）。

**6. 缺信息时编造 API、参数、引用。** 判据反直觉：**越像越可疑**。命名风格和那个库的惯例完美吻合、链接格式标准但打不开、编号格式正确但内容不存在——因为它被优化的目标就是"像"。你该问："这个函数你从 context 哪一段看到的？把原文贴出来。"贴不出来就是编的——这条追问把"知道"和"读到"分开了。

**7. 把过期版本当作现行。** 症状：用的是某个库若干年前的调用方式，语气极笃定——因为旧写法在训练语料里出现的次数远多于新写法。识别：问"这个用法哪个版本引入、哪个版本废弃"，答不准就是在靠统计惯性写。修法是把当前文档放进 context 并写明"以下文档优先于你的既有知识"——默认情况下，context 里出现一次的未必赢得过权重里出现上万次的。

**8. 把"它很确定"当成正确性信号，把它改口当成纠错。** 症状：你问"你确定吗"，它道歉并改；再问一次，它可能改回来。识别就是连问两次看它横不横跳——横跳说明两次改动都不基于证据，只是在续写"用户质疑 → 让步"这个高频模式。正确的追问是"给出一个我能自己跑一遍、用来判定对错的检查步骤"。

**9. 同一个 prompt 不同结果，被当成 bug 报上来。** 症状：工单写"昨天好的今天坏了"，代码没动。识别顺序：先看采样参数，再看 prompt 里有没有时间戳、随机排序、每次不同的检索结果。分开"输入变了"和"采样抖动"的办法是固定一份完整输入跑 10 次看分布——分布散是采样问题，分布集中但和昨天不同是输入变了。

### B 组：AI 帮你写系统时在这一层的错

**10. 用字符数或词数近似 token 数。** 症状：代码里出现 `len(text) // 4`、`len(text.split()) * 1.3` 这类魔法系数，截断逻辑在中文、JSON、base64 上偏差极大，上线后要么超长报错、要么白白浪费窗口。识别：搜这些系数。你该问："这里凭什么能用字符数近似 token？中文、代码、base64 各会偏多少？改成调用真正的 tokenizer。"

**11. 把动态内容放进 prompt 最前面。** 最常见的是当前时间、session id、随机 uuid、用户名。症状：缓存命中的 token 数长期为 0，输入成本和首 token 延迟完全不随会话推进而下降。识别：把连续两次请求的完整 prompt 做 diff，看**第一处**不同在什么位置——它前面的还能缓存，后面的全部作废。你该问："这个前缀在两次请求之间是不是逐 token 一致？第一个变化点在第几个 token？能不能挪到最后？"

**12. 用"塞更多 context"来修准确率。** 症状：方案是"把整个 repo、整个文档目录都放进去"。机制上这通常更糟：稀释加污染。你该问："这次任务真正需要哪几段？把其余的删掉再跑一次对比。"删掉反而变好，你当场就拿到了注意力稀释的证据。

**13. 同时要求"一步步仔细分析"和"直接输出 JSON，不要任何多余文字"。** 自相矛盾：一边要长途推理，一边没收草稿纸。症状是这类 prompt 在复杂样本上正确率明显低于简单样本，而简单样本一切正常，问题被长期掩盖。识别：读 prompt 找这对矛盾。修法是让推理进入一个专门字段或前置段落，再解析结论。

**14. 用 temperature 或措辞去解决"确定性"需求。** 症状：分类服务靠 prompt 里写"请严格保持一致"来保证一致性，或把 temperature 调到 0 就宣称确定。第 9 节说过这两条都不成立。确定性只能在系统层拿到：受限输出、schema 校验、多次采样投票（见第 12 章、第 21 章）。

## 判断清单

可以直接抄进 CLAUDE.md 或审查模板。前六条对每个任务问，后八条对每个系统问。

**派任务前：**

1. 这个任务需要的信息，在 context 里、在权重里、还是根本不在？不在的话我打算怎么补进来？
2. 它是模式匹配型（相似、改写、归纳、生成）还是精确型（计数、算术、逐字复制、精确匹配）？精确的那部分交给代码还是交给模型？
3. 它需要多步推理吗？如果需要，我给了草稿纸吗（允许中间输出、thinking、或拆成多轮）？
4. 关键约束在 context 的什么位置？开头写了、结尾复述了吗？会不会掉进中间？
5. 我要求确定性吗？如果要，兜底在哪一层（schema / 断言 / 投票），而不是靠措辞？
6. 它的正确性我打算用什么证据判定？这个证据是模型自己给的，还是外部可复现的？

**做系统时：**

7. 我的 prompt 前缀在多次请求之间逐 token 一致吗？第一个变化点在哪？
8. context 里现在有多少是噪声（过时对话、无关文件、上一个任务的残留）？能删掉多少？
9. 长会话到多长会触发压缩？压缩后哪些硬约束会丢？丢了之后靠什么重新注入？
10. 有没有 canary 或等价手段，能让我观察到"中间那段到底有没有被读到"？
11. token 计数是用真 tokenizer 算的，还是用字符数拍的？
12. 输出里有多少 token 是没人读的（客套、复述问题、重复解释）？那既是延迟也是钱。
13. 当模型"不知道"时，系统里有没有一个地方能观察到这个事件？如果没有，它就只会编。
14. 这次的错误，我归因到了哪一层：tokenization / attention 与位置 / cache / context 组织 / 采样 / 训练（第 11 章）/ 我的工具与 harness（第 18 章）？说不出层，就还没诊断完。

## 飞机上的练习

只需要纸和脑子。每题都有参考答案，先写完再看。

**练习 1：六个现象的机制归因（本章核心练习）。**
对下面每一个现象，写出（a）由哪个零件的哪条性质导致，（b）一条规避策略，（c）一个能验证你归因正确的观察。

1. 让它数一段话里有几个 "the"，它给了一个自信但错误的数字。
2. 一份 30 页文档，它对第 1 页和最后一页复述准确，第 14 页的关键条件被完全忽略。
3. 同一个任务，你只在 system prompt 开头加了一行"当前时间"，账单翻了一倍。
4. 你让它输出 JSON，99 次正常，第 100 次多了一句解释导致解析失败。
5. 你加了一句"请一步步思考"，一道多步题从错变对。
6. 你问"你确定吗"，它道歉改口，改成了另一个错答案。

*参考答案要点*：(1) token 不透明，看不见字符；交给代码；验证是让它逐个枚举，看枚举个数与它给的总数是否矛盾。(2) softmax 预算固定 + 位置呈 U 形；关键条件在最前和最后各写一遍，或先分段抽取再综合；验证是把条件挪到结尾重跑看是否被采纳，并用 canary 测中间。(3) KV cache 按**前缀**匹配，改动点之后全废，改动点在最前等于全部失效；把动态内容挪到最后；验证是 diff 两次请求找第一个变化点。(4) 采样从分布里抽，尾部本来就有概率，temperature 0 也因浮点与 batching 不完全确定；受限输出 + schema 校验 + 重试；验证是同输入跑 N 次看失败率是否稳定在一个小比例。(5) 一次前向计算量固定、没有草稿纸，中间步骤必须以 token 写出来才能被后续 attention 看到；验证是对比两种 prompt 在同一批多步题上的正确率。(6) 自回归的自洽压力，加上"用户质疑 → 让步"是高频模式；验证是连问两次看它横不横跳。

**练习 2：设计一个 context 布局。**
你要给一个"读用户上传的合同、回答问题、必要时调工具"的 agent 排 context。写出四到六个分区的顺序，每个分区标注：里面放什么、变化频率、以及排在这个位置的两条理由（一条来自缓存，一条来自注意力）。

*评判标准*：（1）稳定度单调递减，越靠前越不变；（2）当前轮的问题在最后；（3）硬约束在开头出现过、并在最后复述；（4）历史对话在中段，并说明"这里会被稀释，不放关键约束"；（5）你能说出改动某个分区会从哪里开始缓存失效。五条中四条算过关。

**练习 3：十个任务分四类，外加一条辨别法。**
把这十个任务分到"模型层可解 / 需要工具 / 需要系统约束 / 不该用 LLM"，每个写一句机制理由：翻译一份合同、算这份合同的应缴税额、写一条 SQL、总结 50 页报告、逐字引用其中第 3 条、判断两份简历谁更匹配岗位、给 10 万条记录去重、根据历史数据预测下季度销量、把用户反馈归类到 8 个标签、判断一段代码有没有安全漏洞。然后回答第二问：当你手上只有一份输出、没有标准答案时，怎么把"流畅但错误"和"笨拙但正确"分开？

*参考答案要点*：分类判据就是那张能力边界表——精确计数与长度 → token 不透明；算税这类多步算术 → 数字被切片且无草稿纸，走工具；逐字引用 → 必须由代码从原文取；10 万条去重 → 确定性集合运算走代码；预测销量 → 该走统计模型，不该用 LLM；归类到 8 个标签 → 模型可解但要 schema 约束枚举值；判断有没有漏洞 → 模型可解但结论必须外部验证。**说不出"因为哪个零件的哪条性质"的条目不算分。** 第二问的核心是**不看语气，看可证伪性**：流畅但错误的输出通常没有可检查的锚点——没有引文位置、没有中间值、没有可复现的步骤，你想验都不知道从哪下手；笨拙但正确的输出往往拖着一堆你能逐条核对的东西。判据不是"读起来对不对"，而是"我能不能在五分钟内独立判定它错"。答不出第二问的，前面十题全对也不算过关。

**练习 4：预测位置实验的曲线。**
一个 20k token 的 context，你把同一条关键约束分别放在 5% / 25% / 50% / 75% / 95% 的位置，各跑 20 次统计遵循率。先画出你预测的曲线形状并写出理由；再写出两个会让这条曲线变平（位置影响变小）的因素、两个会让它变陡的因素。

*参考答案要点*：大致 U 形，两端高、中部低，结尾通常不低于开头。变平：总长度短、噪声少、任务简单、约束重复多次。变陡：接近窗口上限（外推退化）、噪声比例高、约束与周围内容语义相似而被淹没、任务需要多跳推理。**只答"U 形"说不出为什么两端高只算半分**——两端高的原因不同：开头是训练分布里指令常在开头，结尾是位置距离最近。

**练习 5：账单归因。**
一个 agent 每轮把完整历史重新发一遍，跑 20 轮。输入 token 总量随轮数怎么增长，线性还是平方？如果前缀完全稳定、只在末尾追加呢？如果每轮开头注入一次当前时间呢？

*参考答案*：完整重发时第 n 轮输入线性增长，20 轮累计是平方量级——长会话成本失控的主因。前缀稳定时每轮只需 prefill 新增部分，累计压回接近线性。开头注入时间戳则第一个 token 就变了，缓存命中为零，退回平方量级——**一行看起来无害的"当前时间"，能让 agent 的成本曲线换一个数量级**。

## 落地后的练习

目标不是"跑通"，是**亲手把这些机制的效应量出来**，让它从知识变成直觉。

1. **量 token 密度。** 用真 tokenizer 对同一段内容的四种形式计数：中文散文、等价英文散文、同信息的 JSON、一段 base64，记下四个比值。再算你项目 CLAUDE.md 的 token 数乘以它一天被重复发送的次数——这个乘积通常会让你当场删掉一半。

2. **lost-in-the-middle 实验。** 造一个 20k token 的长 context（塞无关文档即可），把同一条可验证指令（"回答末尾附上 `X7Q`"）分别放在开头、25%、中间、75%、结尾，各跑 10 次统计遵循率，画成曲线，和练习 4 的预测对比。做成可复用脚本，以后怀疑"它是不是没读到"就直接跑。**这是本章唯一必做的实验。**

3. **草稿纸对照实验。** 造 20 道需要三步以上推理的题（多位数算术、日期差、多条件筛选），同批题跑三种方式：直接答 / 允许中间推理 / 调用工具算，记录三条正确率。看第三条是不是接近满分——是的话你以后不会再争论"要不要给它工具"。

4. **缓存实验。** 同一个长 prompt 做两组请求：一组只改结尾，一组只改开头一个字符，对比缓存命中 token 数、输入成本、首 token 延迟。然后审计你现有 harness 的 prompt 拼装顺序，把动态内容全挪到最后，再测一次。

5. **抖动与幻觉。** 同一个分类 prompt 在 temperature 0 和一个较高值下各跑 20 次，统计输出分布，亲眼看到"参数不等于确定性"。然后问一个不存在的库的函数签名，观察它编造的完整度，再接一个检索工具重跑，看"不知道"有没有被外化成一个你能观察到的事件。

6. **把系统弄坏再修好。** 在你现有的 agent 里故意做三件事：把当前时间注入 system prompt 第一行；把关键约束从结尾挪到中间；把三个不相关的大文件塞进 context。分别记录成本、延迟、成功率的变化，再一件件改回来。**说得出每一项各让哪个指标变了多少，这一章才算学完。**

## 一句话记忆钩子

**它只有两个地方能"知道"——权重和 context；它一次只算一个 token、看不见字母、也没有草稿纸；attention 是一份总量固定的预算，缓存只认前缀。窗口是塞得下多少，注意力是用得上多少。**
