# 第 03 章 前端：浏览器是一台不可信的客户端——DOM、渲染、state、async、hydration

*前端的 bug 几乎都不是"画错了"，而是"同一份数据存了两份、两个异步谁先回来看运气、以及你把只有服务端才有资格做的判断交给了一台用户可以随意改写的机器。*

## 为什么这一章对你重要

前端是 AI 写得最快、看起来最像样、最容易骗过你的地方。因为浏览器极其宽容：CSS 写错不报错，只是位置歪一点；一个 promise 被拒绝没人 catch，页面照样显示；一个组件多渲染了二十次，你眼睛看不出来。你看到的是一张能跑的截图，于是你以为它对了。

它没对。它只是在"网络永远快、用户永远只点一次、数据永远非空、屏幕永远是你这块"的假设下没炸。真实世界里这四条全不成立，于是出现这类报告：切换客户后看到上一个客户的数据；点两次按钮下了两个单；刷新页面登录状态没了；手机上按钮跑到屏幕外；你的 API key 被人从公开的 JS 文件里翻了出来。

你交付的一切，用户真正摸到的就是这一层。这一章给的不是写 UI 的手感，而是**一套怀疑的顺序**：看到一个能用的界面时，先问状态住在哪、再问两个异步交错会怎样、再问刷新和后退会怎样、最后问这台不可信的机器上放了什么不该放的东西。

## 核心机制

### 3.1 浏览器这台机器：一条主线程干完所有事

先建立最底层的图像。浏览器拿到 HTML 之后做的事是一条流水线：

```
HTML 字节 → 解析 → DOM 树 ─┐
                            ├→ 计算样式 → 布局(layout) → 绘制(paint) → 合成(composite) → 屏幕
CSS 字节  → 解析 → 样式规则 ┘
                    ▲
JS ─────────────────┘  可以在任何时刻改 DOM 或样式，把流水线往回踢
```

关键事实只有一个，但它解释了前端一大半的性能问题：**解析 HTML、执行 JS、计算样式、布局、绘制，全部跑在同一条线程上**（合成和部分动画可以交给别的线程，但触发它们的逻辑仍在主线程）。这条线程同时还要处理你的点击、滚动、输入。

于是推论：

**长任务 = 页面卡死。** 一个 60Hz 的屏幕，每帧大约十几毫秒。JS 里一段同步的重活——遍历十万条数据、同步解析一个大 JSON、在渲染函数里排序整个列表——只要超过这个量级，这一帧就画不出来。体感是点击没反应、打字延迟、滚动一顿一顿。注意区分：**不是"慢"，是"不响应"**——慢是转圈但页面还能动，不响应是整页冻住、连光标都不闪。看到"冻住"，去找主线程上的同步长任务。

**大列表必须虚拟化。** DOM 节点不是免费的，每个都要参与样式计算和布局。一次渲染一万行，首屏就是几秒白屏加冻结。虚拟化（只渲染视口内的几十行，滚动时换内容）不是优化技巧，是列表可能上千行时的架构决定。AI 默认全渲染，因为它测试用的假数据只有五条。你要问的话是：**"这个列表在一万条数据下会怎样？有没有分页或虚拟化？"**

**重排（layout）比重绘（paint）贵。** 改颜色只需要重绘；改宽高、位置、字体大小会让浏览器重新算布局，而布局是牵一发动全身的。更糟的是"强制同步布局"：改完样式紧接着读 `offsetHeight` 这类几何属性，浏览器必须立刻重算布局才能回答；写在循环里就是每次迭代重算一次。症状是一个只在"移动几个方块"的动画卡到不能看。

**event loop：异步的顺序是有规则的，不是玄学。** 主线程执行完当前这段同步代码后，先清空 microtask 队列（promise 的 `.then`、`await` 之后的部分），再取一个 macrotask（`setTimeout`、事件回调、网络响应回调），执行完再清空 microtask，如此循环。你需要记住的实用结论有三条：

1. `await` 不会让出主线程给"重活"，它只是把后面的代码排到 microtask；如果你 await 的是一个同步的重计算，页面照样冻。
2. `setTimeout(fn, 0)` 不是"立刻"，是"下一轮 macrotask"，排在所有 microtask 之后。AI 用 `setTimeout(..., 0)` 来"等 DOM 更新完"是一种赌博式修复——它有时候有效是因为恰好排在了渲染之后，换个框架版本或换台慢机器就失效。看到代码里出现无解释的 `setTimeout(..., 0)` 或 `await sleep(100)`，那是一个时序 bug 被藏起来了，不是被修好了。
3. microtask 里产生的 microtask 会在同一轮被继续清空——一条自我繁殖的 promise 链能把浏览器饿死，连 `setTimeout` 都轮不上。

**Web Worker 是唯一真正的逃生口。** 重计算要离开主线程只能放进 worker（独立线程、不能碰 DOM、靠消息通信）；其余一切"优化"只是把长任务切成几段，让页面在段之间喘口气。

### 3.2 UI = f(state)：框架到底替你做了什么

现代框架的核心抽象是一个等式：**界面是状态的函数**。你不再描述"把这个节点的文字改成 X"，你描述"当状态是 S 时，界面长这样"，然后由框架去算出 DOM 要怎么改。

这个抽象带来两个必须理解的机制：

**重渲染的触发条件。** 组件重新执行渲染函数，是因为它自己的 state 变了、它的 props 变了、或者它订阅的 store/context 变了。渲染函数被重新执行 ≠ DOM 被重新创建——框架会把新算出的结构和旧的比对，只把差异写进真实 DOM。所谓"虚拟 DOM"就是这个比对的中间表示，它的意义不是"快"，而是**让你可以用"整个界面重画一遍"的心智模型写代码，而实际代价只有真实变化的那部分**。

但比对有代价。一个组件重渲染，默认带着整棵子树一起重跑渲染函数（即使最终 DOM 没变）。渲染函数里塞了排序、过滤、格式化大量数据的逻辑时，这代价就变成 3.1 的长任务。症状：输入框每敲一个字整页卡一下。

**key 是身份证，不是编号。** 渲染列表时框架需要知道"新列表里的这一项，是不是旧列表里的那一项"。key 就是这个身份判断。用数组下标当 key，在列表顺序变化、中间插入删除时，框架会认为"第 2 项还是第 2 项，只是内容变了"，于是复用了错误的 DOM 节点和组件内部状态。经典症状：**删掉列表第一行，结果第二行的输入框里出现了第一行的文字；或者勾选状态跟着位置走而不是跟着数据走。** 这个 bug 极其隐蔽，因为静态列表下永远正常。你该问的是：**"这个列表的 key 是什么？如果中间插入一条会发生什么？"**

**直接操作 DOM 会和框架打架。** 框架维护着一份"界面应该长什么样"的账本。你用原生 API 改了 DOM，账本不知道；下次重渲染按账本比对，你的改动被抹掉，或因节点结构对不上直接抛错。症状是"我加的元素时有时无""滚动位置随机跳回顶部"。看到框架组件里出现直接的节点查询和插入，先假设它有 bug。

### 3.3 state 的五个住址，以及"单一事实来源"

前端复杂性的根源不是渲染，是状态。一份数据可以住在五个地方，每个地方有不同的生命周期和不同的失效方式：

| 住址 | 生命周期 | 刷新后 | 适合放什么 | 放错的症状 |
|---|---|---|---|---|
| URL（path / query / hash） | 跟着地址走 | 保留 | 当前页码、筛选条件、搜索词、选中的 tab、详情 id | 用户没法把当前视图发给同事；点后退直接退出整个页面而不是回到上一个筛选 |
| 组件本地 state | 组件挂载期间 | 丢失 | 输入框草稿、展开/收起、鼠标悬停 | 组件一卸载就丢；父组件重渲染导致子组件重建时神秘清空 |
| 提升到共同父级的 state | 父组件挂载期间 | 丢失 | 两三个兄弟组件要共享的东西 | 提得太高：改一个小状态导致半个页面重渲染 |
| 全局 store | 页面会话期间 | 丢失（除非持久化） | 真正全局的东西：当前用户、主题、通知队列 | 什么都往里塞，最后没人知道谁在改它；数据过期了也没人清 |
| 服务端数据的本地缓存 | 你定义的失效策略 | 看策略 | 从 API 拿来的一切 | 见 3.4，这是最大的坑 |

**单一事实来源（single source of truth）**：每一份数据，只能有一个地方"说了算"，其他地方要么从它派生，要么根本不存。这条原则听起来抽象，检查方法非常具体：**同一个值，在代码里有没有出现第二次被独立赋值的地方？**

最常见的违反是"派生状态被存起来了"。比如既存了 `items` 又存了 `filteredItems`，还存了 `itemCount`。后两者本该是从 `items` 算出来的，一存就必须手动保持同步，而 AI 一定会在某条代码路径上忘记同步其中一个。症状：列表里明明有 3 条，计数显示 5；筛选条件改了，列表变了但"共 N 条"没变。你该问：**"这三个 state 里，哪些是可以从另一个算出来的？为什么要存？"**

### 3.4 server state 是缓存，不是状态

这是本章最重要的一节。

从 API 拿回来的数据，本质上是**远端真相在本地的一份缓存副本**。缓存有三个必答问题：key 是什么、什么时候失效、失效了怎么办。AI 写前端时几乎从不回答这三个问题，它只是：请求一次，塞进一个变量，然后渲染。

于是有了那个最经典的 AI 前端事故：**把服务端数据复制进本地 state 然后两边不同步。**

```
// AI 的典型写法
const [user, setUser] = useState(null)
useEffect(() => { fetch(`/api/users/${id}`).then(r => r.json()).then(setUser) }, [id])
// 然后在别的地方
const handleSave = async () => {
  await fetch(...)                 // 服务端改了
  setUser({ ...user, name: newName })  // 本地手动拼一份"应该是这样"的数据
}
```

第二行的问题是：服务端真正保存后的数据可能和你在本地拼的不一样——服务端会加时间戳、会规范化格式、会因为并发被别人改过、会触发级联更新。于是本地那份缓存和真相开始漂移。症状：**保存成功，页面显示的是你输入的值，刷新一下变成另一个值。**"刷新之后就不一样"是 server state 不一致的标志性症状，看到它就往这个方向查。

正确的心智模型是：**写操作之后，本地缓存应该被标记为失效，重新从服务端取；或者用服务端返回的完整对象整体替换本地副本，而不是自己拼。**

**缓存 key。** 缓存条目必须以"决定这份数据是什么"的所有输入为 key。列表页的 key 至少包含：资源类型、筛选条件、排序、页码、以及**当前用户身份**。漏掉用户身份，就有了那个恐怖的 bug：切换账号后看到上一个账号的数据。漏掉筛选条件，就是切换筛选后闪现旧结果。你该问的是：**"这份数据的缓存 key 包含哪些字段？换个用户/换个筛选，key 会变吗？"**

**失效策略。** 至少要想清楚四个时机：写操作之后（invalidate 相关的 key）、窗口重新获得焦点时（用户切回来了，数据可能旧了）、离开页面再回来时、以及时间超过 N 之后。这四个不必都做，但必须是**有意识地选择不做**，而不是从来没想过。

**stale-while-revalidate 的取舍。** 成熟做法是先显示旧缓存（页面不空白），同时后台重新请求，回来再替换。代价是用户短暂看到旧数据：对列表页是好交易，对余额、库存、权限不是。你要能判断哪些数据允许过期几秒。

### 3.5 异步竞态：先发的请求后回来

这是前端最纯粹的机制性 bug，也是 AI 命中率最高的坑。

场景：搜索框，输入即搜。用户敲 `ab`，发出请求 A；再敲一个 `c`，发出请求 B。网络不保证顺序，如果 B 先回来、A 后回来，而你的代码只是 `setResults(response)`：

```
时间 →
输入 "ab"  ├──发出 A ─────────────────────────► A 返回 → setResults(A 的结果)
输入 "abc" │    ├──发出 B ────────► B 返回 → setResults(B 的结果)
                                              ▲                  ▲
                                          界面正确           界面变回 "ab" 的结果
                                                          但输入框里写着 "abc"
```

最终屏幕上：输入框是 `abc`，结果是 `ab` 的。这就是"结果错位"。同一个机制会产生一整族症状：**快速切 tab 显示上一个 tab 的内容；快速点两个客户，详情页显示先点的那个；分页快速翻，停在第 3 页却显示第 2 页的数据。**

三种修法，理解它们的区别：

1. **取消（AbortController）**：发新请求前把旧请求 abort 掉。最干净，还省带宽。注意 abort 会让 fetch 抛出一个特定错误，必须和真正的网络错误区分开——否则用户每敲一个字就看到一次红色报错。这是 AI 加完取消后引入的第二个 bug，极常见。
2. **序号 / 最新优先**：给每次请求编号，回来时检查"我是不是最新的那个"，不是就丢弃。适合无法取消的场景。
3. **把请求的 key 绑进缓存层**：由缓存库保证"当前 key 是 abc，就只显示 key 为 abc 的数据"。这是最不容易写错的做法，因为竞态被结构性地消掉了，而不是靠每个调用点记得处理。

**去抖（debounce）不是修竞态。** 去抖只是减少请求数量，把竞态的概率降低。网络一慢，竞态照样出现。AI 被指出竞态问题时，非常喜欢加一个 debounce 然后说"修好了"。你要能识别这个假修复：**"debounce 减少了请求次数，但如果两个请求还是发出去了并且乱序返回，代码里哪一行会丢弃过期的那个？"** 让它指出具体那一行。

**组件卸载后 setState。** 请求发出后用户离开了页面，响应回来时组件已经不在。症状是控制台警告，或内存泄漏。清理函数（见 3.6）就是干这个的。

### 3.6 effect 与副作用：依赖、清理、以及两种无限循环

"渲染"应该是纯的：给定 state，算出界面。发请求、订阅、设定时器、操作 DOM 这些"对外界产生影响"的事情叫副作用，必须放在专门的位置（effect）。这里有三个必须理解的机制：

**依赖列表决定 effect 什么时候重跑。** 写多了（把每次渲染都新建的对象或函数放进去）→ 每次渲染都重跑 → effect 里又 setState → 再触发渲染 → **无限循环**。症状极好认：**Network 面板里同一个请求刷屏几百上千条，机器发烫。** 看到请求刷屏，直接查 effect 依赖。

**写少了 → 陈旧闭包（stale closure）。** effect 里捕获的是它上一次执行时那一刻的变量值。依赖漏了，effect 不重跑，里面用的还是旧值。症状比无限循环阴险得多：**定时器里读到的永远是初始值；点了三次"加一"，服务端只收到从 0 加到 1。** 没有报错、没有警告、只是数字不对。这类 bug 靠看代码很难发现，要靠"用一句话描述这个 effect 里用到的每个外部变量，什么时候会变"来审。

**清理函数是防泄漏和防竞态的地方。** effect 里开的东西——订阅、定时器、WebSocket、未完成的请求——必须在 effect 重跑前和卸载时关掉。没有清理的症状：来回切几次页面后同一个 WebSocket 连了五条；离开页面定时器还在跑；上一节的竞态。审查时最快的问法是：**"这个 effect 里创建了什么？对应的清理在哪一行？"** 只要 effect 里出现了订阅、定时器、连接、或可取消的请求，而 effect 没有返回清理函数，就是 bug。

框架的严格/开发模式常常会故意让 effect 多执行一轮，专门用来暴露"没写清理函数"的代码。AI 遇到这种双重执行的报错时，一个常见的错误反应是关掉严格模式——那等于把体温计砸了。

### 3.7 表单、重复提交与乐观更新

**受控与非受控。** 输入框的值由 state 说了算（受控），还是 DOM 自己保管、提交时才读（非受控）。受控能随时校验、联动、格式化，代价是每敲一个字触发一次渲染——大表单里的"输入卡顿"就来自这里。需要实时反应才受控。**最危险的是半受控**：value 由 state 给，某些路径又直接改 DOM，光标跳到末尾、中文输入法打一半被吞。"打中文时字被吃掉、光标乱跳"是这族问题的标志症状。

**防重复提交：disable 按钮只是 UX，不是保障。** 用户双击、网络慢时用户重按、手抖、脚本、以及浏览器自动重放，都能让同一个提交发出两次。前端把按钮置灰能挡住其中一部分，但存在一个时间窗口——从点击到 state 更新再到重渲染完成之前，第二次点击可能已经进来了。更根本的是：**前端是不可信客户端，用户可以直接构造请求，绕过你所有的按钮逻辑。** 真正的保障是服务端的幂等性（同一个 idempotency key 只生效一次，见第 02 章、第 04 章）。前端该做的是生成这个 key 并在重试时复用它。

审查话术：**"如果用户在 200 毫秒内点了两次提交，服务端会收到几个请求？会创建几条记录？"** 如果答案里只提到"按钮 disable 了"，说明只做了 UX 那一半。

**两边都要验证，但只有服务端算数。** 客户端验证为体验（立刻提示格式不对），服务端验证为正确性。AI 常只写一边：只写客户端，等着有人绕过写脏数据；只写服务端，让用户填完整张表才知道第一行错了。

**乐观更新（optimistic UI）**：不等服务端回来，先按"假设成功"更新界面，失败了再回滚。它值得做的场景有共同特征：**成功率极高、失败后果可承受、并且用户会连续做很多次**——点赞、勾选待办、拖动排序、发消息。不值得做的：支付、删除、任何用户会盯着结果看的操作。

做乐观更新，回滚路径必须写全，而这正是 AI 最容易漏的：
- 保存回滚所需的**旧值快照**（而不是"再减一"这种反向操作——多个并发操作时反向操作会算错）；
- 失败时恢复快照，**并且告诉用户**（静默回滚会让人以为自己看花了眼）；
- 处理"回滚时数据已经被别的操作改过"的情况；
- 最终以服务端返回的数据为准做一次校正。

症状识别：一个乐观更新如果失败后界面没有任何变化，说明回滚根本没实现——你可以在飞机上光看代码就判断：**catch 分支里有没有恢复状态的语句？**

### 3.8 SSR / CSR / hydration：两台机器渲染同一个页面

三种模式，区别只在"HTML 是谁生成的、什么时候生成的"：

```
CSR：服务器给一个近乎空的 HTML + 一个 JS bundle
     → 浏览器下载并执行 JS → JS 请求数据 → JS 生成 DOM → 用户看到内容
     首屏慢（要等 JS 和数据），但之后交互快；对爬虫不友好

SSR：服务器每次请求都执行组件、生成完整 HTML → 浏览器立刻显示
     → 再下载 JS → JS "接管"这份已存在的 HTML（hydration）→ 可交互
     首屏快，服务器有成本，且引入 hydration 这一层新的失败方式

SSG：构建时就把 HTML 生成好，运行时只是发静态文件
     最快最便宜，代价是内容是构建那一刻的
```

**hydration 是什么。** 服务端生成的 HTML 只是一具"尸体"——有结构有文字，但没有事件监听、没有状态。客户端 JS 加载后会再执行一遍同样的组件，把算出来的虚拟结构和已经存在的 DOM 对上号，然后挂上事件、接管状态。这个"对上号"的过程就是 hydration。

**mismatch 为什么发生。** 前提是：服务端和客户端两次渲染的结果必须一致。三类东西天生不一致：

1. **时间**：服务端渲染时是 10:00:00，客户端 hydrate 时是 10:00:02。任何 `new Date()`、"3 秒前"这类相对时间、倒计时，都会不一致。
2. **随机**：随机 id、随机排序、随机推荐位，两次算出来必然不同。
3. **只有一边有的信息**：`window`、`localStorage`、cookie 里的偏好、屏幕宽度、用户时区、浏览器扩展往页面里插的节点。服务端不知道这些，客户端知道。

症状：控制台出现一条关于服务端 HTML 与客户端渲染不匹配的报错；页面**先闪一下正确内容，然后跳成另一个样子**（或者反过来）；深色模式先白闪一下再变黑。

**为什么不能压掉这个警告。** mismatch 意味着框架在这段无法确认对应关系，它可能丢弃服务端 HTML 重渲染整棵子树——首屏优势没了，还多一次闪烁；更糟的是事件绑到错的节点上，于是"点第一个按钮触发了第二个的动作"。AI 遇到 hydration 报错最常见的两种处理都是错的：**加上抑制警告的属性**（把体温计砸了），或者**整个关掉 SSR**（把病人推出手术室）。正确的处理是按上面三类根因分类：时间和随机 → 在客户端挂载后才渲染这一部分（先渲染一个占位，效果上放弃这一小块的 SSR）；只有一边有的信息 → 同上，或者把信息挪到服务端也能拿到的地方（比如 cookie）。

审查话术：**"这个 hydration 警告的根因是时间、随机，还是只有客户端才有的数据？你的修复是消除了不一致，还是只是不再显示警告？"**

### 3.9 浏览器是不可信客户端：bundle、XSS、CORS、token

这是本章标题的那句话，它有非常具体的技术含义：**运行在用户机器上的一切代码和数据，用户都能读到、改掉、绕过。** 由此推出四条：

**（一）打进 bundle 的东西等于公开发布。** 前端构建工具会在**构建期**把环境变量的值直接内联进产物文件。以 `NEXT_PUBLIC_` / `VITE_` / `REACT_APP_` 这类前缀命名的变量尤其如此——这个前缀的语义就是"我知道它会被公开"。AI 被要求"让前端能调这个 API"时，最省事的写法就是把 key 放进这类变量。结果：任何人打开 devtools 的 Sources 面板、或直接下载那个 `.js` 搜索，就拿到了你的 key。

这里有个致命的认知陷阱：**这类泄露不产生任何错误，功能完全正常。** 它只会在某天变成一张异常的账单。验证方法只有主动去找：在构建产物里搜索你 key 的前缀。你该问的是：**"这个 key 在运行时是从哪读的？它会出现在浏览器下载的任何文件里吗？"** 正确的架构是：密钥只在服务端，前端调你自己的后端，后端再去调第三方（见第 09 章）。

**（二）XSS 的机制是"把数据当代码执行"。** 用户提交的一段文本里含有 `<script>` 或 `onerror=...`，如果你把它当 HTML 插进页面，浏览器会老老实实执行它。框架默认把插入的值当纯文本转义，所以默认是安全的；不安全的是那些明确"我要插原始 HTML"的 API（`innerHTML`、`dangerouslySetInnerHTML` 及各框架的等价物）。AI 实现"富文本""渲染 Markdown""显示后端返回的 HTML"时会直接用它们，因为那是最短的路。规则：**每一处插原始 HTML 的地方都要回答"内容来源是谁、经过了什么 sanitize"。**"我们自己后端返回的"不算安全答案——后端的内容也可能来自用户。

**（三）CORS 是浏览器对你的礼貌，不是服务端的防线。** 同源策略限制的是**浏览器里的脚本**能不能读到跨源响应；它挡不住 curl、挡不住脚本、挡不住任何非浏览器客户端。所以"加个 `*` 就好了"这种修复必须被追问：**"这个改动放宽了什么？现在谁能从哪些站点读到这个接口的响应？带 cookie 吗？"** 特别是允许任意来源同时允许携带凭据这种组合，等于把用户的登录态交给任何一个网页。CORS 的协议细节见第 02 章；这里你只需要记住定位方法：**CORS 报错出现在浏览器控制台，服务端日志里可能什么都没有（预检请求被拒的话）——这是"客户端限制"而不是"服务端故障"的信号。**

**（四）token 放哪的取舍。** 放 `localStorage`：JS 能读，所以任何一次 XSS 都能把它偷走；好处是跨域调用方便。放 httpOnly cookie：JS 读不到，XSS 偷不走；但会被浏览器自动带上，于是需要防 CSRF（见第 09 章）。没有免费的选项，只有"你更怕哪种攻击、你有没有做对应的防护"。AI 默认选 localStorage，因为代码最短。

**（五）所有校验都必须在服务端再做一遍。** 前端隐藏了"删除"按钮不代表删除接口不能被调用；前端只让你选自己的项目，不代表接口不接受别人的 id。**前端的权限控制是 UX，服务端的才是安全。** 问法：**"我用普通用户的 token 手动发一个管理员接口的请求，会发生什么？"**

### 3.10 流式 UI 的状态机：LLM 界面的特有坑

你会大量做流式的聊天/生成界面，它的状态比普通请求复杂得多，值得单独画出来：

```
        ┌──────────────────────────────────────────────┐
        ▼                                              │
     [idle] ──发送──► [connecting] ──首个 chunk──► [streaming] ──结束标记──► [done]
        ▲                  │                          │  │
        │                  │连接失败                   │  │用户点停止
        │                  ▼                          │  ▼
        └──重试────────► [error]  ◄──流中断/超时────────┘ [cancelled]
                            ▲                             （保留已生成的部分？）
                            └── 后端 500 / 解析失败
```

必须被回答的问题，每一个都是 AI 常漏的：

- **连上了但一个 token 都没来**，卡在 connecting 多久算超时？（没有这个超时，用户会盯着一个转圈的界面永远等下去）
- **流到一半断了**（网络断、后端崩、代理超时），已经显示出来的半截内容怎么处理：保留并标记"未完成"、还是清空？无论选哪个，**都必须让用户知道这是半截的**——最糟的结果是用户把一段被截断的回答当成完整答案。
- **用户点了停止**，前端停掉渲染很容易，但请求真的被中止了吗？后端还在为你烧 token 吗？（"停止"只改自己的显示，是常见的成本泄漏）
- **取消之后立刻重新发送**，上一条流的残余 chunk 会不会追加到新的消息里？这是 3.5 的竞态在流式场景的版本，症状是**两次回答的文字交错混在一起**。
- **流中间出错时怎么传达**。流式响应的 HTTP 状态码在第一个字节就定了（通常 200），之后出错只能在流内部用一个事件表示。AI 常只处理"HTTP 层错误"，对流内的错误事件视而不见——后端明明报错，前端显示一个正常结束的空回答。
- **自动滚动**：内容不断增长时滚到底部，但用户手动往上翻时必须停止自动滚动。少了这一条，用户永远没法读前面的内容。

审查一个流式 UI，最快的方法是直接要求：**"把这个界面的状态机列出来，每个状态的进入条件、退出条件，以及 cancelled 和 error 各自留下什么。"** 说不出来的，一定没处理全。

### 3.11 三态、布局与前端的可观测性

**loading / error / empty 是三个必须存在的状态，不是可选装饰。** AI 默认只写 happy path，因为它测试的数据永远有内容、请求永远成功、返回永远很快。四个具体的缺失症状：数据没回来时页面一片空白（用户以为坏了）；请求失败时界面停在 loading 转圈（永远转）；结果为空时显示一个空框而不是"没有找到匹配的记录"（用户以为坏了）；错误只在控制台里，界面上什么都不说。

再加两个 AI 几乎不测的边界：**超长文本**（一个没有空格的长串会把布局撑破或溢出屏幕）和**极端数量**（0 条、1 条、10000 条）。

**布局的最小必要模型。** 盒模型、flex（一维）、grid（二维）、断点（不同宽度换布局），四个概念覆盖绝大多数正经布局。AI 的坏味道是：固定像素宽高（`width: 1200px`）、绝对定位配手算偏移（`top: 137px`）、用负边距补对不齐。这些在你的屏幕上完美，换字号、换中文、换手机就全线崩溃。识别方法很物理：**把窗口拖到很窄**，出现横向滚动条、按钮跑出屏幕、文字重叠就是这个病。修复指令要说到机制——"这个容器用了固定宽度，改成弹性布局、窄屏下堆叠成一列"，而不是"手机上不好看"。同一族被系统性忽略的还有**可达性**：按钮用 `div` 拼、图标按钮没有文字标签、弹窗打开后焦点没进去。验证同样物理：**只用键盘 Tab 走一遍**，如果焦点消失、顺序乱跳、弹窗关不掉，就是这个病。

**前端错误的可观测性。** 你的服务端有日志，你的前端跑在几百台你看不见的机器上。默认情况下，用户那边报的错你永远不知道。需要三层网：组件级的 error boundary（一个组件崩了不要整页白屏，显示局部的降级 UI）、全局的未捕获错误和未处理 promise 拒绝的监听、以及**把捕获到的错误连同用户操作上下文送回服务端**。没有第三层，你的所有诊断都依赖用户截图。

顺带一个关键的失败方式：**未处理的 promise 拒绝是静默的**。一个 async 函数抛错、没人 catch，页面不会白屏、不会报红字给用户，只会"这个按钮点了没反应"。这是前端最难查的一类 bug，因为它连症状都很含糊。审查时问：**"这个 async 调用链上，每一个可能失败的地方，错误最终会走到哪个 UI 状态？"**

## AI 在这里最常犯的错，以及怎么识别

| # | 错误 | 可观察的症状 / 你该问的问题 |
|---|---|---|
| 1 | 把服务端数据复制进本地 state，写操作后手动拼一份 | **症状**：保存后显示的值和刷新后的值不一样。**问**："写成功后，本地这份数据是被失效重取了，还是你自己拼的？" |
| 2 | 不处理请求竞态 | **症状**：快速输入/快速切 tab 时，内容和当前选择对不上。**问**："如果第一个请求比第二个晚回来，哪一行代码会丢弃它？" |
| 3 | 用 debounce 假装修好了竞态 | **问**："debounce 之后，两个请求还是可能都发出并乱序返回。这种情况下代码怎么处理？" |
| 4 | 只写 happy path，缺 loading/error/empty | **症状**：白屏、永久转圈、空框无提示。**验证**：把网络调到最慢、把接口关掉、把数据清空，各看一遍 |
| 5 | effect 依赖写多 → 无限请求 | **症状**：Network 面板同一请求刷屏几百条，机器发烫 |
| 6 | effect 依赖写少 → 陈旧闭包 | **症状**：没有报错，但数字不对/定时器读到初始值。**问**："这个 effect 用到的外部变量有哪些？它们变了 effect 会重跑吗？" |
| 7 | effect 里创建订阅/定时器/连接却没有清理函数 | **症状**：来回切页面几次后，重复的连接、重复的定时器、请求数翻倍 |
| 8 | 用数组下标当列表 key | **症状**：删除/排序后，输入内容或勾选状态跟错了行 |
| 9 | 按钮 disable 当作防重复提交的全部方案 | **问**："绕过前端直接发两次请求，服务端会创建几条记录？"（幂等见第 02 章） |
| 10 | hydration 报错就抑制警告或关掉 SSR | **症状**：首屏闪一下变样。**问**："根因是时间、随机、还是只有客户端才有的数据？" |
| 11 | 把 key/secret 放进会被打进 bundle 的变量 | **症状**：没有任何症状——这是最危险的地方。**验证**：在构建产物里搜索 key 前缀 |
| 12 | 用插入原始 HTML 的 API 渲染用户内容 | **验证**：让接口返回一段含 `<script>` 或 `<img onerror=...>` 的字符串，看是被显示成文字还是被执行 |
| 13 | "CORS 报错就在服务端放行 `*`" | **问**："这个改动允许谁从哪些来源读什么？带凭据吗？" |
| 14 | 流式 UI 不处理取消与中断 | **症状**：点停止后文字还在往外冒；断网后留下半截内容且没有任何标记 |
| 15 | 固定像素布局、从不看窄屏 | **验证**：把窗口拖到手机宽度，看有没有横向滚动条 |
| 16 | 派生数据被单独存成 state | **症状**：列表和计数对不上、筛选变了统计没变 |
| 17 | 为了"能跑"而关掉类型检查、lint、严格模式 | **症状**：diff 里出现忽略注释、配置里多了关闭项。这是把警报器拆了，不是修好了 |
| 18 | 在框架组件里直接操作原生 DOM | **症状**：加的元素时有时无、滚动位置乱跳、偶发节点错误 |

## 判断清单

可以直接抄进 `CLAUDE.md` 或前端审查模板：

**状态**
1. 这份数据的 single source of truth 在哪？代码里有没有第二份独立赋值的副本？
2. 哪些 state 是可以从别的 state 算出来的？为什么被单独存了？
3. 哪些状态应该在 URL 里（筛选、页码、tab、选中项）？刷新和点后退分别会发生什么？
4. server state 的缓存 key 包含哪些字段？包含当前用户身份吗？
5. 写操作之后，哪些缓存被失效了？

**异步**
6. 每个异步操作的状态机是否完整：pending / success / error / cancelled / empty？
7. 用户在 200 毫秒内重复操作两次，会发生什么？乱序返回时哪一行丢弃过期结果？
8. 每个 effect 创建的东西，清理在哪一行？
9. 每个可能失败的 async 调用，错误最终走到哪个 UI 状态？有没有静默的 promise 拒绝？

**渲染**
10. 这个列表在一万条数据下会怎样？key 是什么？
11. 有没有在渲染路径上做重计算或大排序？
12. hydration 有警告吗？根因属于时间/随机/客户端专有数据中的哪一类？

**不可信客户端**
13. 构建产物里有没有 key、内部地址、全量数据？（搜一遍前缀）
14. 用户输入到渲染之间有没有转义？有没有插入原始 HTML 的地方？
15. 前端做的每一个权限判断，服务端有没有再做一遍？
16. 这次 CORS / 权限修复放宽了什么？

**交付前的物理检查**
17. Console 有没有红字和黄字？
18. Network 里请求数量是预期的吗？有没有重复请求？
19. 网络调到最慢，界面是什么样？把接口关掉呢？返回空数组呢？
20. 窗口拖到手机宽度，有没有横向滚动条？

## 飞机上的练习

**练习 1：竞态推演（纸上画时序图）**
搜索框，用户依次输入 `a`、`ab`、`abc`，三个请求分别耗时 300ms、100ms、200ms，间隔各 50ms。画出时间轴，写出屏幕上最终显示的是哪个请求的结果，以及中途会闪现哪些内容。然后写出三种修法各自会让哪几个请求的结果被丢弃。

*参考答案要点*：三个请求几乎同时在飞，返回顺序是 `ab`(150+100=250ms 前后)、`abc`、`a`。屏幕会闪现 `ab` 的结果、`abc` 的结果，最后被最慢的 `a` 的结果覆盖——**最终显示的是 `a` 的结果，而输入框里是 `abc`**。取消方案：`a` 和 `ab` 在发下一个请求时被 abort，只有 `abc` 会 setState。序号方案：三个都返回，但 `a` 和 `ab` 因为序号不是最新被丢弃（浪费了带宽）。缓存 key 方案：三份结果都进缓存，界面只读 key 为 `abc` 的那一份——顺带的好处是用户退回 `ab` 时立刻有结果。**判分标准**：有没有意识到"最慢的最早请求最终覆盖一切"是最坏情况；有没有区分"丢弃结果"和"取消请求"。

**练习 2：给聊天界面画完整状态机**
画出一个流式聊天界面的状态机，至少包含：idle、发送中、连接中、streaming、done、cancelled、error、加载历史消息、重试。标出每条转移的触发条件，以及每个终态**留下什么**（消息内容是完整的还是半截的？有没有标记？能不能重试？）。

*判分标准*：（a）cancelled 和 error 是两个不同的状态，处理不同；（b）标出了"connecting 超时"这条转移；（c）回答了"半截内容保留还是清空"并说明用户怎么知道它是半截的；（d）考虑了"取消后立刻重发"时旧流的残余 chunk 归属；（e）加载历史与正在流式输出是可以并存的两条独立的异步线。能画出前三条就已经超过大多数 AI 生成的实现。

**练习 3：五个 bug 报告，推断根因层**
不看代码，只根据症状写出最可能的机制根因和第一条验证动作：

1. "切换客户后，详情页先显示上一个客户的数据，半秒后才变对。"
2. "保存成功了，页面显示我输入的名字；刷新一下变回旧名字。"
3. "删除列表第一行后，第二行的备注框里出现了第一行的文字。"
4. "页面刚打开时深色模式闪一下白的。"
5. "生产环境某天账单暴涨，没有任何报错。"

*参考答案*：(1) 没有清空/失效旧缓存就发新请求，且旧数据仍在渲染——不一定是竞态，先看是否有"key 变了但仍显示旧 key 的数据"；验证动作：把网络调慢，观察闪现的是不是上一次的完整数据。(2) server state 被本地拼装覆盖，或写成功后没有失效缓存；也可能服务端根本没保存成功而前端只看了 HTTP 200 没看 body（见第 02 章）；验证：看 Network 里那个写请求的响应体，和刷新后 GET 的响应体对比。(3) 用数组下标当 key，组件内部状态跟着位置复用；验证：看列表渲染的 key 表达式。(4) hydration / 首屏渲染时读不到只有客户端才有的偏好（localStorage 或系统主题），服务端先渲染了默认主题；验证：看控制台有没有 mismatch 警告。(5) key 被打进了 bundle 被人拿去用——**注意这一条的判分重点是：能不能在"没有任何报错"的前提下想到泄露**；验证：在构建产物里搜索 key 前缀，同时看第三方后台的调用来源。

**练习 4：设计一个列表页的 server state 缓存**
一个"客户列表"页面，支持搜索、按状态筛选、排序、分页，登录用户可以切换所属团队。在纸上写出：（a）缓存 key 的完整构成；（b）四个失效时机各触发哪些 key 的失效；（c）新增一个客户后，哪些 key 必须失效、哪些可以不管；（d）用户从详情页返回列表，你希望立刻显示旧缓存还是等新数据，为什么。

*判分标准*：key 里必须包含**用户/团队身份**（漏掉就是跨账号串数据）和全部筛选维度；新增客户后应该失效"该团队的所有列表 key"而不只是当前这一页（否则翻到第二页还是旧的）；(d) 的答案要能说出取舍——列表这类数据适合先显示旧的再后台刷新，代价是短暂看到过期数据。

**练习 5：写你自己的十条前端验收清单**
不看上面的判断清单，凭这一章的机制自己写十条，然后对照。你写不出来的那几条，就是你还没真正理解的机制——回去重读对应小节。这份清单以后每次让 AI 写前端时贴给它。

## 落地后的练习

1. **制造并诊断竞态。** 让 Claude Code 写一个带搜索框的列表页（不要提竞态）。用 devtools 把网络节流到最慢档，快速输入几个字符，观察结果错位。然后要求它修复，并且明确要求："不要用 debounce 掩盖，告诉我哪一行代码丢弃了过期响应。" 对比修复前后的 Network 面板：请求是被取消了（状态显示取消/失败），还是照常返回但结果被丢弃了。

2. **把 loading/error/empty 逼出来。** 同一个页面，做三件事：网络节流到最慢看 loading 态；在 devtools 里把接口离线或让后端返回 500 看 error 态；让接口返回空数组看 empty 态。每缺一个，就用一句精确的指令让它补上（"接口返回空数组时显示'没有匹配的客户'并提供清除筛选的按钮"），而不是"处理一下边界情况"。

3. **搜自己的 key。** 让它写一个调用某个第三方 API 的前端功能，然后构建，在产物目录里用文本搜索你的 key 前缀。如果搜到了，让它改成"前端调自己的后端、后端持有 key"的结构，再搜一遍确认。这个练习做一次，你终身不会再犯这个错。

4. **注入一段 `<script>`。** 在后端接口里返回一段包含 `<script>alert(1)</script>` 和 `<img src=x onerror=alert(1)>` 的字符串，看前端是把它显示成文字（安全）还是执行了（XSS）。特别测试"渲染 Markdown""富文本预览"这类功能。

5. **压一个大列表。** 让它渲染一万行数据，打开性能面板录制一次滚动，看主线程上有没有超过十几毫秒的长任务块。然后要求虚拟化或分页，再录一次对比。

6. **打断流式输出。** 做一个流式聊天界面，然后依次测试：中途点停止、中途断网、后端在流中间返回错误、取消后立刻重新发送。记录每种情况下界面留下了什么；把没处理的情况按状态机的语言描述给它（"cancelled 状态下需要保留已生成内容并标记为未完成，且真正中止后端请求"）。

7. **打开严格模式看重渲染。** 打开框架的严格/开发模式和组件调试工具，观察 AI 写的组件在一次简单交互下重渲染了多少次。如果一次点击导致整页组件全部重渲染，去找原因：是不是 store 放了太多东西、是不是 state 提得太高、是不是每次渲染都新建了对象当 props。

8. **窄屏审查。** 把它写的每个页面拖到手机宽度，截图，然后练习用机制语言下指令："这三个卡片用了固定宽度导致横向溢出，改成在窄屏下单列堆叠"，而不是"手机上不好看，修一下"。
