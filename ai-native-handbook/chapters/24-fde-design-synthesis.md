# 第 24 章 设计合成：buy/build、架构适配、最小可落地系统、成功指标与真正落地

*本章一句话：最合适的架构不是最先进的那个，而是在这家公司的约束里最可能上线、最容易运维、最容易退出的那个——设计合成就是把约束翻译成形态、把形态切成最小切片、把切片绑上指标，然后让它真的被人用起来。*

## 为什么这一章对你重要

第 23 章结束时你手里有一堆东西：流程图、数据地图、谁痛谁反对谁买单、合规红线。它们还不是设计。设计合成是把这堆材料收束成一个能上线的系统的过程，而这个过程有两种典型死法。

第一种：技术正确、组织不合适。方案里有向量库、多 agent、微服务，评审时没人挑得出技术毛病，三个月后没人会运维，半年后系统还在跑但没人信它的输出。第二种：技术跑通了，没人能说清它有没有用。demo 惊艳，pilot 结束时业务方问"所以省了多少钱"，你手里只有一个 eval 分数。

FDE 的口碑就建立在避开这两种死法上。AI 能在十分钟里给你三套架构图，但它不知道这家公司的 ERP 只有一个每晚跑一次的 CSV 导出、不知道那个反对的部门主管其实在保护一条真实的风险、不知道六个月后维护这套系统的是一个兼职 IT。这些判断只能你做。本章给你做这些判断的顺序和工具。

## 核心机制

### 1. 顺序：约束在架构之前，用例在技术之前

设计合成的第一条纪律是顺序。绝大多数失败的方案都倒过来做了：先决定用 RAG 或 agent，再去找一个能套上的问题。正确顺序固定四步：

```
约束清单  →  用例选择   →  架构形态     →  组件与集成
(硬/软)     (三档+评分)    (错误代价定)     (buy/build/assemble)
```

约束清单的原料在第 23 章的 discovery 里已经采集了，这里要把它整理成两栏。**硬约束**是违反了就不能上线的：数据能不能出域、能不能进第三方模型、审计要求、现有系统的接口现实（ERP 只有夜间导出、CRM 有 API 但没人有 key）、预算与时间窗、团队能维护什么、失败的可接受度。**软约束**是可以用钱或时间换的：延迟、覆盖率、UI 偏好。

把两栏写在架构图前面有一个具体作用：每一条硬约束都会直接杀掉一批方案。"数据不能出境"杀掉所有默认调用境外托管模型的方案；"没有 on-call"杀掉所有需要有人半夜看告警的自主 agent；"ERP 无 API"把整个集成层从"调接口"改成"读文件"。先杀再选，剩下的选项通常只有两三个，选择反而容易。

你该问 AI 的第一句话不是"给我设计一个架构"，而是："**这是硬约束清单。先逐条告诉我每一条分别排除了哪些常见方案，再给我剩下的选项。**"如果它的回答里没有任何一条约束"排除"了任何东西，说明它没把约束当约束，只当成了背景描述。

### 2. 痛点到用例：三档翻译与"判断密集 / 规则密集"切片

同一个痛点可以翻译成三种完全不同的用例，它们的架构、风险、验证方式差一个数量级：

| 档 | 谁做决定 | AI 的角色 | 典型形态 | 首个用例 |
|---|---|---|---|---|
| 自动化 | 规则 | 没有或极少（确定性 workflow 里嵌一个分类） | 代码为主 | 适合 |
| 增强 | 人 | 出草稿、找线索、预填、对照 | 辅助工作台 | 最适合 |
| 代理 | AI | 自主多步执行 + 审批点 | agent 系统 | 几乎不适合 |

绝大多数首个用例应落在前两档。原因不是保守，是验证成本：增强档的输出天然有一个人在看，每一次纠正都是免费的标注数据；代理档的输出没人看，你得先建一套 eval 与监控才敢放出去（见第 21 章）。

翻译的方法是把流程切开。把第 23 章画的流程按环节标注：这一步是**规则密集**（输入确定则输出确定，"金额超过阈值就走二级审批"）还是**判断密集**（要读非结构化材料、要权衡、要问人，"这封投诉该归哪个责任部门"）。规则密集的环节交给代码，判断密集的环节才是 AI 的位置。一个常见错误是把整条流程整体交给 agent，让模型去做一行 `if` 就能做对的事——模型做错的概率不为零，而 `if` 是零。

切完之后你会发现，很多流程里判断密集的环节只有一两个，而且它们往往正是等待时间最长的地方：材料堆在某个人桌上等他看。那一两个环节就是候选用例。切片时要特别追问例外："这条规则有没有不适用的时候？谁来处理？"访谈记录里通常没有例外，例外全在老员工脑子里，而 AI 整理出来的流程图永远比真实流程干净。

### 3. 错误代价矩阵：可逆性 × 频率决定人工门在哪

这是本章最重要的工具。对候选用例里 AI 要做的每一个动作，问两个问题：做错了能不能撤回？多久发生一次？

```
                  低频                          高频
可逆    │ 全自动，事后抽查              │ 全自动 + 采样审计 + 反指标
        │（内部草稿、标签建议）          │（工单分类、文档摘要）
────────┼──────────────────────────────┼────────────────────────────
不可逆  │ 人工门前置，AI 只出建议       │ 不自动化；先做增强档，
        │（对外报价、合同条款）          │ 或用代码把它变成可逆
        │                              │（付款、删除、对外发送）
```

四个格对应第 14、15 章的自主性光谱上的四个位置，区别在于这里的坐标由业务给出，不由技术给出。右下角的"用代码变可逆"值得展开：对外发邮件不可逆，但"写入待发队列 + 三十分钟延迟 + 可撤回"就可逆了；直接更新 ERP 库存不可逆，但"写入一张 staging 表 + 人一键确认合并"就可逆了。很多时候架构里最值钱的一段代码就是这个把不可逆变可逆的薄层，它让 AI 可以放心出错。

人工门的位置也由矩阵定：门放在不可逆动作之前，不放在流程开头。放在开头的门（"AI 先问人要不要开始"）没有保护作用，只有摩擦；真正的错误发生在第七步，第一步的确认拦不住它。

### 4. 四种架构形态与它们的适用区间

AI 应用在形态上只有四种，其余都是组合：

| 形态 | 描述 | 适用的错误代价 | 可验证性要求 | 集成难度 |
|---|---|---|---|---|
| 单点增强 | 现有流程里加一个 AI 步骤（分类、抽取、摘要） | 低~中 | 低：人在看 | 低 |
| 辅助工作台 | 人主 AI 辅：草稿、检索、对照、预填 | 中 | 中：纠正率可测 | 中 |
| 自动化管线 | AI 主人审：批处理 + 抽检 + 异常升级 | 中 | 高：eval + 采样审计 | 中~高 |
| agent 系统 | AI 自主多步 + 审批点 | 低（否则不该做） | 很高：trace + eval + 回滚 | 高 |

这张表从右往左读：先看你的可验证性能做到哪档、集成能做到哪档，再决定形态，而不是先选形态再补验证。一家没有测试、没有 CI、日志靠 print 的公司（第 08 章的工程成熟度判断），最多支撑到辅助工作台；在这种环境上堆 agent 系统，出问题时你连 trace 都拿不到，第 22 章的诊断流程从第一步就卡死。

参考架构里的常见模式——内部知识助手、流程自动化、数据抽取流水线、客服增强、代码/文档迁移——各自的关键风险都能从表里推出来：知识助手的风险是检索质量与权限泄漏（见第 16 章）；数据抽取的风险是静默错误进入下游报表，需要 schema 校验加抽检；客服增强的风险是对外承诺不可逆，门必须前置；代码迁移的风险是没有测试就没有可验证性，先补测试再迁移。

### 5. 用例评分与否决项：首个用例的特殊标准

有了候选用例，用四个维度打分：**价值**（省的时间、钱、错误率，要能换算成业务方认的单位）、**可行性**（数据拿得到吗、有接口吗、权限批得下来吗）、**可验证性**（能不能量化对错、有没有 baseline）、**风险**（不可逆性、合规、对外影响）。每维 1~5 分，但**打分之前先过否决项**：

- 数据拿不到，或权限在项目周期内批不下来 → 否决
- 对错无法定义（"让报告更有洞察"）→ 否决
- 第一个动作就是高频不可逆 → 否决
- 需要客户没有的运维能力才能安全运行 → 否决
- 涉及的数据按合规不能进任何外部模型，且没有域内替代 → 否决

否决项的意义是防止总分掩盖致命项：一个价值 5、可行性 1 的用例，总分可能比价值 3、可行性 4 的高，但前者做不出来。AI 写的用例评估几乎总是只有加分项，看到一份没有任何否决项的评估，问它："**这五个用例里，哪一个有一票否决的问题？为什么？**"

首个用例还有三条额外标准：**快赢**（四到八周量级看到结果）、**可度量**（业务方自己能算出省了多少）、**低不可逆**（做错了不上新闻）。首个用例不是为了最大价值，是为了建立信任与拿到真实数据——之后每一个用例都站在它的信任上。为技术炫技选用例（"这个能展示多 agent 协作"）是 FDE 最贵的反模式，它把信任押在最难验证的东西上。

### 6. 三套候选方案与"为什么不选另一种"

对选定的用例，强迫自己出三套方案：最小、中等、理想。不是为了三选一，是为了看清每一级增量买到了什么、付出了什么。

```
方案    能力                          周期        主要风险               可逆性
最小    规则 + 单次调用 + 人审        周级        覆盖率低               高：随时下线
中等    辅助工作台 + 检索 + eval      一到两个月  检索质量、adoption     中：数据已进系统
理想    自动化管线 + 审批 agent       季度级      运维、漂移、锁定       低：流程已依赖它
```

然后写"为什么不选另一种"：为什么不选理想（客户没有运维能力、可验证性不够）；为什么不选最小（覆盖率太低，业务方看不到价值）。这一段是设计文档里信息量最大的部分，也是 AI 最不会写的部分——它会给你三套方案，但不会告诉你放弃哪两套的代价，因为那需要知道这家公司的约束。

把约束和形态合起来，得到一张"约束 → 形态"表。它是第 14 章决策图、第 16 章 RAG 判据、第 17 章微调判据、第 21 章三角检查在客户现场的合成：

| 约束 | 推出的形态 |
|---|---|
| 数据不能出域 | 域内部署模型，或脱敏层在前；先问脱敏后的数据够不够用 |
| 老系统无 API | 文件 / 邮件 / RPA 集成；批处理管线，不做实时 |
| 无 on-call | 只做增强，或带自动降级的管线；不做需要人半夜介入的 agent |
| 输出对错难定义 | 增强档；先用人工纠正率当 proxy 指标 |
| 知识每周在变 | RAG 而不是微调（见第 16、17 章） |
| 高频不可逆动作 | 加可逆层，或不做 |
| 单人 IT 兼职维护 | assemble 托管服务，胶水层不超过他能读懂的规模 |

### 7. buy / build / assemble：三年后谁维护

三分法：核心差异化的部分 build，通用能力 buy，其余大部分 assemble——托管服务加一层薄胶水。判断一个组件属于哪类，问四个问题：

1. **它是不是这家公司的差异化？** 客服话术库是，向量数据库不是；行业术语的抽取规则是，OCR 不是。
2. **谁维护？** 三年后这个组件坏了，是客户的 IT、是你、还是供应商？没有答案的组件不该 build。
3. **锁定风险有多大？** 换掉它要迁移什么：数据格式、prompt、eval 集、用户习惯。数据和 eval 集能导出的锁定可以接受，导不出的不行。
4. **演进速度匹配吗？** 模型层几个月一变，胶水层要能在一天内换模型；把模型调用硬编码进业务逻辑的 build，会在下一次模型升级时全部重写（见第 12 章）。

默认答案是 assemble。默认 build 一切的方案通常来自 AI 或想炫技的人；默认 buy 一切的方案通常来自没看过集成现实的采购。assemble 的薄胶水层——一个模型调用抽象、一个 prompt 版本管理、一个 eval runner——正是你作为 FDE 留给客户的可复用资产，也是你 OPC 产品的雏形（见第 27 章）。

AI 在这一步的偏向很稳定：它倾向选最新的框架，因为训练数据里最新框架的讨论最热。问它："**这个框架一年后如果停止维护，我们要重写哪些文件？换成标准库或托管服务要多做什么？**"回答里重写范围越大，build 的理由就越薄。

### 8. 集成现实：入口、出口、身份、数据重力

经验上，AI 应用一半以上的工作量在集成，不在模型。设计时对每一个系统边界写三行：

- **数据从哪进**：批（每晚 CSV）、流（webhook）、API（有文档吗、有 key 吗、限流多少）、文件（共享盘、邮件附件）、人工（有人手动粘贴）。
- **结果到哪去**：回写系统（要写权限，写错了怎么撤）、通知（邮件 / IM）、报表（谁看）、只留记录不动任何系统。
- **身份与权限从哪来**：AI 以谁的身份读数据？读到的是不是它不该看的？结果回写用谁的账号？审计日志里显示的是谁（见第 09 章）？

老系统没有 API 是常态不是例外。集成手段按可靠性排序：数据库只读副本（如果给）> 定期文件导出 > 邮件解析 > RPA 模拟点击。RPA 排最后，因为它随界面变化而碎，且没有幂等保证——脚本跑一半断了，你不知道那张单提交了没有（见第 02 章的幂等）。

**数据重力**决定架构落点：数据在哪，计算就往哪靠。核心数据在一个不能出域的数据库里，那么模型调用发生在域内、把结果写回域内，比把数据搬出去再搬回来可靠一个数量级——每多一次搬运就多一处不一致，多一个要解释给审计的复制（见第 07 章）。AI 出的架构图里，箭头几乎总是画得很顺：系统 A → 向量库 → 模型 → 系统 B。你要对每根箭头问："**这根箭头对应的真实接口是什么？谁给的 key？失败了重试还是丢？**"答不出来的箭头是虚线，虚线的数量决定了项目的真实工期。

### 9. 最小可落地系统（MVS）：一个瓶颈、一个用户群、一个指标、一条兜底路径

MVS 不是 MVP，更不是 demo。MVP 回答"有人要吗"，demo 回答"能不能演示"，MVS 回答的是"**能不能在这家公司的真实数据、真实权限、真实用户上跑起来并被测量**"。它的切法是竖切不是横切：横切是每个功能都做 30%（有个上传页、有个聊天框、有个管理后台，但没有一条路真正从客户的系统进、再回到客户的系统），竖切是一条路做到 100%——从真实入口拿到数据，经过 AI 步骤，结果落回真实出口，中间有人看着。

四个"一"是硬性的：

- **一个瓶颈上的环节**：第 23 章定位出来的那个，不是排第二的。
- **一个用户群**：三到八个人，坐得近、痛得深、有一个愿意当冠军用户的。不是"全公司客服"，是"处理退货投诉的那四个人"。
- **一个可测指标**：他们自己能算、你不在场也能算的数字。"每单处理时间从 40 分钟到 15 分钟"可以；"提升效率"不行。
- **一条人类兜底路径**：AI 挂了、慢了、错了，这四个人明天怎么继续干活？答案必须是"和上周一样干"，也就是老流程一天都没拆。MVS 是并联上去的，不是串联替换的。

四到八周的量级不是拍脑袋：它是集成一个真实入口出口、跑一轮真实数据、让用户用两周并测到指标的最短时间。短于四周通常意味着没接真实系统，长于八周通常意味着范围是横切的。

AI 会把 MVS 做成"全功能 v1"，识别信号很稳定：功能列表超过五条、出现"支持多种格式"、出现管理后台、出现"可配置的"。你该问的是："**把这个方案砍到只剩一个用户群、一个环节、一个指标。列出你砍掉了什么，以及每一项为什么可以等到 pilot 之后。**"它砍不掉的东西里，才有真正的最小系统。

MVS 和生产版本之间有一份差距清单，写 MVS 的时候就该同时写它，否则"把 demo 当生产"就会在 pilot 成功的那天发生——业务方说"那就全公司上吧"，而你的系统没有认证、没有重试、没有成本上限、日志靠 print。差距清单的固定条目：身份与权限、错误处理与重试、限流与成本上限、日志与 trace、eval 与定期回归、数据刷新、prompt 版本管理、告警与 on-call。每一条标"MVS 已有 / pilot 前补 / 扩展前补"。

### 10. ADR：给未来的自己和客户的记忆

架构决策记录解决一个具体的病：几周后没人记得为什么这么做。症状是同一个决定被反复重新讨论——"我们为什么不直接用向量库？""当时不是说过要用批处理吗？"——每次重新讨论都靠在场人的记忆，而记忆偏向最近一次争论的赢家。

ADR 的固定骨架：

```
ADR-007  退货投诉分类使用规则前置 + 单次模型调用，不用 agent
日期 / 决策人 / 状态（提议、采纳、废弃、被 ADR-012 取代）
背景：      投诉每天 200~300 条；60% 可由关键字规则判定；剩余需读全文
约束：      客户无 on-call；CRM 只有夜间导出；投诉回复对外、不可逆
选项：      A 全部走模型  B 规则 + 模型兜底  C agent 自主分类并回复
决策：      B
理由：      规则部分零错误率且可解释；模型只处理 40%，成本与错误面都小
后果（正）：日处理时间预计从 3 小时降到 1 小时；错误可定位到"规则还是模型"
后果（负）：规则要有人维护；模型部分的边界样本需要 eval 集
切换条件：  规则命中率低于 40% 持续两周 → 重评 A；纠正率低于 2% 且监控就位 → 考虑 C 的部分自动回复
```

两条纪律。第一，**后果一栏必须有负面**。只有正面后果的 ADR 是宣传稿，AI 起草的 ADR 几乎总是这样，你要追问："**这个决定让我们放弃了什么？六个月后最可能因为它后悔的是什么？**"第二，**每个组件都有一行 ADR**，哪怕只有三句话：为什么是它、替代是什么、什么情况下换掉。一个说不出替代方案的组件，通常是"AI 推荐的"或"上次项目用过的"，这两个都不是理由。

ADR 是让 AI 起草最划算的文档之一，前提是你先把推理讲给它听。反过来——让它先写 ADR 再由你认可——你会得到一份看起来完整、但理由是事后编的文件。顺序是：你说决策和理由，它整理格式，你检查负面后果和切换条件是不是真的。

### 11. 成功指标：北极星 → 驱动 → 健康，每一个配反指标

技术上跑通的系统，一半死在没人用，另一半死在没人能说清它有没有用。指标体系防的是第二种死法。三层：

| 层级 | 回答的问题 | 例子 | 谁看 |
|---|---|---|---|
| 北极星 | 业务值不值 | 每单处理时间、每月人工返工小时、错误导致的赔付 | 买单的人 |
| 驱动 | 为什么北极星会动 | 覆盖率（多少单经过系统）、采纳率（多少建议被接受）、人工纠正率 | 用的人、你 |
| 健康 | 系统还活着吗 | 延迟、失败率、每单 token 成本、eval 回归分 | 维护的人 |

每个指标写四样东西：**测量方式**（从哪个日志、哪张表算出来）、**基线**（上线前的数字）、**目标**（pilot 结束时要到哪）、**时间窗口**（按周还是按月看）。四样缺一样，这个指标就不可测，而不可测的指标在复盘会上会变成形容词——"感觉快了不少"。

**基线必须在上线前测。** 这是最常被跳过的一步，跳过的理由永远是"来不及"。测基线便宜得多：让那四个人在一周里每处理一单记一个开始和结束时间，或者直接从工单系统的时间戳算。没有基线，pilot 结束时你只有一个后测数字，而业务方会合理地问"那以前呢"——你答不出来，项目就从"省了 60%"变成"好像是快了"。

**反指标**：每个指标配一个防止它被玩坏的指标。处理速度配错误率，采纳率配"接受后又改回去的比例"，覆盖率配"被用户跳过的比例"，成本配延迟。单一指标必然被优化到失真（见第 21 章的机制），反指标是让失真在仪表盘上可见。

三种典型的错位要能一眼认出：**eval 分数当业务成功**——eval 到了 92 分，但采纳率 15%，因为输出格式和用户的工作流不合；**采纳率当价值**——大家都在用，但每单处理时间没变，因为他们用它的时间等于原来查资料的时间；**成本估算没有模型支撑**——方案里写"月成本约几百元"，但没有"每次调用平均输入多少 token、输出多少、日调用量、重试率"。问 AI："**按平均输入输出 token、日调用量、重试与 fallback 比例，给我一张每单成本与 P95 延迟的表，并标出哪个变量翻倍时成本会失控。**"没有这张表的成本数字是猜的（成本机制见第 12 章）。

### 12. Pilot：提前写好"看到什么就停"

Pilot 是一次实验，实验的定义是结果可能是"失败"。五个要素——真实用户、真实数据、有基线或对照、明确期限、提前写好的退出标准——少任何一个，它就退化成一次长 demo。

对照的三种现实形式，按成本从低到高：

- **前后对比**：同一批人，上线前两周的基线 vs 上线后两周。最便宜，但会把季节和学习效应算进来。
- **影子运行（shadow mode）**：AI 跑但不生效，和人的实际决定并排记录。零风险，直接产出 eval 集，pilot 前跑一周影子几乎总是值得的。
- **分组**：一半人用一半人不用。最干净，但小团队分不了组，而且不用的那组会有情绪。

退出标准要在第一天写在纸上，写三种结局：**成功**（北极星达到目标且反指标没恶化 → 进入扩展）、**失败**（看到以下任何一条就停：对外错误一起、用户绕过率超过一半、纠正率高于某阈值持续一周、安全或合规事件一起）、**不确定**（延长一次，最多几周，延长的理由必须是新信息而不是"再看看"）。提前写的作用是防止 pilot 结束时靠气氛判断——业务方投入了情感、你投入了时间，两边都不想说失败。

**不要在 pilot 里做 agent。** pilot 的目的是建立信任和拿到真实数据，agent 系统在没有 eval 与 trace 的环境里出错时（第 15 章的失败模式全都会出现）没人能解释为什么，一次没法解释的错误会把前面建立的信任全部烧掉。增强档跑通、纠正率稳定、监控就位之后，再考虑放宽（见 §14）。

### 13. Adoption 四道门与信任建立

使用率的流失是分段发生的，每一段的原因不同，混在一起看就只能得到"大家不爱用"的结论。四道门：

```
能找到 ──→ 第一次用得顺 ──→ 结果可信 ──→ 嵌入日常流程
  │              │                │               │
  不在他们        要复制粘贴、要      不知道为什么      要单独打开一个
  已经打开的      切窗口、第一次      这么说、纠正      工具、和绩效
  界面里          就报错             了没反应          不挂钩
```

每道门在日志里有不同的形状：第一道门流失，日志里根本没有这个用户；第二道门流失，有登录、没有第二次；第三道门流失，用了但接受率低、纠正后又回退；第四道门流失，用量在第二周掉到只剩冠军用户一个人。使用率一周从六成掉到一成，几乎总是第三或第四道门，而团队的第一反应通常是去修第二道门的 UI。

信任的建立有固定顺序，跳不过：**先辅助再自主**；**显示来源与置信度**（"这个分类依据的是投诉里的这两句话"）；**纠正闭环**——用户改了之后要看得见改动生效，哪怕只是下次同类样本的表现变了，否则纠正就是无偿劳动；**透明地承认错误**——把 pilot 的错误率写在培训材料的第一页，比让他们自己发现要便宜十倍。默认交互形态是"AI 建议 + 人确认"，不是因为保守，是因为它把每次确认都变成了标注。

变革管理里技术人最容易轻视的三件事：受影响者的**激励与恐惧**——处理投诉的人如果担心系统上线后裁掉两个，他们会用脚投票让 pilot 失败，而且不会告诉你；**反对者的合理诉求**——反对的部门主管通常指向一个真实风险（"分类错了是我背锅"），把他的诉求写进退出标准和兜底路径，反对者常常变成最认真的测试者；**管理层的可见成果**——买单的人需要在四周内看到一个数字，否则项目会在下一次预算会上被静默砍掉。

### 14. 演进与退出：什么触发 v2，什么触发下线

设计的最后一部分是写清楚系统的下一步和终点，两者都要有可观测的触发条件，不能靠"到时候看"。

**放宽人工门**的条件是三项同时满足：纠正率低于某阈值并持续若干周（不是某一周）、eval 集覆盖了已知的失败样本并稳定、监控和回滚已就位并演练过一次。三项里少一项就放宽，等于把一个没测过的系统推到自主档。**升级为 agent** 再加两项：错误代价矩阵里该动作在可逆格、trace 可以回放（第 21 章）。**下线**的条件也要提前写：北极星连续两个周期没有改善、维护成本超过节省、依赖的上游接口停了、或者一次不可接受的事故。

演进能不能做，取决于设计时的可迁移性：数据、prompt、eval 集要能导出成普通文件；模型调用要走一层抽象，换模型是改一个配置而不是改业务代码；供应商的能力可以用，但把它当成随时会消失的东西——避免锁定不是不用托管服务，是保证换掉它时要迁移的只有配置和胶水层。

设计评审的最后三问，是给方案做压力测试的：**最弱的一环是什么**（往往是那个"每晚跑一次的 CSV"或者"只有一个人会改的规则文件"）；**如果模型明天变差三成，系统还成立吗**（成立的方案靠的是规则前置和人工门，不成立的方案是把可靠性全押在模型上）；**如果关键人离职呢**（冠军用户走了 adoption 塌不塌；那个兼职 IT 走了系统有没有人能重启）。三问里有两问答不上来，方案就需要降一档形态。

### 15. 运维、交接与 FDE 的退出

方案里默认要打包的东西，不是可选项：身份与权限边界（见第 09 章）、日志与 trace（见第 08、21 章）、定期跑的 eval、成本上限与告警。AI 出的方案里这些通常缺席或者只有一句"加上监控"，你要求它具体到"哪个指标、什么阈值、告警发给谁、他看到之后做什么"。

Runbook 的骨架是"症状 → 检查 → 动作 → 谁有权"：

```
症状：分类建议全部变成"其他"
检查：1) 模型调用失败率（健康面板）  2) 昨晚 CSV 是否到达  3) 规则文件最近改动
动作：调用失败 → 切换 fallback 模型（配置项 MODEL_FALLBACK）
      CSV 未到 → 通知 ERP 管理员，系统自动跳过当日
      规则被改 → 回滚到上一版本（git tag）
权限：切换模型：IT；改规则：客服主管；改 prompt：需跑 eval 通过后由 IT 合并
```

"谁有权改什么"这一栏是 AI 写的 runbook 最常缺的，而它是交接后最先出问题的地方：有人为了应付一个特例改了 prompt，没跑 eval，两周后全线漂移，没人知道是哪天改的。模型升级走同一道门：新模型先在 eval 集上跑，分数不低于当前版本才切换，切换记一行 ADR。

交接完成的标准不是"文档交了"，而是三件可验证的事：**一个不了解项目的人按 runbook 处理了一次模拟故障**；**owner 有名字**，且他跑过一次 eval、改过一次 prompt 并看到 eval 结果；**eval 集、prompt 版本、数据导出都在客户自己的仓库里**，不在你的笔记本上。

FDE 的退出要在设计的第一天就开始：把自己设计成可替换的。留下的是能力不是依赖——诊断模板、用例评分表、ADR 模板、eval 集、runbook、那层薄胶水。这些资产在下一家客户可以复用，也是你 OPC 产品的雏形（见第 27 章）。客户在你走后三个月还能自己升级一次模型，是 FDE 交付质量唯一诚实的度量。
