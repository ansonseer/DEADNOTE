# 第 02 章 网络与 HTTP：一个请求的一生——状态码、超时、重试、幂等、CORS、流式

*一个请求会在路上的每一跳被拖慢、被拒绝、被重复、被截断，而你要审的不是代码写没写对，而是这四件事各自发生时系统会怎样。*

## 为什么这一章对你重要

你让 AI 做的所有"应用"，剥掉外壳都是同一件事：请求进来，状态改变，响应出去；中间再调几个别人的 API——模型、数据库、支付、邮件。"AI 写的东西跑不通"的第一层原因，大半落在这条路上：CORS 报错、请求挂住不回、重试把用户的订单下了三次、明明失败却返回 200 让监控一片绿、流式输出到一半断掉后把半截 JSON 当结果解析。

这些雷有一个共同特点：demo 阶段永远不炸，上线后一定炸。因为 demo 里网络永远通、下游永远快、用户永远只点一次。

这一章不教你写 TCP。它教你三件事：一个请求从浏览器出发到响应体回来，每一段会在哪里出问题、症状长什么样；HTTP 的语义（方法、状态码、header）为什么是一份契约，AI 最常在哪里违约；以及超时、重试、幂等、流式这几个机制是怎么相互作用的——单独看每一个都简单，组合起来才会出事。读完之后，你面对 AI 交付的任何一个 API 客户端或 endpoint，应该能在一分钟内问出五个让它露馅的问题，并且能用一条 `curl` 独立验证它的说法，而不是再问它一遍。

## 核心机制

### 2.1 一个请求的一生：路径，以及每一跳的失败方式

先把整条路画出来。从浏览器点一个按钮，到响应体的最后一个字节回来：

```
浏览器/客户端
  │ ① DNS：域名 → IP
  │ ② TCP 三次握手：建立连接（1 个 RTT）
  │ ③ TLS 握手：协商密钥、验证证书（1~2 个 RTT）
  │ ④ 发送请求：method + path + headers + body
  ▼
CDN / edge ──────── 可能直接从缓存返回，根本不到你的服务
  ▼
负载均衡 / 反向代理 ─ 改写 header、终止 TLS、选一台后端实例
  ▼
你的服务进程
  ├ 路由：匹配 path 和 method
  ├ 中间件：auth、限流、日志、body 解析
  ├ 业务逻辑
  │   ├ 调数据库（见第 05、06 章）
  │   ├ 调 LLM API（又是一整条这样的路）
  │   └ 调第三方（支付、邮件……）
  ▼
响应：status + headers + body（一次性或分块流式）
  ▲ 原路返回，经过同样的代理、同样的网络
```

每一跳都有自己的失败方式，而且症状各不相同。这张表值得反复看，因为诊断的第一步永远是"卡在哪一跳"：

| 跳 | 典型失败 | 你看到的症状 |
|---|---|---|
| DNS | 解析失败、解析到旧 IP、内网 DNS 与公网不一致 | `ENOTFOUND` / `getaddrinfo` 错误；浏览器能开但容器里的代码不能 |
| TCP 连接 | 端口没开、防火墙拦截、对端进程挂了 | `ECONNREFUSED`（立刻失败）或 connect timeout（等很久才失败） |
| TLS | 证书过期、自签名证书、SNI 不对、公司代理做中间人 | `CERTIFICATE_VERIFY_FAILED`、`self signed certificate in chain` |
| CDN / edge | 缓存了旧内容、缓存了错误响应 | 改了代码没生效；某些用户看到旧版本 |
| 负载均衡 / 代理 | 后端健康检查失败、代理自己的超时比你短、body 超过代理限制 | 502 / 504 / 413，但你的应用日志里一条记录都没有 |
| 路由 / 中间件 | path 拼错、方法不对、auth 拒绝、限流 | 404 / 405 / 401 / 403 / 429 |
| 业务逻辑 | 抛异常、逻辑错误 | 500，应用日志里有堆栈 |
| 下游调用 | 下游慢、下游挂、下游限流 | 你的服务变慢或返回 502/504；症状出现在你这里，根因在别处 |
| 响应回传 | 客户端读超时、连接被中间设备掐断、流式被代理缓冲 | 客户端 read timeout；流式"一次性到达"而不是逐字出现 |

一条经验规则：**502 / 504 / 413 而应用日志里没有记录，问题在你的进程之前**；**500 而日志里有堆栈，问题在你的代码**；**客户端超时而服务端日志显示请求正常完成，问题在两者之间的超时配置不匹配**。这三条能把一半的"AI 说不清是哪里坏了"直接定位到层。

**延迟从哪里来，为什么连接复用重要。** 看上面 ①②③：在发出第一个字节的请求之前，客户端已经花掉了 DNS 查询加两到三个来回（RTT）。跨洋链路一个 RTT 是百毫秒级，那么建连本身就是几百毫秒。如果每个请求都重新走一遍 ①②③，你的应用就在为每一次调用付这笔固定税。HTTP/1.1 默认 keep-alive——请求完成后连接不关，下一个请求直接复用——就是为了省掉这笔税。所谓"连接池"，就是客户端库维护的一组已经握手完成、可以立刻用的连接。

这件事的反面很具体：AI 生成的客户端代码里，如果每次调用都 `new Client()` 或者在函数内部创建 session 再销毁，高并发下会出现两个症状。一是延迟异常高，每个请求都在付握手税；二是端口耗尽——每个关闭的连接会在操作系统里停留一段 TIME_WAIT（几十秒量级），本机可用的临时端口只有几万个，每秒新建几百个连接，几分钟就把端口用光，之后所有新连接都失败，报 `EADDRNOTAVAIL` 或 `cannot assign requested address`。这类错误的特征是"平时好好的，压测一上来就全挂，等一分钟又好了"。

### 2.2 HTTP/1.1、HTTP/2、HTTP/3：并发与队头阻塞

这三代协议的差别，对你来说只需要理解一个词：**队头阻塞（head-of-line blocking）**。

HTTP/1.1 一条连接上同一时刻只能处理一个请求——发出去，等响应回来，才能发下一个。要并发就要开多条连接，浏览器对同一个域名的连接数有个位数的上限。所以 HTTP/1.1 时代的页面加载像排队买票：窗口只有几个，队伍前面一个人慢，后面所有人都等。

HTTP/2 在一条 TCP 连接上做多路复用：多个请求被切成帧交错发送，互不排队。窗口变成了一条传送带，理论上一个连接就够。但 TCP 本身是按序交付的字节流——只要一个包丢了，整条连接上所有请求的后续数据都得等这个包重传，即使那些请求跟丢的包毫无关系。这是 TCP 层的队头阻塞，HTTP/2 消除了 HTTP 层的排队，却把所有鸡蛋放进了一个篮子。

HTTP/3 换掉了篮子：底层不再是 TCP 而是基于 UDP 的 QUIC，每个流独立丢包、独立重传，一个流丢包不影响别的流；握手也和加密合并，建连更快。

机制层面你需要记住的推论：
- 你的服务与下游之间如果是 HTTP/1.1，并发能力受连接池大小限制。AI 写的"并发调 50 次 LLM API"如果连接池只有 10，实际是 10 个在跑、40 个在排队，表现为"并发了但没变快"。
- 在弱网、高丢包环境下，HTTP/2 的表现可能不如多条 HTTP/1.1 连接——因为一个丢包卡住所有流。
- 反向代理常常在对外一侧讲 HTTP/2 或 HTTP/3，对内一侧退回 HTTP/1.1。所以你在浏览器 network 面板里看到的协议版本，不一定是你的服务真正用的。

### 2.3 HTTP 是无状态的：状态放哪，以及 Cookie / Header / Body 的边界

HTTP 协议本身不记得上一个请求。每个请求都是陌生人敲门，服务端要靠请求里带的东西认出"这是刚才那个人"。这个"带的东西"只有四个地方可以放：

- **Cookie**：浏览器自动附带、按域名归属、可以被服务端设成 `HttpOnly`（脚本读不到）和 `Secure`（只走 HTTPS）。它的特点是"自动"：用户不用做任何事，每个同域请求都会带上。这个"自动"同时是 CSRF 攻击的根源（见第 09 章）。单个 cookie 大小是 KB 级上限。
- **Header**：`Authorization: Bearer <token>` 是最常见的用法。header 由代码显式附加，不会被浏览器自动带上，所以跨站不会泄漏，但也意味着每个调用点都要记得加。header 总大小在多数服务端和代理那里有 KB 级限制，超出会得到 431 或被代理直接切断——把一个巨大的 JWT 塞进 header 就会撞上这个。
- **URL / query string**：会进访问日志、浏览器历史、Referer 头，长度也有 KB 级限制。任何 secret 都不该出现在这里。AI 生成的代码把 `?api_key=xxx` 拼进 URL 是常见错误，症状是日志里能直接 grep 出密钥。
- **Body**：只有 POST / PUT / PATCH 才有意义，大小限制由服务端和每一层代理各自决定，超过谁的限制谁就返回 413。分层限制不一致时的症状是：本地测试上传 20MB 没问题，上线后 413，因为前面多了一层代理，它的默认上限比你的应用小。

**服务端把"记住的东西"存在哪里**，决定了服务能不能横向扩展。把 session 放在进程内存里（一个 `Map` 或全局 dict）在单实例 demo 里工作得很好；一旦重启就全部丢失，一旦部署两个实例，请求被负载均衡分到另一台，用户就"随机掉线"。这也是为什么默认设计是"无状态服务 + 外部状态"：进程本身不记东西，状态放到数据库、缓存、队列里（见第 07 章）。识别方法很简单，问 AI 一句："这个服务开两个实例，登录态还在吗？"如果它开始解释 sticky session，说明状态确实在进程里。

### 2.4 请求方法与幂等性：重试策略的根据

HTTP 方法不只是命名习惯，它们各自承诺了一件事：**重复执行会不会改变结果**。

| 方法 | 语义 | 幂等 | 重复执行的后果 |
|---|---|---|---|
| GET | 读 | 是 | 无副作用，可随意重试、可被缓存 |
| HEAD | 只要头 | 是 | 同上 |
| PUT | 整体替换到指定状态 | 是 | 执行十次和一次结果相同 |
| DELETE | 删除 | 是 | 第二次可能返回 404，但资源状态不变 |
| PATCH | 局部修改 | 不保证 | "把余额加 10"重复执行就多加了 |
| POST | 创建 / 触发动作 | 否 | 重复下单、重复发送、重复扣款 |

幂等（idempotent）的定义是：执行一次和执行多次，对系统状态的影响相同。注意是"对状态的影响"相同，不是"返回值"相同——DELETE 第二次返回 404 不影响它的幂等性。

这个属性之所以是全章的枢纽，是因为**重试的安全性完全由它决定**。网络里有一种失败是"不知道成没成"：请求发出去了，响应没回来。可能是请求根本没到，可能是服务端处理完了而响应在路上丢了。对幂等操作，这个不确定性无所谓，再发一次就是。对非幂等操作，再发一次意味着可能重复产生副作用。AI 写的通用 HTTP 客户端最爱在这里犯错：一个 `retry(3)` 装饰器不分方法一律重试，于是网络抖动一次，用户的付款请求被提交了三次。

把非幂等操作变成可安全重试的办法就是 **idempotency key**，2.7 节讲它的实现原理。

### 2.5 状态码是契约：4xx 改请求、5xx 等一等、429 退避

状态码的第一位数字回答一个问题：**这次失败是谁的责任，调用方接下来该做什么**。

- **2xx** 成功。200 有 body、201 创建了资源、202 已接受但还没处理完（异步任务的正确表达）、204 成功且无 body。
- **3xx** 重定向。301/308 永久、302/307 临时。注意：老的 301/302 会被很多客户端把 POST 改成 GET，307/308 才保证方法不变。AI 写的 POST 到一个会重定向的 URL，最后落地时变成了 GET 并且 body 丢了——症状是服务端收到的是"空的 GET 请求"。
- **4xx** 调用方的错，**改请求再发，不要原样重试**。原样重试 400 只是把同一个错误再产生一遍。
- **5xx** 服务方的错，**等一等再重试可能会好**。
- **429** 单独拿出来：不是你错也不是它错，是你太快了。正确应对是退避（backoff），并且优先遵守响应里的 `Retry-After` header。

细分几个 AI 最常混用的：

| 状态码 | 含义 | 应对 | 对 AI 说什么 |
|---|---|---|---|
| 400 | 请求格式或参数错 | 改请求 | "把请求体和文档里的必填字段逐个对照" |
| 401 | 未认证：不知道你是谁 | 换/刷新凭证 | "token 是否过期？header 名字对不对？" |
| 403 | 已认证但无权限 | 改权限或换身份，重试没用 | "凭证是对的，但这个身份没有这个权限，不要再重试" |
| 404 | 资源或路径不存在 | 查 URL 和文档 | "这个 endpoint 在官方文档里存在吗？引用原文给我看" |
| 405 | 方法不允许 | 换方法 | "路径对了但方法错了" |
| 408 / 客户端超时 | 等太久 | 看超时链 | "谁的超时先到的？" |
| 409 | 冲突（版本、唯一约束、重复的幂等键带不同参数） | 读最新状态再决定 | "冲突的是哪个约束？" |
| 413 | body 太大 | 拆分或压缩 | "是应用限制还是代理限制？" |
| 422 | 格式对但语义错 | 改内容 | 同 400 |
| 429 | 限流 | 退避，看 Retry-After | "退避策略是什么？有没有读 Retry-After？" |
| 500 | 服务端未处理异常 | 可重试，但先看日志 | "服务端日志里的堆栈是什么？" |
| 502 | 代理拿不到后端响应 | 后端挂了或 crash | "应用进程活着吗？健康检查过了吗？" |
| 503 | 服务暂时不可用（过载、维护） | 退避重试 | 同 429 |
| 504 | 代理等后端超时 | 后端太慢，代理先放弃 | "代理超时和应用超时分别是多少？" |

**401 与 403 的区别是全书反复出现的一对**：401 说"我不知道你是谁"，应对是提供或刷新凭证；403 说"我知道你是谁，但你不能做这件事"，无论重试多少次都一样。AI 遇到 403 常常去"修 token"，遇到 401 常常去"修权限"，两者都白费。凭证本身的几种形式（API key、Bearer token、OAuth、session cookie）及各自的失效方式在第 09 章展开，这里只需要一条：**token 会过期，过期的表现就是原本工作的请求突然 401**；如果 AI 写的客户端没有刷新逻辑，症状是"运行一小时后所有请求都失败，重启就好"。

**用 200 返回错误是最隐蔽的违约。** 形如 `200 OK` + `{"success": false, "error": "insufficient balance"}`。它破坏的是整条链上所有依赖状态码的东西：监控看到的是 100% 成功率；重试逻辑不会触发；负载均衡的健康检查通过；调用方的 `if resp.ok` 分支走进成功路径，然后拿着一个没有 `data` 字段的对象往下走，在几层之外抛一个和真正原因毫无关系的 `undefined` 错误。识别方法：看 AI 写的 handler 里 `catch` 块返回什么——如果 `catch` 里 `return res.json({error: ...})` 而没有 `.status(...)`，就是这个问题。反过来审客户端：如果它的错误判断靠 `body.success` 而不靠状态码，说明它在适配一个违约的服务端。

还有一个反向的违约：**5xx 的 body 里带内部细节**——堆栈、SQL、内部主机名、依赖版本。这是给攻击者的地图（见第 09 章）。正确做法是 5xx 对外只给一个错误 ID，细节进日志。

### 2.6 超时的分层：没有超时等于无限挂起

"超时"不是一个数字，至少是三个：

- **connect timeout**：从发起连接到 TCP 握手完成的上限。它保护你不被"对方根本不在"拖死。防火墙丢弃 SYN 包（而不是拒绝）时，没有 connect timeout 的客户端会等到操作系统的默认上限，通常是分钟级。
- **read timeout**：两次收到数据之间的最大间隔。它保护你不被"连上了但对方不回话"拖死。注意它是"间隔"不是"总时长"：一个每秒吐一个字节的服务端永远不会触发 read timeout。
- **total deadline**：整个请求从发起到结束的上限。它是唯一能保证"这个调用一定会在 N 秒内返回（成功或失败）"的东西。

三者各管一段，缺一个就有一个洞。AI 生成的代码最常见的两种情况：完全不设（很多常用 HTTP 库的默认行为就是永不超时——这一点你应该在你用的库上亲自验证，而不是信任任何人的说法）；或者只设一个笼统的 `timeout=30`，而这个参数在不同库里含义不同——有的是 connect+read 各 30，有的是总时长，有的只是 read 间隔。

**没有超时的症状很有辨识度**：请求数不多，但服务的连接数、线程数或事件循环里的挂起 promise 单调增长，永远不下降；日志里没有错误，因为没有东西失败，它们只是永远没完成；最终表现为服务"越来越慢然后不响应"，重启后恢复，几小时后重演。这是典型的"一个慢下游拖死整个服务"：你的服务每个 worker 都在等那个不回话的下游，新请求进来没人接。

**超时链：每一层的超时必须比它上游短。** 想象用户浏览器 → 你的 API → LLM API。如果浏览器等 30 秒，你的 API 等 LLM 60 秒，会发生什么：第 30 秒浏览器放弃，用户看到失败并点了重试；你的服务器还在为第一个请求等 LLM，同时开始处理第二个；LLM 那边两个请求都在跑。用户点几次，你的后端就有几倍的负载，而每一份工作的结果都没人要。正确的排列是从外到内递减：网关 60 秒 > 你的 API 50 秒 > 下游调用 40 秒。这样最内层先放弃、向外报告一个明确的错误，每一层都还来得及做点什么（记日志、返回 504、清理资源），而不是被外层突然掐断。

一个具体的诊断技巧：**客户端说超时，服务端日志说请求正常完成用时 45 秒**。这不是 bug，是超时链倒挂——客户端的 30 秒先到了。修法不是把客户端超时调大（那只是把问题推给用户），而是问：为什么要 45 秒？如果这个操作本来就要几十秒（跑模型、生成报告、发一批邮件），它就不该在一个请求-响应周期里做完，应该返回 202 + 一个任务 ID，把工作丢进队列，让客户端轮询或订阅结果（队列的代价——顺序、重复、可见性——见第 07 章）。AI 写的 handler 里如果有 `await sendEmail()`、`await runModel()` 这样的长操作直接串在请求里，就是在等这个雷炸。
